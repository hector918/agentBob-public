# promptlib 语料导入

把收集到的文学文本导入 promptlib 素材库。库会自动切块、嵌入,之后可被语义
检索(检索出的片段将用作音乐/图片生成的素材)。

配套工具 **corpus_import**——**认证与端点已自动处理**。

## 标准流程:脚本转换 → 文件 → 引用式导入

成规模的语料(几十条以上)一律走这条,**核心纪律:大段正文永远不进 tool_call
参数**。模型一次能吐的 token 有限,把整份语料内联进参数(无论是 `corpus_import`
的 items,还是 `fs write` 的 content)都会在半路被截断,产出坏调用。

1. **拿到源数据**:下载或已有(如 `shijing.json`)。
2. **用脚本转换落盘**:用 `terminal` 跑一段脚本(python 等)读源文件、按下面的
   整理规则映射成规范 import JSON,**写到空间里一个文件**。是脚本写盘,不是模型
   逐字吐——所以再大也不会截断。规范格式:
   ```json
   {"caption":"…","items":[{"heading":"…","body":"…"}, …]}
   ```
   (也可以只写 `[{"heading":…,"body":…}, …]` 数组,caption 用工具参数给。)
3. **引用式导入**:`corpus_import({"file":"<文件路径>"})` —— 参数就一个路径,
   工具在服务端读文件、带 key 一次 POST。需要覆盖/补 caption 就加 `caption` 参数。

> 上下文会被源数据弄脏(读很多文件/长输出)时,可以把第 1-2 步用 `delegate`
> (suite `files`)丢进子任务,子任务产出文件路径,你在主上下文里再 `corpus_import`。
> 注意 `corpus_import` 是主上下文的工具,导入这一步在主上下文做。

**内联 items 只给三五条临时的**:`corpus_import({"caption":"…","items":[…]})`。
超过这个量就走文件,别内联。

## 整理规则(脚本按这个映射)

**一个 item = 一个检索单元**,这是唯一要做对的事:

- 一首诗/一阕词/一段独立文本 = 一个 item。**不要**把多首合并进一个 item,
  也不要把一首拆成多个 item;
- `heading` 填「题目 · 作者」(会和正文一起被嵌入,让"李白写月亮的诗"这类查询
  能命中;也是展示时的出处)。没有题目/作者可省略 heading;
- `body` 是正文,保留原有换行。**不用**清洗内部空行或行尾空白——服务端会归一,
  item 永远不会被意外劈开;
- `caption` 写清楚集名+来源+采集时间,这是整包内容在库里的标签;
- 保持原文用字(繁体不要转简体),检索跨繁简可用。

## 分包

- 单次调用 ≤ **16 MiB**、≤ **50000 items**;超过就按集/卷分成多个文件多次导入,
  每次调用在库里落为一条独立内容(工具会在超限时提示你分包);
- 相同内容重复导入是**幂等**的(返回同一条内容,不会重复占库),失败重试安全。

## 工具返回

- 成功 = 返回内容 JSON(含 `id`/`caption`)。嵌入是异步的,提交即可,无需轮询;
- 报 400 = items/body 空或格式错;报 401 = key 未配置/不对(报告用户不要重试);
- 报"文件太大"/413 = 拆分文件;报限流/429 = 按提示的 Retry-After 稍后重试;
- 报"读不到文件" = 先确认脚本把规范 JSON 写到那个路径了。

## 采集纪律

- 只导入公有领域或明确可用的文本(古典诗词文集通常公有领域;当代作品须确认
  授权)。caption 里必须记来源;
- 导入前把采集物核对一遍:去重、剔除乱码/截断的条目、确认 UTF-8;
- 完成后向用户汇报:导入几包、各包 caption、每包 item 数、返回的内容 id。
