# chat-retrieval sidecar（冷记忆）

对话语料的长期检索服务：把消息按公司分区存进带向量扩展的 Postgres，按对象 / 时段 / 语义三种问法捞回**结构化结果**。
它自己**从不调用 LLM**。

---

## 在架构中的位置

一个 Python 服务（FastAPI + asyncpg），跑在自己的容器里，自带一套 Postgres；向量与重排模型又是它自己的下游 HTTP 服务，可以单独摆到有算力的机器上。主进程只通过 HTTP 与它对话。

主进程侧是 `leaf/retrieval/` 模块，向 trunk 注册两个能力：

| 能力 | 方向 | 消费者 |
|---|---|---|
| `contract.RetrievalFeed` | 写 | 流程层在回合收尾时 `EnqueueTurn` |
| `contract.RetrievalClient` | 读 | 模型可见工具 `recall_memory`（`leaf/tools/58-recall.go`） |

**默认关闭。** `Start` 在 `retrieval.enabled` 与 `base_url` 都给齐之前什么都不注册；消费者据此降级——`recall_memory` 报告不可用，流程跳过入队。配了 api key 就在每次请求上带 `X-API-Key`。

### 写路径是持久 outbox，不是直连

回合结束时 `40-feed.go` 把这一回合的用户事件与助手回复落成 `bob_retrieval_outbox` 的行，一个 drain goroutine 按 tick 批量推给 sidecar。

- 每条用户事件保留**自己的**说话人 handle，群里的归属才不会糊成一团；
- 语料写入是尽力而为的旁路：入队失败只记日志，**永远不让一个回合失败**；
- 写入用的是不受回合取消影响的上下文——会话关闭和进程停机都会取消回合 ctx，但这条已经算完的语料该落还得落。

outbox 有几处是设计，不是实现细节：

**2xx 才删行。** sidecar 的写入端点是同步的——embed 与落库都成功才回 200。它不能返 202，因为 drainer 把 2xx 当「已持久化」并删掉自己的行；202 之后的后台失败就是永久丢数据且不重试。

**毒丸批次进死信。** 内容类 4xx 被识别成永久性拒绝，整批 dead-letter，免得一批坏数据把 FIFO 队列永久堵死。

**硬上限。** sidecar 长期挂掉时 outbox 会无界增长（每行带全文），队列有个行数天花板，扫除时从**最老**的开始丢。宁可丢掉最旧的冷记忆，也不能把主库撑爆。

**进库前脱敏。** 文本走 `heartwood/scrub` 并按长度截断。语料是 append-only 的——不删不改，撤回和编辑都不回退——凭证一旦进去就取不出来了。

### 可观测性

`leaf/retrieval/90-panel.go` 把队列深度、队头年龄和当前排空状态挂到 webui 面板上（仅管理员可见，因为叶子地址和失败文本都是部署细节）。

这条不是装饰。drain 失败只在由通到断的那一刻打一条 WARN 然后闭嘴，于是一次长期中断在日志里只有每次重启一条记录，唯一的痕迹是行数在涨。**把状态放到有人看的地方，比放在日志里管用**——这也是为什么读不到统计时面板显示 `?` 而不是 `0`：一个读不出来的队列绝不能渲染成一个空队列。

## 功能

### 写入

`POST /messages` 与 `/messages/batch`（单条即 N=1，批量有条数上限）。每条消息带：

- 公司（分区键）、会话、频道 / worker（多成员编排下的路由信息）；
- 说话人的**不可变 handle**——account 是可变的（可认领、可合并），所以语料只存 handle，查询时由主进程把 account 展开成 handle 列表；
- **双时间戳**：来源声明的时间（客户端可伪造）与调用方权威收到的时间；
- 角色、正文、可选语言标签；
- 可选的派生标签（情绪 / 是否承诺 / 短意图）与自由 metadata。

空正文在门口就被拒（422）：空串会让整批 embed 被后端拒绝，而批量端点对同一批重试永远失败——那是一颗毒丸，得让调用方走死信而不是重试。

### 检索

单一入口 `POST /retrieve`，按 `query_type` 分派：

| query_type | 回答的问题 | 做法 |
|---|---|---|
| `entity_mentions` | 某个人 / 公司 / 项目说过什么、被谁提过 | 作者匹配 + 字面模糊 + 向量语义三路召回，按消息去重后重排 |
| `time_window` | 某段时间发生了什么 | 时段内的代表性消息（给了查询就语义切片，没给就取最近若干条）+ 聚合统计：总量、独立用户、按天分布、活跃用户 |
| `semantic` | 通用语义兜底 | 向量召回 + 重排 |

过滤条件是通用的一组：公司、用户、worker、频道、会话、语言、角色、派生标签、时间区间、用户属性。

**查询形状错误一律 400，不是 500。** 模式与参数不配套（比如要求按作者查却没给 ID）会响亮拒绝，而不是三个分支全部跳过返回空——调用方的 LLM 分不清「没数据」和「这个查询是个空动作」。同理，400 让调用方去修查询，500 会触发它的「服务故障」处理（fail-open、重试），那是错误的反应。

**返回结构化数据，叙述交给调用方。** 话题建模与时段叙事曾经在这里，后来整条移除了：主进程拿 `time_window` / `entity_mentions` 的结果用自己的 LLM 现场综述，质量更好，而且不需要维护一条离线流水线。

### 探活与自检

`/health` 确认进程和库都通。库挂了返 503 + degraded，让探针能区分「进程在但库死了」。它用最轻的查询而不是计数——健康检查是高频的，在大分区表上做全表计数会越来越慢并周期性压库。

`/selftest` 是**接口符合性自检**：一个请求把四件事一次验完——

1. 库连通；
2. 向量扩展版本够新（旧版没有迭代扫描，带过滤的召回会差）；
3. **embedding 维度与 schema 相符**；
4. 重排服务可达。

第三项是首跑最容易全挂的地方：维度不符时每一条 INSERT 都会失败。它还区分两种不符——服务端返回的维度比期望**大**是可接受的（可截断的模型家族），比期望**小**就是配错了模型，直接判失败，别写脏数据。

这个端点的意义是**代替一份部署前的手工清单**：清单会被跳过，一个返回 503 的端点不会。

## 内部结构

```
main.py               FastAPI 入口：lifespan、鉴权依赖、/health、/selftest
config.py             全部配置从环境变量读
clients/db.py         asyncpg 连接池、分区管理、向量格式化
clients/embedder.py   向量服务客户端（OpenAI 兼容协议）
clients/reranker.py   重排服务客户端
ingestion/handler.py  写入端点：批量 embed → 确保分区 → 事务内批量 INSERT
retrieval/api.py      /retrieve 路由与 fail-closed 校验
retrieval/*.py        三个 query_type 的 handler + filters→SQL 的翻译
schema.sql            分区表 + 索引
```

### 分区是隔离

`messages` 按公司做 LIST 分区。这一条同时解决两个问题：

- **召回正确性**——「中等选择性的元数据过滤 + 全局向量索引」是个经典的欠召回陷阱（先取全局近邻再过滤，过滤完就没剩几条了）。带公司过滤的查询经分区裁剪只命中单个分区的索引，召回才是对的。
- **跨公司隔离成为结构性保证**——一次查询物理上只进自己公司的分区。

普通索引建在父表上、自动传播到现有及未来分区；向量索引必须**按分区单独建**。新公司的分区由写入路径按需创建，用 advisory 事务锁串行化——否则同一新公司的两个并发首批会双双通过存在性检查，输家撞 duplicate table 让整批失败。

### 但分区键不是身份

跨公司不泄露**首先**靠主进程每次都下这个 filter。路由层对缺失的公司过滤直接 400 拒绝（fail-closed），分区是第二道防线。

`recall_memory` 工具本身也不含身份逻辑：scope 由流程解析出的 caller 夹定——私聊只回忆自己的，群里只回忆本群的——模型只管给 query。数据面鉴权（`X-API-Key`）是第三道：叶子装着跨公司语料，没有这道门，任何能到达端口的进程都能读任意分区、或者往里注入「记忆」。

### 三处顺序上的讲究

都是被连接池教出来的：

**查询向量在拿池连接之前算。** embed 是外部 HTTP 调用，超时按分钟计；攥着一条池连接干等会把池抽干。

**重排在连接归还之后做。** 而且重排失败只是退回向量分加一条 WARN，不是整个查询失败。

**向量索引的检索参数必须每次 checkout 重设。** 连接归还时的 RESET 会把它们清掉，只在建连接时设一次的话，之后会静默退回默认值——带过滤的向量查询于是欠召回，且不报任何错。这类「静默退化」是最难发现的一种 bug，所以值得在代码里写死原因。

### 响应顺序不能信

OpenAI 兼容的向量协议不保证返回顺序（所以才有 `index` 字段）。客户端按 index 排序后再核对条数：

- 乱序会把 A 的向量配到 B 的消息上——静默的语料损坏；
- 少返会让朴素的配对丢掉尾巴，然后照常返回 200。

## 设计理据：为什么这部分要出主进程

**依赖形状完全不同。**
这是一套 Python 生态：FastAPI、asyncpg、一个带向量扩展的 Postgres，以及两个本地推理服务。把它们塞进主进程要么意味着主进程变成 Python，要么意味着在 Go 里重造向量检索——两条路都不是。做成 sidecar 之后，模型服务可以单独摆到有算力的那台机器上，主进程零改动。

**检索与生成解耦。**
这个服务只做检索，生成式调用的主权完全在主进程。好处是双向的：sidecar 不需要模型池、不需要凭证、不需要知道「回合」是什么；主进程不必接受一段它没法审计的叙述，拿到的是带精确时间戳的原话，可以直接当证据摆给用户。

**fail-open。**
服务不在时主进程照常运行——`recall_memory` 报告不可用，语料在 outbox 里排队等它回来。冷记忆是增益，不是关键路径，任何时候都不该因为它挂了而让一个回合失败。

**存储选型是可以重来的，维度不行。**
向量存在通用关系库里而不是专用向量库，是按规模做的取舍：中等规模下两者性能持平，而关系库在元数据过滤、事务和运维复杂度上完胜；真到了规模换不动的那天，被替换的只有一个客户端模块。

但 **embedding 的模型与维度是一次性选择**：换了等于所有历史向量作废重算。这类冻结依赖应该在文档、schema 注释和自检端点里**同时**写明，而不是让它安静地躺在配置文件的一行默认值里。
