# browser sidecar（browserd）

把整个浏览器子系统——chromium 进程、页面动作、登录态金库、人类接管——搬进独立容器的服务。
主进程侧只剩一个薄 HTTP 客户端和一个模型可见的 `browser` 工具。

---

## 在架构中的位置

`sidecars/browser/` 是一个**独立的 Go module**：自带 `go.mod`、自带 vendor 目录、离线可构建，主进程的 module 不包含它（嵌套的 `go.mod` 就是模块边界）。

它构建成自己的镜像：

- 构建阶段编译 `cmd/browserd` 成一个静态二进制；
- 运行阶段是 debian slim + chromium + 字体（含 CJK），非 root 用户运行；
- 一个持久卷挂成它自己的数据家目录，装 profile 金库和它自己的配置；
- 入口用 tini 转发信号，收到 SIGTERM 走优雅关闭——chromium 逐个关掉，目录与 profile 原样保留，下次启动是热的。

主进程镜像因此可以完全不装 chromium。

### 主进程侧的对接点

对接点只有一个包：`leaf/tools/browserremote/`。

| 方向 | 主进程侧 | 协议 |
|---|---|---|
| 模型动作 | `browserremote.Client`（`client.go`）→ 唯一的模型可见工具 `browser` | JSON over HTTP，控制面 |
| 人类接管 | `browserremote` 实现 `contract.BrowserTakeover`（`takeover.go`），由 `leaf/webui` 消费 | SSE 帧流 + 输入 POST，接管面 |

两个面是**两个独立的监听器**。接管面的 SSE 是长连接，混在控制面上会把控制面的 goroutine 和超时设置一起拖住；分开之后，一条被人看了半小时的接管流不影响任何一次 `navigate`。

地址来自 `BROWSERD_LISTEN` / `BROWSERD_TAKEOVER_LISTEN`；主进程侧用 `BROWSERD_URL` 指过来，接管面的地址由控制面地址推导（同 host、约定端口），部署时只需配一个 URL。

接管面的启动失败**不是致命的**：控制面（browserd 存在的理由）继续服务，只是人工接管这一项没了。

### 信任模型

**browserd 不做任何授权判断。**

它是私网里的可信执行器：主进程跑完 warrant 授权、解析出「哪个身份、哪个会话、哪种模式」，把结果（`scope` + `profile_key` + `mode`）随每个请求一起送来，browserd 照单执行。

- 两个面共用一把 `BROWSERD_API_KEY` 作 bearer。这把 key 认证的是「主进程」这**一个**客户端，**不编码任何用户业务**。
- 谁能接管哪个浏览器，由主进程 webui 侧先裁决完再发起。人的浏览器永远只连主进程、连不到 browserd。
- key 未配置时进程在启动日志里大声 WARN——那时只剩网络隔离一层防线，这个端口绝不能出私网。

曾经有过一版把「逐次接管」的授权票据编进 browserd，后来整条退掉了：那是把用户业务塞进了一个不该懂它的服务。

### 工具永远在

`browser` 工具**永远注册**，不随后端可用性出现或消失。browserd 没配或挂了，工具的 `Run` 报告后端不可用。

消失会让模型以为「这件事做不了」，报错才让它知道「这件事现在做不了」。只有 `contract.BrowserTakeover` 的注册受配置门控——没有 URL 就没有接管这个能力。

## 功能

### 一个工具，12 个动作

模型看到的是单个 `browser` 工具加一个 `action` 枚举：

`browser_navigate` · `snapshot` · `click` · `type` · `press` · `scroll` · `back` · `console` · `get_images` · `dialog` · `vision` · `tab`

合成一个工具是有意的：

- 模型的工具列表短一截，长列表本身就是选择噪声；
- 授权只需要一条 cap，而不是十二条；
- 工具能在**动作层面**自我把关——未 `navigate` 过的会话调交互动作直接拒绝，连 browserd 都不打扰；
- 同一个远程页面上的并发动作被序列化，不会互相踩。

这条自我把关有来历。更早的版本把交互动作作为独立工具**按会话可见性**门控（跑过一次 navigate 才出现），因为「用户刚发了张图」时 `get_images` 看起来很相关，模型会拿它去读用户的附件。合成单工具之后，门控从「可见性」变成了「运行期拒绝」——工具一直在，用错了会被明确告知先 navigate。

### ref 协议

`snapshot` 返回的不是 CSS 选择器森林，而是一棵紧凑的可交互元素树，每个元素带 `@e1` / `@e2` 这样的 ref id，`click` / `type` 用 ref 定位。

模型不必构造或猜选择器——对小模型尤其关键。ref 每次 snapshot 重新从 `@e1` 编号，所以提示词里明确要求：任何可能让页面重排的交互之后要重新 snapshot。

Go 侧还对 ref 做了形状校验（只接受 `@e` 加数字），把模型构造的属性选择器注入挡在解析期。

### 登录态金库

每个身份（member）在 browserd 的持久卷上有一份 master profile 目录。

- worker 回合跑在从 master 播种的**只读副本**上：自己的 chromium、自己的目录。同一身份的并发回合互不打架，副本用完即弃。
- 播种时跳过缓存类子目录（体积大、可再生、不含登录）和 chromium 的进程单例锁文件（带着活锁的副本会让新实例以为目录被占）。
- 只有一条路径能写回 master：人接管副本、登录成功、显式「保存登陆」。
- 金库另有导出/导入端点（tar.gz），供主进程做备份。导出对**正被 checkout 的** profile 直接 409——chromium 活着时它的内嵌数据库是不一致的，一份坏备份比没有备份更糟。

登录 cookie 走一条**旁路**：从活着的浏览器内存里经调试协议取全量 cookie（含 session cookie）存到 master 旁边。磁盘写回只能带上 chromium 已刷盘的部分，而且结构上排除 session cookie（没有过期时间就不落盘）——不走这条旁路，就得关掉浏览器才能保存，还照样丢一部分登录。

### 人类接管

接管面把某个 scope 的活 chromium 以 SSE 截屏流推给 webui，反向接收鼠标/键盘事件。

这是一条**与模型不同的信任路径**：截屏订阅与输入分发直接走调试协议，不经过给模型的那份严格白名单。理由是这条路径的门在别处——webui 的管理员认证，加上「只有显式发起接管才会开流」。

- 同一个 scope 同时只允许一条接管流。后来者驱逐先到者，并等它完全释放之后再获取，这样新流是这个标签页上的第一个观察者、能应用自己的画质档。
- 一条五分钟没有任何输入的流会自己关掉。开着的流会把 profile 副本**钉住**（豁免空闲回收），一个被遗忘的接管否则会永久占着它。

### 控制保持（hold）

人在接管里切到「控制」模式时，前端对该 scope 声明一个心跳租约。

- 租约期内，模型侧的每个 `browser` 动作返回一句固定的让路提示，而不是去和人抢同一个页面。
- 租约是**心跳制**：不续期就静默过期。所以无论接管流怎么死（关标签页、断网、进程重启），模型都不会被永久堵住。
- 人**显式**交还控制时，额外留一张一次性便条，下一回合由提示词层递给模型：「人弄完了，接着做」。
- TTL 自然过期**不留**便条——人可能只是断了网，下一个动作照常进行就好。

两种结束方式的语义必须分开，这是这块设计的要点：显式交还是一个事件，超时只是一个缺席。

## 内部结构

### 控制面（`browserd/`）

`server.go` 是一台 mux 加一个 `*browser.Pool`。每个 handler 都很薄：解码 → `Pool.AcquireRouted(scope, profileKey, mode)` → 调对应的动作函数 → 装信封。

端点分三组：

- **动作**：navigate / snapshot / click / type / press / scroll / back / dialog / console / get-images / vision / tab；
- **会话管理**：purge（清掉某 scope 的浏览器状态）、save（保存登陆）、live（该 scope 现在有没有可接管的活实例，只读、绝不拉起 chromium）；
- **金库**：`POST /profiles` 是活 checkout 快照（接管选择器的数据源），`GET /profiles` 是持久化 profile 列表，加上导出/导入。

`wire.go` 定义整套请求/响应类型。**信封的分层是刻意的**：

- 传输层问题（方法错、body 解不开）→ 4xx；
- **动作层失败**（导航超时、选择器找不到、profile 被占）→ HTTP 200 + `ok:false` + `error`。

后者是正常的、模型该看到的错误，不是服务故障。把它们做成 5xx，主进程的健康统计会把「模型点错了一个按钮」记成「后端坏了」，然后把一个健康的后端冷却掉。

`/healthz` 除了存活还回显 browserd**实际解析出来的**配置。两个进程读各自的配置文件；页面超时如果不一致，慢动作在主进程侧会表现成传输错误而不是超时。把解析结果摆在健康端点上，部署时一眼能看出漂移——这是被动诊断面，不强制握手。

`takeover.go` 是接管面的三个端点与逐流的驱逐、空闲关闭逻辑。`profiles.go` 是金库的列举/导出/导入，以及一把按 profile 的 I/O 锁。

### 引擎层（`tools/browser/`）

这一层按职责分文件，是这个 sidecar 的真正主体：

| 文件 | 职责 |
|---|---|
| `pool.go` | chromium 实例与 profile checkout 的**单一所有者**：启动、空闲 TTL、LRU 收割、console 环形缓冲、JS 对话框处理、数据目录清扫。唯一 import 底层调试协议包的地方 |
| `actions.go` | 每个浏览器操作作为一个 `(ctx, *Session, params)` 的纯 Go 函数。换引擎时这是唯一要重写的文件 |
| `ref_map.go` | 可交互元素发现与 `@e<n>` ref 协议，一段注入的 JS |
| `tools.go` / `specs_export.go` | ToolSpec 定义。主进程的远程 shell 直接复用导出的 Spec，模型看到的名字、描述、参数 schema 两边逐字节一致，单一真相源 |
| `tabs.go` | 多标签/弹窗管理。点击或 `window.open` 拉起新 target 时，引擎仍绑在原 target 上、模型会瞎掉；这里跟踪活 target、自动跟随孤立弹窗，并在每次列举前先对账 |
| `custodian.go` | profile 独占 checkout 的**单 goroutine actor** |
| `humanize.go` | 人类输入模拟：带曲率与抖动的鼠标轨迹、元素内随机落点、逐键打字节奏 |
| `screencast.go` | 接管面背后的调试协议层：截屏帧订阅与输入分发 |
| `profile.go` / `profilecopy.go` | master 目录解析、副本播种、陈旧单例锁清理 |
| `logincookies.go` | 登录 cookie 旁路 |
| `hold.go` | 控制保持租约与一次性恢复便条 |

两处值得单独说：

**custodian 是一个 actor。** 谁持有哪个 profile、何时回收，全部状态活在一条 goroutine 上串行处理。于是这个功能引入的所有恶心并发——跨 scope 抢占、释放与取消的竞争、空闲回收、接管钉住——一个锁都不需要。它有两道**自动**释放门：拥有者 scope 的最后一个会话结束，或一次 checkout 空闲超过 TTL 被回收。释放会关掉 chromium，但 cookie 留在磁盘上——**释放不是登出**。

**humanize 的规划器是纯函数。** 几何与时序（轨迹、落点、按键间隔）都由注入的随机源驱动，可确定性单测；只有分发那几个 helper 碰引擎。用的是普通伪随机而不是加密随机——这是行为模仿，不是安全材料。

### 清扫与关停

sidecar 自己转两类定时清扫，因为主进程的 housekeeping 够不着它的磁盘：

- **空闲清扫**：超过空闲 TTL 的实例被关掉，但按契约**保留数据目录**，下次动作热重启；
- **数据目录清扫**：正因为上一条保留目录，没有这一条它们会在卷上无界增长。按修改时间的 TTL 收割，且**排在空闲清扫之后**跑，免得一个刚关掉的 scope 因为一条过期的活会话记录被跳过。

启动时还有一次性清扫：崩溃在导入中途留下的 staging 目录（OOM / SIGKILL 会绕过清理），每个可能几百兆。

关停走的是和空闲清扫相同的语义：停止接受、关掉每个 chromium、目录与 profile 保留。

### 辅助包

`tools/` 下另有几个小包：

- `policy` —— 路径与命令的三分类：**禁止**（直接拒绝，不走审批。「不许做的事就别问」——一个永远不会被批准的审批只会把回合钉在那儿）、**需审批**、**放行**；
- `file` —— 沙箱内的读 / 搜 / 改；
- `neterror` —— DNS 类失败的统一识别，加一句**处方式**提示。抽象的「换个方式试试」对小模型没用，它需要一个具体的下一步，否则会在同一个品牌名的各种域名变体上打转；
- `textcap` —— 大文本截断与截断标记。在**工具边界**就止血：一次臃肿的返回能有十万 token，进了对话历史之后连压缩都救不回来（压缩提示词本身就会撑爆）。

### 移植来的支撑层

`config/` 与 `core/` 是主进程重建之前那套代码的**冻结分支**，留在这里只为让引擎层原样编译。它们不参与主进程的架构约束，也不该反向影响主进程——真正被守着的只有一个包。

### scrub 分叉与等价性守卫

`scrub`（凭证脱敏）在主进程属于 `heartwood`，是「必须处处逐字节一致」的原语。sidecar 是独立 module，**没法 import `heartwood`**，于是这里有一份手抄的分叉。

`arch/51-scrub-parity_test.go` 把这份分叉焊死：

- canonical 目录里每个 `.go` 文件必须在分叉里有**逐字节相同**的对应文件；
- 反向也不许有多余文件；
- 任何漂移直接把 CI 打红；
- 确有正当理由的差异要显式登记并写下理由（当前登记为空）。

这不是假想的风险。分叉曾经冻在一个旧版本上，而主副本一路打了四轮脱敏补丁，连续几轮 review 都没发现——因为每轮只读了主副本。守卫把注释里的承诺变成了机器强制的不变量。

## 设计理据：为什么这部分要出主进程

**chromium 是不肯讲道理的邻居。**
一个页面就能吃掉几个 G，而 OOM killer 挑的不一定是它。chromium 跑在自己的容器里之后，它的内存与 CPU 再怎么爆，杀的是 browserd，主进程的对话回合不受影响；重启策略把它拉回来，登录态在持久卷上原样还在。

**主进程镜像保持干净。**
主进程是一个静态链接的 Go 二进制，不需要为了「有时候要开个网页」而背上 chromium、字体和一整套图形栈。这条与其它 sidecar 是同一个动机：重依赖（chromium、CUDA、Python 生态）挡在主进程之外，sidecar 想部署到哪台机器就哪台机器，主进程零改动。

**独立 module 是代价，不是好处。**
独立 module 意味着不能复用 `heartwood`，于是产生了 scrub 分叉，于是需要一个 arch 守卫。这笔账认了：换来的是 sidecar 可以独立构建、独立 vendor、独立发版，不被主进程的依赖图牵着走。但**分叉必须有守卫**——这是这里最值得抄走的一条经验。

**权限不下沉。**
一个「哑」服务的价值在于它对用户业务一无所知。它不知道什么是公司、什么是角色、谁是管理员；它只知道请求带没带那把 key，以及请求里写的 scope 和 profile 是什么。所有关于「谁可以」的判断留在主进程——那里才有 warrant、permissions 和身份解析。
