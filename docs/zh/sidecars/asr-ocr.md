# 语音转写与 OCR sidecar

三个小服务：两个语音转写后端（`fun-asr` / `moss-asr`）与一个 OCR 后端（`pp-ocrv6`）。
它们共用同一种接线方式——**主进程零代码改动，只在模型池里多一条 entry**。

---

## 在架构中的位置

主进程的模型池按 `kind` 选路：`kind: asr` 的条目服务语音转写，`kind: ocr` 的条目服务图像取字。一个 sidecar 只要把自己伪装成该 kind 期望的协议，池子就能把它当成一个普通 provider 用。

| kind | 线协议 | 主进程侧调用者 |
|---|---|---|
| `asr` | OpenAI 兼容 `POST /v1/chat/completions`；音频作为 `audio_url` 的 data-URI 内容块进去，转写文字作为 assistant 消息出来 | `leaf/asr/`（进站转写）、`leaf/tools/99-audio.go`（按需拉取） |
| `ocr` | `POST /ocr` multipart（`image` + 可选 `lang` / `bbox` / `enhance`），返回逐行框与合并文本 | `leaf/tools/96-ocr.go`（`vision task=read`），provider 实现在 `leaf/model/providers/36-rapidocr.go` |

两条主进程侧的路径值得先说清楚，因为 sidecar 的很多取舍是被它们逼出来的。

### 语音分两个位次

`leaf/asr/10-asr.go` 在**进站时**转写——在消息落库之前。转写结果直接进消息正文，下游所有读者（提示词、存储的历史、语料 feed）当普通文字看，只打一个标记让模型知道这是说出来的不是打出来的。

它按「这段话是谁的话」分位：

- **指令位**——发送者自己的、无字幕的语音条。转写**就是**他的请求，像打字一样放进消息文本，不做净化：那是用户自己的话在用户自己的槽位里，他打的字也不会被净化。
- **素材位**——带字幕的片段、从引用消息里带进来的片段、视频的音轨。第三方内容，要框起来、注明来源、走和引用行同一套卫生处理。

这个分位是整块设计的重点。在它之前，转写会被附到字幕后面、无边界地落进用户角色——这是系统里**唯一**一条把别人的话不加工具边界送进指令通道的路径（工具结果是 tool 角色，引用回复有专门的行处理）。

### 进站有一条时长线

超过约 30 秒的片子不在进站转写，而是**announce** 一句，让模型按需用 `audio` 工具去拉。

这条线是**延迟预算，不是能力上限**：进站是同步的，有人在等这个回合起步；后端能一口气吃下长得多的音频，但进站付不起那个墙钟。

「拒绝」和「失败」在这里必须分清楚：转写失败会给模型一句「请用户重发」的兜底，而对一个我们**主动选择不转**的片子说这句话既是假话，又会把模型从那个还能取到文字的工具身边推开。

announce 只对**音频**做，视频不 announce：视频音轨通常没有可辨识的语音，给每个分享的视频都广告一句「有话可取」会白买一轮工具调用。文件仍在附件列表里、`audio` 工具也接受视频——words 依然可达，只是不主动推销。

### 按需那条腿自带闸

`leaf/tools/99-audio.go` 单次最多转写 5 分钟，并**报告剩余区间**。

分段策略是「让模型自己当分段器」：它要更多就带下一个区间再来一次，够了就停。这里刻意没写切片拼接引擎——那种引擎总是把整段都转完，包括没人问的那 50 分钟。

它还有**自己的**超时，这不是礼貌而是止损：provider 的硬超时会**记进条目健康**，两次慢调用就足以把唯一一条 `kind: asr` 冷却掉，连带把进站转写一起打瘫。自带的上下文超时过期只是一个普通的 context 错误，只赔上这一次调用。

### 图像不预抽取

图片不在进站 OCR，而是模型通过 `vision` 工具按需读。

`96-ocr.go` 的 `readImageText` 与 `97-vlm.go` 的视觉腿共用一个 `kindChat`——一个**绑死单一 kind** 的模型池句柄。媒体工具只能够到自己那个后端，永远够不到通用 LLM。读字腿只收图片：给一段动态场景做逐帧转写不是「逐字转写」的意思，悄悄采一帧则是在回答没人问过的问题。

## fun-asr

**定位**：`kind: asr` 的常规后端，短语音条的主力。一个 0.8B 端到端语音识别模型（中文含方言、英文、日文），CPU 上跑，外面套一层 OpenAI 兼容的 FastAPI shim。

**接口**：

| 方法 | 路径 | 谁在用 |
|---|---|---|
| POST | `/v1/chat/completions` | 主进程（音频进、文字出） |
| GET | `/v1/models` | 模型池的可达性 Ping——它容忍 404，但 2xx 更干净 |
| GET | `/healthz` | 存活 + 模型是否已驻留 |

**内部结构**：`server.py` 一个文件。

从 messages 里按顺序抽出所有 `audio_url` data-URI 片段（主进程一次只发一个，但按 N 个防御性处理），解码进临时文件，交给模型，把文字装回 chat completion 的形状。

- 模型**惰性加载**：`torch` 与权重的 import 推迟到第一次真转写，所以健康探针不会把它拽起来；
- 加载后**常驻**（这是一台专用机器，不玩空闲退出那套）；
- 一把锁把加载和推理都串行化——单个 CPU 实例，并发请求互相踩没有意义。

语言由 `ASR_LANGUAGE` 定，逆文本规范化由 `ASR_ITN` 定，两者都能在请求里逐次覆盖。这个模型需要显式指定语言（没有文档化的自动检测），而主进程不下发语言，所以默认值是部署侧的事。

**为什么是 OpenAI 兼容 shim 而不是一个 `/asr` 端点**：这样它就是模型池眼里一个普普通通的 provider，不需要主进程写一个专用客户端。整个接入是配置里的一条 entry。

**一条部署经验：`/healthz` 不是冒烟测试。** 它在从没碰过模型的情况下也回 ok——图是惰性加载的，一个根本加载不了模型的构建照样探针全绿（`/v1/models` 同理，而那正是模型池 ping 的那个）。冒烟必须真发一次转写，然后确认健康端点里的「模型已加载」翻成了真。

## moss-asr

**定位**：另一个 `kind: asr` 后端，说**完全相同的线协议**，所以切换是配置里改一行 `base_url` 加 `model`。背后是一个转写 + 说话人分离 + 时间戳一次出的模型（50 余种语言，单次可吃很长的录音），经一个 ggml C++ 移植跑在 CPU 上。

### 为什么用 ggml 移植而不是官方 PyTorch

目标机是一台老 CPU：只有 AVX2，没有更新的矩阵指令。

这个模型的解码器是自回归的，在 CPU 上是**内存带宽瓶颈**——fp32 下每生成一个 token 要把几个 G 的权重读一遍，同级硬件上实测实时率大约 1.0（40 分钟录音跑 40 分钟）。移植在量化下快 2–3 倍，权重从 3.4 GB 降到约 0.6 GB。

敢用一个第三方移植的理由是它的**正确性论证**：逐组件对着参考模型 dump 的张量做数值门禁，端到端在较高精度档上逐字节相同。第三方移植通常栽在精度上，这个问题已经先被回答了。

### 内部结构

同样是一个 `server.py`，但形态和 `fun-asr` 完全不同：

- 移植方目前只有 CLI，所以 shim **按请求 fork 子进程**。代价可接受：ggml 用 mmap，启动时预热把权重拉进 page cache 之后，每次「加载」只是页表走一遍。
- 主进程送的是 FLAC，CLI 只吃 WAV，所以每次请求都用 ffmpeg 转一道 16 kHz 单声道。**这不是可选优化**，漏掉就是第一个请求直接失败。
- 若干量化档一起烤进镜像、**运行期选**。于是换档是一个环境变量（或一次请求覆盖），而不是一次重新构建加一次几百兆的下载。
- 子进程有墙钟上限，且**刻意设得比每个调用者自己的期限都长**：谁提的问，谁先放弃——调用者的超时是「人愿意等多久」的策略，这个上限只负责别让一个卡死的子进程永久占住一个 worker。

它还额外实现了标准的 OpenAI 转写端点（multipart 上传），今天没人用——留在那儿是为了将来主进程侧换个 provider 时，不需要 sidecar 再改一版。

### 输出形态是这里最要紧的一节

模型的原始输出带时间戳和说话人标签。

**默认返回干净文字，时间戳丢掉。** 这个字符串会被直接折进消息正文；时间戳此后在每一次提示词里占预算，而下游没有任何读者会用它。

**说话人前缀只在真有两人及以上时出现**，沿用群消息加说话人前缀的同一条规则（少于两人不加）。于是单人语音条的渲染结果与 `fun-asr` **完全一致**——对绝大多数真实流量，换后端在输出上是不可见的。

**解析走 CLI 的默认原始输出，而不是它的 JSON 格式。** 方括号格式是**模型自己的**输出契约（上游模型卡与移植方文档写法一致），JSON schema 是移植方的、可能变。

解析有三层降级：完整分段 → 无说话人标签 → 剥掉所有标记只留字。**格式出意外会退化成纯文字，不会退化成空转写**——这是选择降级方向时唯一要紧的事。要原始串和分段结构，请求里带 `verbose_json` 即可，响应会多带原始输出、逐段的起止/说话人/文本，以及说话人清单。

### 两个结构性发现，比任何单点数字重要

**① 有一个约 15 秒的固定地板。**
一秒的音频也要十几秒——编码器按 30 秒窗口对齐，短片付的是整窗的钱。所以它的实时率**随音频变长而变好**，和直觉相反。线程数在物理核处见顶，超线程对自回归解码基本白给。最激进的量化加满线程也压不到地板以下，这一条是结构性的。

**② 另一个后端在长音频上不是慢，是坏。**
几分钟的录音会返回退化重复的垃圾串——看起来像转写，其实是垃圾。今天靠进站的超时挡住了，但一旦为长音频放宽超时，这段垃圾就会被折进消息正文。这不是快慢问题。

**于是两个后端是互补而不是替代：**

| 场景 | 用谁 | 为什么 |
|---|---|---|
| 短语音条（进站、同步、有人在等） | `fun-asr` | 几秒 vs 十几秒；15 秒地板在这里最痛 |
| 长录音（按需工具、没人看着） | MOSS | 另一个后端输出垃圾；MOSS 还额外给说话人分离 |

这正好落在已有的 push/pull 分工上——**音频即消息就 push，音频是素材就 pull**。

**路由用现成机制**：给 MOSS 的条目打 longform 标签、`fun-asr` 保持更高优先级；进站照常按 kind 取到 `fun-asr`，`audio` 工具按标签取到 MOSS。不需要新机制。

短片自动提线程是同一个逻辑的延伸，而且**刻意和「公平」反着来**：短片的成本被固定编码器窗口主导，而且是同步付的（有人在等）；长录音按需跑、没人看着，就对这台机上的邻居客气点。

## pp-ocrv6

**定位**：`kind: ocr` 的后端——检测 + 识别两个 ONNX 模型加一层 FastAPI。只用 onnxruntime、纯 CPU、轻量，与视觉模型那台机器完全独立。这正是它存在的意义：**视觉模型下线时，OCR 还活着**。

**契约**：`POST /ocr` multipart 收 `image`，可选 `lang`（为兼容而接受）、`bbox`（服务端裁剪）、`enhance`。返回逐行的框 + 文本 + 置信度，外加一份合并好的全文。

`enhance=gray` 是深色屏处理：深色背景上的彩字（医疗、超声一类屏幕）先去色再检测识别。主进程在强制 OCR 的那几轮里传它——这是一个**契约参数**，不是服务端的猜测。

主进程侧的 provider 把一次 Chat 调用映射成若干次 `/ocr`：一条消息带一张图、各自带自己的参数，返回一个聚合信封。**失败是逐图收集式的**——某张图的错误只填进那张图的字段，不打断整批。

**并发与背压**：OCR 是阻塞的 CPU 活，所以请求在 worker 线程里跑，引擎实例数（`OCR_ENGINE_POOL`）就是并发上限，每次调用借一个。

这**不是吞吐旋钮**——onnxruntime 本来就把单个请求摊到各核上，两个 worker 几乎不会让吞吐翻倍。它的作用是两条：让第二个调用者不必整整等完第一个；让健康端点在 OCR 期间仍然答得动。实例是惰性建的，所以从来只见一个请求的容器也只建一个。

等不到空闲引擎超过 `OCR_QUEUE_TIMEOUT` 就回 **503**。503 的语义是**忙，不是坏**：主进程把它归类成暂时性后端错误，排队退避重试，而不是宣布 OCR 已死。这个超时必须明显长于一次正常 OCR（普通排队要能成功），又必须有界（卡死的引擎要表现成「忙」，而不是把调用者永久停在那儿——每个等待者钉住一个共享线程池 worker）。

**模型文件**：检测/识别 ONNX 与识别字符表在构建期下载，三个路径全部可由环境变量覆盖；已存在的文件保留（脚本幂等），所以想钉自己的权重就提前放进去。

健康端点带一个「用的是不是新版模型」的标志——**部署后必须看它**：为假说明模型文件没找到，服务静默退回了内置的旧版模型。一切照常工作，只是精度不是你以为的那个。这类静默降级正是健康端点该负责暴露的东西。

## 共同的设计理据

**重依赖挡在主进程外面。**
torch 加权重是几个 G，onnxruntime 加模型是几百兆，ggml 移植要一套 C++ 工具链。主进程是一个干净的 Go 二进制，这些一样都不该进它的镜像。做成 sidecar 之后，哪台机器合适就摆到哪台——有算力的、CPU 空闲的、和主进程完全不同的一台——主进程零改动。

**同一条线协议 = 换后端零代码。**
三个 sidecar 都是把自己伪装成模型池**已经会说**的协议，而不是发明一个新端点让主进程去适配。代价是 shim 里要做一层格式转换（音频转码、结果重装信封），收益是接入与替换都只是配置：加一条 entry、改一个 `base_url`。两个 ASR 后端能同时在线、按标签分流，就是这个选择直接换来的。

**繁忙与损坏必须分开报。**
503 表示忙、可重试；5xx 表示坏。这条在两端都要守：sidecar 得在队列满时回 503，而不是干等或回 500；主进程得把 503 归类成暂时性错误去排队重试，而不是记进条目健康把后端冷却掉。搞混的后果是不对称的——把「忙」当「坏」会让一个健康后端被自己的负载打下线。

**健康端点不是冒烟测试。**
惰性加载的服务在从没碰过模型时也能全绿。健康端点该回答的是「进程和它的依赖在不在、配置解析成了什么」——比如 OCR 那个模型版本标志、检索侧那个维度自检；冒烟必须真跑一次业务调用。

**「不做」也是结论，写下来。**
这几个 sidecar 里有若干个明确决定不做的事：不在 shim 里做繁简转换、不写切片拼接引擎、不给视频音轨做 announce。它们都不是遗漏，是权衡后的选择——把理由写在代码注释和文档里，下一个人才不会把同一个「优化」再提一遍。
