# agora — 多成员组织

把「公司 / 角色 / 成员」这张组织图变成可路由、可授权、可投递的运行时：一条消息进来，先问它落在**谁**的收件箱，再由那个身份去跑这一回合。

---

模块声明 `Optional() = true`：没建过组织的部署根本不装它，agora 流程的 `Accepts` 永不命中，全系统按普通对话跑——这是真正的 fail-open。

值得单独点明的是**不存在**的那些边。agora 不 import 任何别的 leaf；它的实体类型也不进 `contract`。跨出模块边界的只有 id、薄值、以及**预渲染好的提示词字符串**——提示词层因此永远不需要认识 agora 这个概念。

## 功能

**组织模型。** 四类实体：

- **成员**是跨公司持久的身份，活得比公司、任职、收件箱都长；
- **公司**持有自己那份角色授权矩阵和运作手册，两者都是它的独立快照；
- **任职**把成员绑到一对 (公司, 角色)，一个成员可以同时持有多份；
- **收件箱**是路由汇聚点，分 `member` 与 `bridge` 两种。

**chat-scoped 身份。** 身份不存在会话里，而是**每回合现算**：来路（chat scope）当 key，去路（能联系到谁）现算，历史归属按每条消息盖章。会话表永不追加 agora 列，也没有 per-session 的 agora 侧表。

**收件箱路由。** 外部聊天通过接线记录绑到收件箱。一个 scope 绑一个收件箱是 1:1；绑多个成员收件箱就是「虚拟组扇出」，靠 `^成员名` 前缀或群的默认成员挑人，再路由到成员子 scope。

**授权供给。** agora 把 (公司, 角色) 的授权折叠成一个 `GrantSet` 交出去，**自己不裁决**——裁决权归 warrant 这一个判官（[warrant.md](warrant.md)）。多公司成员取交集，per-收件箱的可见性黑名单再往下收窄。

**投递与鉴权同源。** 「我能发给谁」和「我通讯录里有谁」是同一份计算的两个出口：能发 ⟺ 在通讯录里。没有管理员 allow-all 后门。

**bridge 对人线。** 每家公司有一个 bridge 收件箱，是它的「对真人」总线：内部消息经 bridge 外发给操作者，人类消息经 bridge 转投到下游成员收件箱。bridge 自己从不跑模型回合。

**岗位经验积累。** 降级回合的轨迹快照按 (公司, 角色) 落盘，交给经验优化器蒸馏，下次同角色的回合自动把结论注入提示词。

**管理面。** `/agora` 命令族加 webui 组织图：开公司、招人、改角色、接线、暂停、编辑权限矩阵与可见性。

## 内部结构

### 组织镜像 OrgCache

`20-orgcache.go` 的 `agora.OrgCache` 是整张 pg 组织图的**唯一内存镜像**。所有热路径——身份解析、发送鉴权、工具投影——只读 RAM，不碰数据库。

读走 `RWMutex.RLock` 加一次 map 查找。写有两条路：

- **写穿透**（改授权 yaml、改可见性）：先写库、再更新缓存，按公司加锁串行化。顺序是硬的——库写失败绝不能让镜像跑偏。
- **全量重载**（管理员触发）：先把四张表读成新 map，再在一次 `mu.Lock()` 里整体换掉。读者要么看见旧的全集，要么看见新的全集，不会读到半截状态。

另有一组「缓存侧 upsert」：操作层刚写完一行就把它塞进镜像，这样新建的公司/成员/收件箱立刻可用，不必等下一次全量重载。

`Snapshot` 返回深拷贝并按 id 排序。深拷贝是为了让调用方改返回值不会污染缓存；排序是为了让 webui 的组织图节点不会因为 map 遍历顺序随机而每次轮询乱跳（节点位置按切片下标算）。

一条贯穿始终的不变式：**已知公司的角色配置永远非 nil**。空的或解析失败的授权 yaml 会落成一个非 nil 的空条目，而不是缺项——否则一次查找落空就可能被读成「没有限制」，那是跨租户可见性泄漏。解析失败时缓存写空条目**并且**把错误返回给调用方，两件事都做。

### 角色授权矩阵

`10-roles.go` 定义每家公司那份授权 yaml 的语法与解析。磁盘形态是管理员一眼能扫的矩阵：顶层 `roles:` 列出角色名，`grants:` 是「能力 → 角色 → on/off」的二维表。反序列化时把它摊平成每个角色一串授权字符串。

授权字符串是**严格三段** `kind:verb:name`（例如 `tool:use:read_file`），**不支持通配符**。解析全程「响」——每一项校验失败都返回错误，而不是静默降级：

- 角色名不合法（限定小写、有长度上限）；
- 同一个角色在 `roles:` 里声明两次；
- 某个 grant 单元格引用了没在 `roles:` 里声明的角色；
- 单元格的值不是 on/off 里的任何一个。

最后一条尤其重要：一个拼错的值**不会**被当成 off，而是硬报错。这是刻意针对「手写 typo 被静默当成关」那一类 bug——它的表现是权限莫名其妙少了一块，而没有任何地方会告诉你。

授权遍历按名字排序，所以同一份 yaml 每次解析出的顺序完全一致。

一个例外形状是**粗粒度角色包**：编排类工具只能通过 `arrangement:role:creator`（定义 + 投放）或 `arrangement:role:collaborator`（领取 + 交回）授予，解析时展开成底下那几个具体的工具授权；四个单独的工具授权名在 yaml 里被明确拒绝，错误信息直接指向对应的包。理由是「半个授权」是没有意义的状态——一个只能领不能交的角色会把整条任务队列卡死。

### 收件箱路由 InboxRouter

`30-inbox-router.go` 维护 chat scope → 收件箱 的索引。整张索引是一个不可变快照，用 `atomic.Pointer` 发布；查找就是一次原子读加一次 map 查，热路径上完全没有锁。重建在互斥锁下进行，最后换指针。

索引的 key 由 `contract.ScopeFor` 从接线记录的坐标（source + 聊天类型 + 聊天 id + 话题 id）算出——**和会话解析器用的是同一套 scope 语法**，两边因此不可能漂移。路由器本身对具体平台零知识。

收件箱**行**来自 OrgCache（模块唯一的镜像，这里绝不回头读库）；只有接线记录是从库里读的，因为镜像不持有它们。

解析一个 scope 有三条路径：

1. **原生路径**——scope 就是某个收件箱自己的 `Scope`。内部投递、成员之间发消息，编码的都是目标收件箱的 scope。
2. **成员子 scope**——`<群 scope>#<成员名>`，在该群的成员绑定里找名字。这条路径**故意不做退回**：找不到就是找不到，不会掉回群的默认成员。成员是被人用 `^名字` 显式点出来的；一个失效的子 scope 只可能来自「回复锚点记下之后该成员被改名或移除」，这时静默改投给别人，违背整个解析器「不做隐式兜底」的模型。让它 miss 掉、重新起一个会话、由人重新点名，才是诚实的。
3. **聊天路径**——scope → 接线记录 → 收件箱。这里有一次例外重试：邮件转发别名的私聊 scope 带 `#<别名>` 后缀，而接线记录匹配的是不带后缀的基础 scope，所以剥掉后缀重试一次（剥完不含 `#`，最多递归一层）。

三条路径最后都过同一道**可寻址闸**：收件箱在快照里、状态是 active、所属公司未被停用。把这道闸抽成一个独立函数是有意的——成员**选择**（虚拟组挑人）预先用同一条规则过滤，就绝不会挑出一个解析器随后拒绝的成员；否则每条消息都会撞进「找谁？」，而那个提问列出的名单里还包含那个挑不动的成员，形成一个没有出口的循环。

「所属公司是否停用」这一项是 fail-open 的：未知收件箱、未知公司都算作活跃。理由在下面的设计理据里。

**虚拟组扇出。** 同一个 scope 绑了多个成员收件箱时，1:1 那张表**故意留空**（它没法选），改由成员寻址决定。几个细节：

- 选人标记用 `^` 而不是 `#`。`#` 会和真实话题标签、论坛 topic 撞车（一个随手打的 `#促销` 不该被读成一个成员）；`^` 是路由专用的，不与任何平台语法冲突。
- 匹配按**前缀 + 名字边界**做，因为中文用户会把标记和正文粘在一起写（`^alice帮我查下`），整词相等永远不会命中。边界检查按字节判断（成员名限定 ASCII），所以 `^alice帮我查` 命中 `alice`，而 `^alicexyz` 不会被误判成 `alice`。多个名字都能前缀匹配时取**最长**的那个。
- `^` 出现了但匹配不上任何成员，返回的是「是扇出群但没选中人」，调用方据此列出名单反问；不是「不是扇出群」。这两种情况的处理完全不同。
- 同一个收件箱通过多条接线记录绑在同一个 scope 上（论坛群的多个话题会摊平成一个 scope）时按收件箱去重，只有默认标记做或运算——它们本来就路由到同一处。

### 每回合上下文

`Impl.TurnContext`（`40-impl.go`）是流程层唯一要调的装配入口，返回一个薄值 `contract.AgoraTurn`：

- `InboxID` / `MemberID` —— 后者比「角色」更细。同一个角色的不同成员可能持有不同的站点登录态，所以成员级的东西按它分。
- `Principal` —— 活跃且有成员的收件箱得到 `member:<成员名>`；其余一律是一个**无授权哨兵**。哨兵的意义是：hub 的管理员身份**永远不可能**漏进一个 agora 回合（没有成员的 bridge 收件箱也落在这里）。
- `Identity` —— 渲染好的身份卡：你是谁、在哪几家公司任什么角色、以及成员自带的人设。**不含任何内部 id**——对用户零价值，模型还可能把它念出来。这张卡**替换**掉默认人设，其余提示词层原封不动。
- `Directory` / `Playbook` —— 渲染好的通讯录与公司运作手册，落在与身份层不同的平台层槽位。
- `Spaces` —— 成员每家公司一个文件空间名。同一个集合同时喂给**硬闸**（流程写进允许的通道集合）和模型可见的工具提示，两者绝不会说两套话。

通讯录的计算在 `50-directory.go`，一次深拷贝快照喂完整趟计算，冻结在一致的视图上。

可达性是成员**所有**在职公司的**并集**：身兼两家的成员能联系到任一家的同事、能走任一家的 bridge、能看到两家的手册。同一个同事出现在两家公司里就产生两条通讯录条目（各带公司名），因为它们是两个不同的地址。

注意这与授权方向**相反**——授权取的是**交集**（一项能力只有在每家公司都授予时才留下）。**并集给触达，交集给权力**，这是刻意的非对称：多打一个招呼没有风险，多一项权力有。

### 授权投影

`MemberProjection` 把一个收件箱的授权折叠成一个 `GrantSet`：跨公司交集，再被该收件箱的可见性**黑名单**收窄。黑名单只会减不会加——它能藏掉一项已授予的工具或技能，永远变不出没授予的；凭证类授权不参与隐藏。黑名单为空（常见情况）时直接返回原集合，不做任何拷贝。

`RoleProjection`（`48-member-scopes.go`）是给编排层用的单 (公司, 角色) 视图，公司按 id 或名字都能匹配，未知一律返回空集。

两者都是**供给**动作，语义是「这个身份有什么」，不是「准不准」。判定动作只有一个词：`Granted`，定义在 `contract` 里，两边共用。

`DecorateToolSpecs` 往吃 `space` 参数的工具描述后面追加该成员可达的公司空间列表——模型选不了一个没给它看过的空间。这是**装饰**不是裁决：spec 先复制一份再改，共享目录不被污染；改完的结果照样要过 warrant 那一关。

### 发送解析

`45-send-resolver.go` 实现 `contract.AgoraSend`，和 `TurnContext` 共用同一份 OrgCache 与路由器——所以「能发给谁」和「通讯录里有谁」在结构上就是一个答案，不是两份需要对齐的逻辑。

`ResolveTarget` 先判断参数是不是已经长得像一个 scope，否则当成员名解析。**名字与 scope 的歧义是在创建时根治的**：实体名被限定为 ASCII 字母数字加 `-` `_`，永远不可能包含 `:` `/` `#` 这类分隔符。所以一个叫 `x:inbox:y` 的成员在建号时就被拒，而不是在发信时被误判——这是「把歧义消灭在源头」而不是「在使用点加一条排序启发式」。

跨多家公司重名的同事返回**歧义错误**并列出候选 scope，要求指名道姓，而不是按公司名顺序悄悄挑一个。

`CheckSend` 的判据只有一条：目标在不在调用者的通讯录里（同公司同事 + 本公司 bridge）。几个刻意的设计点：

- 目标 scope 解析不到任何 agora 收件箱时**拒绝**。「未知即放行」只对非 agora 的调用者成立，而那类调用早在函数开头就返回了；让一个 agora 成员从这里穿过去，等于允许它把自己写的内容发进任意一个外部聊天。
- 自发自收拒绝——会自旋。
- 目标是**没绑真人聊天的 bridge** 时拒绝。那种 bridge 会把消息静默丢掉，不能骗成员说「发出去了」。
- 允许时返回的投递 scope 是**被解析到的收件箱自己的 scope**，不是成员写的那个外部聊天 scope。这样内部事件落在收件箱会话上，不会混进操作者那条外部聊天的会话里。

`ResolveCredentialName` 把工具里的「以某个身份发」参数对上成员授权里的 `credential:use:<名字>`，用的是与工具投影完全相同的那份交集。缺参数时直接放行（走收件箱默认），欠配置时（没解析器、没收件箱、没成员）一律拒绝。

`ResolveBridge` 给「升级找人」用；调用者身兼多家、有多个 bridge 时返回歧义错误——无法确定该升级给哪一家。

### bridge 路由

`BridgeRouting` 报告一个 scope 作为 bridge 该怎么转，三样东西：绑定的外部聊天（内部消息 → 外发）、默认下游成员收件箱（人类消息 → 转投）、以及**所属公司名**。

最后这个是因为多家公司的 bridge 完全可以共用同一个操作者聊天，外发时打上公司名前缀才分得清是谁说的话。

bridge 路由是冷路径（bridge 不跑模型回合），所以接线记录现读，不预热、也不占成员回合的热路径。

### 暂停的两个层级

**公司级暂停**是纯内存开关，不持久化——重启即清空，这是有意的默认。暂停期间该公司的整条链全停：成员回合和 bridge 转发都停，每条到达的消息回弹一句通知，且**不去重**（发信人在恢复后重发即可，去重反而会让人以为消息进去了）。

**收件箱级暂停**是另一回事：一个**存在但被暂停**的成员收件箱，其 scope **仍然归 agora 管**，流程认领后回弹「该成员已暂停」。不这么做的话，一个临时暂停会让整个公司群悄悄掉回通用助手来回答——那比不回答更糟。这条只对 member 类收件箱生效：一个被暂停的 bridge 不是「成员」，按成员措辞回弹是错的，而且会短路掉 bridge 路由本身。

停用（disable）与暂停（pause）也不同：停用是持久的、可逆的总闸，新消息不再进、跨公司发信也进不来，但在途工作继续、外发照走。

### 运维操作层

`60-operations.go` 是数据变更的唯一逻辑处，斜杠命令和未来的 CLI 都只是它的薄前端。每个操作的形状固定：

> 校验 → 写库 → 缓存写穿透 →（仅当改动影响路由时）重载路由器

错误策略也是固定的：校验错返普通错误；库错原样透传，让调用方能判别；缓存与路由刷新失败只记 WARN、**不返回**——副作用已经提交了，镜像陈旧会在下一次重载自愈，把它报成失败反而会诱使调用方重试一个已经成功的写入。

几个操作值得点名：

- **开张**是幂等的一键流程：公司 + bridge + 创始成员 + 任职 + 成员收件箱 + 可选的 bridge 接线。每一步都是「先按自然键查，查不到才建」，可以安全重跑。创始人的角色取授权 yaml 里的**第一个**角色（不硬编码任何名字），并且要再过一遍**严格解析器**——防止一份手改过的 yaml 让某个角色在宽松的节点遍历里存在、在运行时却折叠成零授权，坐出一个有名无实的创始人。
- **公司的两种下线**：停用可逆；硬删不可逆，因此额外挂一道**在途探针**——会话管理器缺席时它 fail-closed 直接拒绝。宁可删不掉，也不敢从一个正在跑的回合底下把收件箱抽走。硬删还要级联清理那些因此失去全部任职的孤儿成员，并回收按公司分配的写锁条目。
- **收件箱接线**走认领令牌：管理侧签发一个令牌，到目标聊天里兑换；兑换动作同时完成「把这个聊天绑到收件箱」和「把兑换者加进准入白名单」两件事。解绑按人读得懂的 scope 寻址（而不是不透明 id），并且会删掉指向同一个 scope 的**每一条**记录——论坛群的多个话题记录本来就路由到同一处。
- **改角色 / 结束任职**都不动收件箱：授权在下一回合从新角色的矩阵重新算出来，没有任何需要回填的存量。

### 斜杠与面板

`70-slash.go` 是 `/agora` 的薄前端，纯参数解析加中文回复，零业务逻辑。它接受 `--key=value` 与位置参数两种写法。

里面有两个专门的诊断子命令，它们是排查这个模块的主力：

- 一个打印**当前聊天**解析出的 agora 身份：收件箱 → 成员 → 任职 → 交集授权 → principal。回答「这个 worker 为什么工具不对」只要看这一屏就够：没有成员就是 fail-closed 空集；身兼多职就是交集把它收窄了；两者都不是，那问题在公司那份矩阵里。
- 另一个打印**指定成员**当前实际看到的完整上下文：身份 + 通讯录 + 手册 + 授权到的工具和技能，走的是与真实回合完全相同的装配路径。回答「它为什么看不到同事 X」。

`90-panel.go` 把组织渲染成 webui 上的节点/边图（公司 / 成员 / 收件箱三条带，任职边与归属边），点节点开只读详情加操作按钮。整个面板仅管理员可见——组织数据是敏感的。

面板带两个编辑器。**权限矩阵编辑器**保存时会拿当前活的工具/技能目录清理已下线的能力，但这里有一道必要的守卫：只有目录**确实解析到了**才动手。否则「不在活目录里」只意味着目录还没起来，照那个判断清理会把所有真实授权一次抹掉。凭证类授权根本没有目录可查，因此永远保留、不参与清理。**可见性编辑器**编的是 per-收件箱的黑名单，同时把完整的目录名单列出来供挑选。

### 岗位经验学习

`80-learn.go` 是一个刻意隔离的外围文件——agora 的核心（操作、路由、斜杠、缓存）完全不知道它存在。

流程层在一个降级的成员回合之后，通过 `contract.MemberFailureSink` 只交两样东西：scope 和轨迹快照。**解析归 agora 自己做**——scope → 收件箱 → 成员 → 活跃任职 → (公司, 角色) 对。一个成员可能同时持有多个角色，快照就在**每个**角色下都存一份，由后续的按角色蒸馏去筛哪一条与它相关。

存储是家目录下的文件环，不进数据库——于是不需要 schema 变更，也不牵扯任何数据迁移。写入是「临时文件 + 改名」的原子替换，文件名带纳秒时间戳（文件系统的修改时间在某些卷上只有秒级精度，不够用）。每个角色的未蒸馏快照有条数上限，防止一个从未被蒸馏的角色（比如根本没配蒸馏模型）把磁盘撑爆。

消费侧只有一个：蒸馏引擎读走快照并顺手删掉已消费的。目录的回收也放在这一步，因为它是唯一的消费者——这样枚举「哪些角色有待蒸馏的失败」就能是一个**纯读**操作，而 webui 面板每隔几秒就会轮询它一次。

蒸馏出的岗位经验由 `TurnContext` 读出，接在公司手册后面注入同一个提示词层，总长度有上限——身兼多职的成员，或者一份被手工改肥的经验文件，都不该把系统提示词无限撑大。

## store 子包

`leaf/agora/store` 是模块自管的 pg 持久层，只说 `contract.DB`（不 import `database/sql`——「这是 Postgres」这个事实到连接池和这个包为止），未命中统一用 `contract.ErrNoRows`。

**实体类型住在这里，不在 `contract`。** 这是边界规则的直接体现：agora 实体是模块自己的数据，`contract.Agora` 用 id、薄值和预渲染字符串对外表达，重结构体留在模块内不出门。

五张表：成员、公司、任职、收件箱、接线。几处约束值得说明：

- **公司 ↔ 收件箱是引用环**（公司指向自己的 bridge 收件箱，收件箱指向所属公司），所以那条外键在建表之后由一个幂等的后置块补加——建表时的前向声明在 pg 里会直接失败。
- **任职**上是一个部分唯一索引 `(member_id, company_id, role_name) WHERE ended_at IS NULL`：同一个三元组最多一条活跃行；离职后的旧行因为结束时间已置而离开索引，所以同一个人可以重新入职同一岗位——哪怕发生在同一秒内。用普通唯一索引就做不到这一点。
- **接线**上是 `(source_id, chat_type, chat_id, thread_id)` 的四元唯一索引，重复接线在库层就被挡住。没有 matcher JSON、没有规范化步骤——**坐标本身就是地址**：入站按这组坐标算 scope，出站直接拿它当回复目标，两个方向共用一行。
- 每家公司把自己那份完整的角色授权配置**内联在一列**里，是一份独立快照。往注册表里加一个新工具**不会**自动授予任何已有公司——它们各自的快照要由管理员显式编辑。这是有意的：新能力默认对谁都不开。

schema 是 wipe-on-bump 的，所以基础形状是一次性建全的合并版本，而不是一串增量 ALTER；未来一次破坏性变更就是加一个更高的迁移步骤。

## 设计理据

**身份现算，不落盘。** 会话表永不追加 agora 列，也没有 per-session 侧表。代价是每回合多几次内存查找；收益是「改任职 / 改权限 / 停用公司」这类操作不需要任何回填或迁移，下一回合自动正确，也不存在一份会和事实漂移的存量身份。整个模块的内存镜像设计，本质上是为了让这个「现算」便宜到可以每回合做。

**供给与裁决分离。** agora 交出 `GrantSet`，warrant 是唯一判官。诱惑当然是让 agora 顺手判掉——数据都在它手里。但一旦两处都能判，「这个调用为什么被拒」就要同时看两个地方，而两处的规则迟早会分叉。分离之后，单租户策略和组织内的按角色权限走的是**同一个判官**，语义不可能不一致。

**鉴权就是通讯录。** 发送鉴权不是另写一套规则，而是复用渲染给模型看的那份通讯录做一次成员测试。这保证了模型看到的可达集合与实际放行的集合逐字相同——它不会去尝试一个「其实发得出去但没列出来」的目标，也不会撞上一个「列出来却被拒」的目标。两种不一致都会让模型学到错误的世界模型。

**fail-closed 与 fail-open 的分界是想清楚的。** 授权侧一律 fail-closed：没有活跃任职、通讯录构建失败、身份中途失效，都投影成空集。路由侧的「公司是否停用」检查却 fail-open：缓存滞后时，投给一个可能已停用的公司，好过把所有消息都丢掉。分界线是后果的不对称——**拒绝错了会漏权，投递错了只是多送一条消息。**

**歧义要报错，不要挑一个。** 重名同事、多个 bridge，一律返回错误并列出候选。静默挑第一个在演示里更顺，但它把「发错了人」变成一个无声故障——没有任何人会发现，直到很久以后。

**没有管理员后门。** 发送判官里没有 allow-all 分支。判官内部的一个逃生口，会让此后**任何**调用方都有办法整个跳过鉴权；而且它会让审计记录说谎。

**歧义消灭在源头，不在使用点。** 成员名不能包含 scope 分隔符，是在建号时用一条正则挡下的。替代方案是在发信解析时加一条「先试 scope 再试名字」的排序启发式——那种规则读起来永远像在猜，而且每加一种新的 scope 形状就要重新想一遍。
