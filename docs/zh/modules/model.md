# model

模型池：把一条「我要一个什么样的模型」的请求，路由到一个此刻活着、带着所需标签、不太忙的后端上，并为这次调用的健康、亲和与账单留下记录。

## 在架构中的位置

**Provides**
- `contract.ModelPool` —— 路由 + 调用 + 快照。消费者：[turn](turn.md)（回合内核与侧路 LLM 调用）、[modelgate](modelgate.md)（对外 API）、[tools](tools.md)、[asr](small-modules.md#asr)、[learn](small-modules.md#learn)（后三者是软边）。
- `contract.ImageCatalog` —— 「有哪些画风可画、每种怎么写提示词」。两个互不 import 的模块要读同一份（`image_create` 工具与 modelgate 的图像端点），所以它作为一个接口下沉到两者之下。

**Needs**
- `contract.DB`（[pgpool](small-modules.md#pgpool)）—— 按小时聚合的用量表。
- `contract.SlashRegistry`（[slash](small-modules.md#slash)）—— `/model` 是池自己的运维命令。
- `contract.PanelRegistry`（[webui](webui.md)）—— 池自述一块面板，含 `models.yaml` 编辑器。

**软边**（`TryRequire`，缺席即降级）
- `contract.AdminLine`（[adminline](adminline.md)）—— 「某一类模型全灭」「等待队列满」的管理员告警；缺席则告警静默。
- `contract.ConsumptionReporter`（[accounts](accounts.md)）—— 每次调用按消费者记账；缺席则不记。
- `trunk.Housekeeper` —— 用量落库与保留期清扫；缺席则只在退出时落一次。

两条软边都用惰性 getter 解析：accounts 与 adminline 都可能在 model 之后启动，取值发生在第一次真正需要的时候。

模块本身 `Optional() == false`，但**配置坏掉不算启动失败**：`models.yaml` 缺失、为空或解析失败时，`Start` 建一个空池——每次 chat 调用都报错，而文件监视仍然活着，改好文件即热加载，无须重启。唯一会中止启动的是数据库迁移失败。

## 功能

- **多池路由**：一份 `models.yaml` 声明 N 个条目（entry），每个条目是「某个 provider 上的某个模型」。请求按 `Kind`（llm / asr / translate / ocr / image）划分候选集，再按标签硬性筛选、按偏好标签打分排序。
- **失败转移**：一次请求内逐个候选尝试，错误即排除并换下一个；候选耗尽才向上报 `ErrNoModelAvailable`。
- **被动熔断 + 按需心跳**：错误累积到阈值把条目打入冷却；只要还有条目是冷的，一个探活 goroutine 就周期性 Ping 它们，成功则「试探性」放回轮转。
- **提示词缓存亲和**：记住每个会话上次落在哪个条目上，在其他条件完全打平时把它留在原处，同时把陌生流量从别人占着的条目上引开。
- **忙碌不等于故障**：后端说「忙 / 我刚重启」时，如果这个请求已经无处可去，就在原地排队重试，而不是宣告这一类模型不可用。
- **有界等待队列**：每个 Kind 一条队列，深度是该 Kind 配置并发数的固定倍数；排满时返回一个专门的「队列满」信号，让上层说「稍后再试」而不是「后端挂了」。
- **计量两本账**：按后端聚合的运维用量（落 `bob_model_usage`，按整点小时 UPSERT 累加），与按用户归属的消费账（转交 accounts）。
- **精确称重**：能给出「服务这次请求的那个后端的分词器」测出的确切 token 数，供回合层做压缩预算的算术。

## 内部结构

### 请求与条目的词汇

进出池的两个信封都定义在 `contract` 里（`70-model-msg.go` / `72-model-pool.go`），因为它们出现在 `contract.ModelPool` 的方法签名上。

一次请求 `contract.ModelRequest` 只有六个字段，每个都对应一条明确的路由语义：

| 字段 | 作用 |
|---|---|
| `Kind` | 路由类别。请求只与**同类**条目匹配，空即 `llm`。 |
| `Requires` | 被选中的条目**必须**带的标签（全含）。空即不限。 |
| `Prefer` | 在合格者之间打平局用的标签，命中越多排越前。 |
| `Tools` | 每轮向模型广告的工具。侧路调用方（压缩、评审、打捞）留空。 |
| `PinnedEntry` | 按名字钉死一个条目。不活着就报错，且**不检查 Kind**。 |
| `AffinityKey` | 一个不透明的会话键，用于**软**缓存亲和。空即不记也不被记。 |

`Kind` 是一个闭集：`llm`（默认）、`asr`、`translate`、`ocr`、`image`。它存在的意义是把一个非聊天模型挡在通用聊天候选集之外——一个 OCR 后端和一个对话模型放在同一个候选池里，是没有任何排序规则能救的错配。

一个条目对外呈现为 `contract.ModelInfo`，其中静态部分来自配置，`State` 与 `InFlight` 由池实时更新。`State` 是五个互斥标签之一：

| 状态 | 含义 |
|---|---|
| `disabled` | 优先级低于阈值。永不路由，也不参与探测和「全灭」判定。 |
| `paused` | 管理员暂停。永不自动恢复。 |
| `cooling` | 熔断器打死，冷却尚未走完。 |
| `tentative` | 心跳 Ping 通了被试探性放回。可选，但一次真实错误立刻重新打死。 |
| `live` | 正常。 |

快照里还有三块非条目读数（心跳是否在跑、正在服务的配置 mtime、用量存储是否已接线）和一份**只报有人在等的 Kind** 的队列读数。

再往下一层是 `contract.Chatter`——**一个连接、一个后端**的最小接口，只有三个方法：`ChatStream`（流式，工具轮次走这条）、`Chat`（非流式，侧路调用方要一个干净的响应）、`Ping`（一次不花 token 的可达性探测）。所有多条目的东西——标签匹配、活性、失败转移——都在池里，`Chatter` 只负责跟一台机器说话。

`Ping` 的契约上写着一句要紧的话：**nil 错误只代表「可达」**（对方答了话，哪怕答的是非 2xx），它**不证明**这个后端能跑完成，所以池只把 Ping 成功当作试探性恢复。这不是保守，是被现实逼出来的——一个懒加载的推理 sidecar 在真正收到第一个请求之前，探针一直是绿的。

流式一侧，`StreamEvent` 携带文本增量、思考增量、工具调用增量（带 index）、用量和终止标记；`Chatter` 返回的 error 只覆盖**开流之前**的失败，通道一旦打开，传输错误就以事件的形式到达。`contract.Usage` 除了输入/输出 token，还带缓存读取与缓存创建的 token 数——池在后端**报告了缓存复用**时打一行可见性日志，其余时候闭嘴（给每个不支持提示词缓存的后端刷零命中率没有意义）。

### 条目表与原子换表

`10-multipool.go` 是主体。`MultiPool` 把整张条目表放在一个 `atomic.Pointer[poolState]` 后面：一次配置重载构造一张全新的表，一次 store 换掉。在途调用仍持有旧的 `*entryRow` 指针（Go 保证它们活着），新请求 `Load()` 到新表。

`entryRow` 是一个条目的全部状态：静态的 `contract.ModelInfo`（名字 / provider / 模型 / kind / 优先级 / 标签 / 上下文窗口 / 并发上限）、一个 `contract.Chatter`、一个并发信号量，以及一组由行内 mutex 守护的动态字段——在途计数、错误滑窗、连续失败数、冷却截止、退避指数、管理员暂停位、试探位、最近一次错误文本，还有按小时聚合的用量桶。这些动态状态**刻意不持久化**：它是进程内的运行观测，重启即清零。

行上还留着解析后的连接事实（base URL 与 key），因为有些**侧信道**要绕过 `Chatter` 直接跟同一台服务器说话——精确分词就是这么走的。它们在构造时定型、之后不可变，因此可以无锁读。

### 重载：两条路径，两种态度

`60-reload.go` 的 `ConfigReloader` 拥有重载锁、mtime 基线和换表动作，本身对 `MultiPool` 一无所知（它只通过三个回调 hook 与池对话）。

- **显式重载**（`/model reload` 或面板保存后）不继承活性：运维刚编辑过的条目应当拿到一张白纸。
- **mtime 监视重载**是异步的，且**继承活性**：一次无关的配置编辑不该把一个正在冷却的条目复活。每次 `pick` 都会顺手做一次被节流的 `stat`（每若干秒最多一次），发现变化就在后台重建。

`buildEntry` 是两条路径共用的条目构造：provider 名归一化、preset 补齐 base URL 与 key 环境变量名、按需探测后端、解析上下文窗口与并发度、钳制优先级、造出 `Chatter` 与信号量。上下文窗口的解析链是 **yaml 声明 > 实时探测 > provider 预设 > 全局默认**——声明即真相，因为某些推理服务器报告的是整机总窗口而非单个请求真正拿得到的容量；当探测值小于声明值时会打一条警告。被禁用的条目**完全跳过探测**：运维可能一次导入几百个禁用条目，每个都去敲一下门是不可接受的启动代价，而池反正永远不会路由到它们。

`servedMtime` 与监视器自己的去重基线是两个字段：前者只在换表**成功**后前进，所以它能回答运维真正在问的那个问题——「我刚才那次编辑生效了没有」。

### 选路：两个 picker，一个窗口盲规则

`30-pick.go`。

`pick` 是**服务用**的选择器：先按 `PinnedEntry` 短路（钉住的条目若被禁用 / 暂停 / 冷却，就直接报错，不偷偷换一个），否则按 Kind 过滤，再按 `Requires` 做严格全含匹配，再滤掉本次请求已试过的和不可用的，最后排序：

```
Prefer 命中数 ↓ → Priority ↓ → 在途负载 ↑ → 自己的亲和条目优先 → 他人占用数 ↑ → 名字 ↑
```

**选路是窗口盲的**：上下文容量不参与路由。理由是它不该参与——回合层用 `WindowFor` 拿到「配置上排第一的那个条目的窗口」，把提示词裁到那个尺寸；真的溢出了，后端返回的是一个可识别的 400，池把它翻译成 `ErrContextExceeded` 原路交回，回合压缩后在**同一个赢家**上重试。让路由去躲窗口，只会让每个候选轮流吃同一个 400。

`pickStatic` 是**定尺寸用**的孪生兄弟：同样的 Kind / 标签 / 回退链，但只看配置（Prefer → Priority → 名字），完全无视健康、负载和已试集合。定尺寸的决定必须在整个循环里稳定——一次冷却抖动若让预算变小，就会对健康的历史做一次**不可逆**的过度压缩。它还接受一个结构性能力过滤器（例如「这个 provider 有没有分词端点」），用于 `CountTokens`。

`WindowFor` 是这套窗口盲设计对回合层的兑现：给它一个请求，它回答「这个请求在**配置上**排第一的那个条目，嘴有多大」。它走的是 `pickStatic`，因此对健康与负载完全无感——服务时真落在哪，可能因为失败转移而不同，但那个方向由「上下文 400 → 压缩 → 重试」这张网兜住。反过来的方向没有网：一个因为瞬时冷却而变小的读数，会让回合对健康的历史做一次不可逆的过度压缩。

**标签回退**（`defaults.fallback`）把一次请求的必需标签集展开成一条有序的尝试链：`[原集, 跳一, 跳二…]`。一跳只在前一个标签集**一个可用条目都没有**时才被走到——它是优雅降级，不是偏好。规则形式是 `(当前集 − rule.Tags) ∪ rule.To`，所以无关的必需标签（比如一个语言标签）在替换中存活。链有跳数上限并做环检测。

### 缓存亲和

`31-affinity.go` 是一本进程内、带滑动 TTL 的台账：`AffinityKey`（回合盖的是它的会话 id）→ 上次服务它的条目。台账**双向**作用于排序的平局区：自己的键优先回到自己的条目（那儿的 KV cache 还热），而所有其他人的请求被推离那些被别的活跃键占着的条目（陌生人落上去可能把人家的缓存槽挤掉）。

两个方向都排在**在途负载比较之下**——「快满了」永远胜过软性粘滞。台账不持久化，因为它镜像的是后端的 KV cache，那玩意也不跨重启。**无键请求拿不到任何视角**：一个会话的侧路调用（压缩、打捞、评审）与主对话不共享 token 前缀，没有缓存可赚；更糟的是，若把请求方自己的记录算作「他人占用」，会把它的打捞调用主动推离那个它的历史刚刚被按尺寸裁过的条目。

### 并发、队列与忙碌退避

`40-chat.go` 里的 `failover` 是 `Chat` 与 `ChatStreamWatch` 共用的唯一候选迭代驱动：钉住短路、pick/排除循环、饱和外溢、饱和主集等待、全饱和最后手段、首字节超时布防、逐次错误转移、终局包装。

三种「拿槽」姿势：

- `tryAcquire` 非阻塞。满了就把该条目记进饱和名单并**外溢**到下一个同标签条目——转移给健康同伴，比在生病的那个后面排队更快也更健康。
- `acquire` 阻塞。阻塞就意味着排队，所以它先经由该 Kind 的**有界等待队列** `enterQueue`；超过容量返回 `contract.ErrModelQueueFull`（一个跨层 sentinel，因为面向用户的措辞必须说「队伍满了，稍后再试」而不是「后端不可用」），并按 Kind 闩锁地告警一次。
- `acquireAnyOf` 是全饱和最后手段：同时等所有饱和条目的信号量，谁先空谁接。

一条重要的策略在 `eligibleSaturatedForPrimary`：如果 pick 交回来的是一个**回退跳**的条目，而主标签集之所以为空**仅仅因为**它的条目都饱和（不是死了 / 暂停 / 出错），那就等主集，别悄悄降级——请求要的是那一档，排队胜过静默降档。只有主集队列也满了，才认降级并大声记录。

`withBusyRetry` 处理「忙 / 我刚重启」这一类：`isTransientBackendErr` 认的是 429 / 502 / 503 / 504，以及无状态码的连接层失败（连接被拒 / 复位 / EOF / 解析不到主机…）。sidecar 后端是**故意**设计成会重启的，所以前置代理短暂没有上游是设计的一部分，不是事故。只有**最后一个候选**才允许排队重试（还有别处可去就该去别处）；重试期间条目的并发槽被**握住不放**——重试者保住自己的位置，别人在 Kind 队列里排在他后面，这正是「后端忙」从外面看应有的样子。整个重试序列在健康账上只算**一次**错误。

「这是不是最后一个候选」这个问题本身也要算：`hasFallbackCandidate` 在每次尝试前问一遍——把当前条目也排除掉之后，pick 还能不能给出东西，或者还有没有一个可等的饱和条目。它决定两件事：停摆的流要不要在首字节超时被切断，以及一个「忙」的后端要不要被排队重试而不是被放弃。

### 流式与观察者

`45-chat-stream-watch.go` 是工具轮次的主入口。它在共享的失败转移驱动之上加三件事：

1. 一个 `StreamAccumulator` 从事件增量地拼出最终 `ChatResponse`（文本拼接 + 按 index 重建 tool_call）。
2. 一个可选的 `contract.StreamWatcher` 逐事件检查累积状态，返回非 nil 即中止本次流。
3. 池自带的结构性保护 `ToolRoundWatcher`，在调用方的观察者**之前**组合进去。

观察者的跳闸分两级，靠 sentinel 分派：

- **条目级**（畸形 tool-call 标记漏成正文）—— 换一个后端不会这样，所以记进该条目的健康账并转移。
- **对话级**（单个 tool_call 的参数 JSON 涨过阈值还不收口）—— 每个候选都会同样地涨，所以**不**记健康账，直接带着「哪个条目跳的闸」交回调用方，由回合层跑它自己的分块重试。

三个横跨流式路径的不变量：

- **首字节看门狗**：条目接了请求却迟迟不吐第一个内容事件（文本、工具增量、**或思考 token**）就切断转移。它只在**还有下一个候选**时布防——最后一个候选跑到 provider 的硬超时为止，因为慢而活着的模型胜过让整个回合失败。首字节到达即撤防，此后的停顿归硬超时管。
- **已提交流**：一旦用户**可见**的内容进了 sink，任何后续失败都不再转移——转移会把第二份回答重新灌进同一个 sink，用户看到的是拼接出来的乱码。纯工具轮次没有可见内容，所以仍然可重试。
- **只思考不回答**：后端计费了输出 token、`reasoning` 非空、可见内容 trim 后为空。这曾经与「模型真的什么都没返回」不可分辨，于是回合内核把它读成空回复、在**未改变的历史**上再转一圈，直到烧完保险丝——每一条腿都是干净的 HTTP 200。现在它让本次尝试**失败**（换一个思考关掉的同伴就答得出来），但**不**记健康账（后端明明活着，它只是配置吃亏了），同时**把 token 记账**——这是唯一一类保证有账单的失败。

### 错误分类

`15-errors.go` 是池的「这算谁的错」判决表，因为路由决策全都挂在它上面。三类：

- **提示词级**（内容 400/413/422、工具参数被截断、上下文溢出）—— 每个候选都会同样地失败，所以不计入任何条目的熔断器。上下文溢出还进一步细分成 `ErrContextExceeded`，因为它是**压缩能修好**的那一小类。
- **条目健康级**（401/403/404/405/429、5xx、真正的传输超时、首字节停摆）—— 这是这个条目自己的问题，该冷它。
- **调用方发起**（ctx 取消 / 调用方 deadline）—— 不是后端的错。这里有个细节：`http.Client` 把「调用方 deadline 到了」和「provider 自己的硬超时到了」包成同样的错误形状，所以池在**调用点**用调用方 ctx 是否还活着来区分，并给后者盖 `errHardTimeout` 章，让它穿过过滤器计入冷却——否则一个卡住的后端永远不会被熔断，每次都白烧一整个硬超时。

分类大量使用子串匹配而非 `errors.Is`，这是被迫的：各家后端把状态码和 body 包成不透明字符串，类型链里没有东西可以 `As`。作为补偿，模式表是多条、大小写不敏感的，改一句措辞不会静默关掉某条保护。

### 健康：被动熔断与按需心跳

熔断有两条独立规则：滑动窗口内失败数达阈值，**或**连续失败达阈值（后者专治低流量部署——错误间隔几分钟，永远填不满窗口）。冷却时长按连续死亡次数指数退避，有上限。

`50-heartbeat.go` 的 `HeartbeatRunner` 是**按需**的：只在有条目死着时才存在一个 goroutine，一旦某一轮发现没有死条目就自己退出。CAS 保证至多一个实例，且退出路径特意先清标志再复查，堵住「清标志与新死亡之间」的竞态窗口。Ping 成功只换来**试探性**复活：条目重新可选，但一次真实错误就立刻重新打死——一个便宜的 Ping 通了，不证明它能跑完成。

一个真实教训写在 `nextProbeAt` 上：前置代理返回 502 时 Ping 仍算「可达」（这是刻意的，否则一个 `/models` 返回 4xx 的后端会被永久搁浅），于是一个坏掉的后端在 dead→tentative→dead 之间循环，退避指数一路爬升而名义冷却一次都没真正走完，每一圈还白烧一个真实请求。现在只有**被证伪过的**那次恢复会换来沉默,而且用的是条目本来就在走的那条退避曲线——不引入第二套退避阶梯。

告警有两套**互相独立**的闩锁，按 Kind 分别持有：

- **全灭**（某个已配置的 Kind 零个可用条目）。Kind 隔离很关键：一个健康的 ocr 条目不能让「llm 全死」看起来像池还活着。
- **候选耗尽**（一次请求烧穿了某个 Kind 的全部候选且都错了）。它必须独立存在，因为熔断器数的是**调用次数**：一个很少被调用的单条目 Kind 可以在它整个历史上 100% 失败，却从没到过任何阈值——条目一直「可用」，没有 Kind 归零，什么都不告警。所以**告警与熔断解耦**了：熔断仍然管路由（数调用次数在那里是对的），但它不再是告警的闸门。

### 用量与计费

两本账，刻意不合并。

`70-usage.go` 的 `ModelUsageRecorder` 是**运维账**的落盘器：每个条目按整点小时聚合桶，由 housekeeping tick 把**已完成的小时**排入 `bob_model_usage`（`85-usagestore.go`，加法式 UPSERT，所以部分小时行也是正确的）。落库失败时桶被放回去等下次——除非这些行正在离开可落盘范围（关停，或一个被换表淘汰的批次的最后一轮），那时失败被明确接受为损失，因为静默放回只是假装它还在。内存里的桶数有上限，溢出丢最老的。

落盘节奏与保留期都交给 trunk 的 housekeeping 调度器，而不是模块自己转一个定时器：一个周期性任务把已完成的小时排出去（于是一次非正常退出最多丢掉进行中的那一个小时，正常退出时的终局 flush 连它一起带走），另一个周期性任务按保留窗口裁掉过老的行。`bob_model_usage` 是遥测——每条目每小时一行、且只增不减地累加——所以它必须有人扫。这类**持久化**维护集中在一处协调，是 trunk 的设计意图。

换表淘汰的旧行不能立刻排干：在途调用还握着它们、还在往上写用量。所以它们被**退休**到 recorder 的名单上，跨若干轮 flush 才被丢弃。

`recordChatTokens` 同时把这次调用的真实 token 报给可选的 `contract.ConsumptionReporter`——**每次调用**就报（而不是回合末），于是深埋在回合里的侧路调用不需要额外接线就被正确归属。归属用的 Kind 是**实际服务的那个条目**的 Kind。

`42-count-tokens.go` 的 `CountTokens` 是称重制的池侧一半：窗口的真相来自 `models.yaml`，token 的真相来自服务它的那个分词器，回合层只在这两个数上做算术。读数按 `(条目, 模型, 内容哈希)` 缓存,所以一个计数**永远不会跨分词器**被复用；换模型自然让旧行失效。选尺子用的是 `pickStatic` 而非 `pick`——一次活体 pick 的健康/负载排序会让尺子在兄弟条目之间抖动，把整份缓存重新键控。

### 快照与运维面

`20-snapshot.go` 是读侧聚合：一次 `state.Load()`、每个条目一把行锁、加上三个子组件各自的 `SnapshotInfo()`。条目状态标签按优先级折叠：`disabled > paused > cooling > tentative > live`。「最近错误」只对**非 live** 的条目呈现——它是解释「为什么这个条目不正常」的诊断，一个已恢复条目留着的陈旧错误不该被永远标红。

队列读数刻意不能由在途数推导：在途调用**已经握着**槽，所以「饱和」和「饱和且后面排着队」在那个字段上读起来一模一样。静止的 Kind 被省略——给每个已配置 Kind 都报一行零，只会把真正要看的那行埋掉。

`80-slash.go` 提供 `/model`（管理员）：无参列表、`pause` / `resume` / `reload`。列表里的状态不是直接印 `State` 原词，而是给冷却中的条目附上**还剩多久**——当运维不在局域网、够不到 webui 时，聊天是这个池唯一的窗口，而「cooling」不带剩余时间，恰好把他来问的那个答案（三秒后能用，还是五分钟后）扣住了。

读路径走 contract 的 `Snapshot`；写子命令对一个窄接口做类型断言，所以一个不支持运维动作的池实现降级成一句提示而不是 panic。`90-panel.go` 把同一份快照翻译成 webui 的通用字段词汇，并挂上 `models.yaml` 编辑器——保存走「校验 → 备份 → 临时文件 + rename」，校验用的是与加载路径**同一个** `Validate`，否则一份语法合法而语义损坏的配置会保存成功、然后被池静默拒绝。

## 子包 `modelcfg`

`models.yaml` 的解析与校验，仅此而已。`ModelsConfig` = 条目列表 + 一段 defaults（全局输出上限、标签回退规则）。`Validate` 要求：至少一个条目、名字非空且唯一、provider 与 model 非空、`kind` 必须是那个闭集里的值。

最后一条值得说明：一个拼错的 kind 会「加载成功」、条目显示为 live、但永远匹配不到任何请求，同时还会**压住**全灭告警（这个 kind 有一个「可用」条目）。所以整份配置被拒绝，退回空池——一个吵闹的错误远好过一个安静的黑洞。

输出上限的解析链是 `条目 → defaults → 0`。模块侧的 `entriesFromConfig` 是配置与池唯一的相遇点：它把 `ModelEntry` 翻成 `model.Entry`，顺手把标签统一小写（请求侧的标签是代码常量，本来就是小写），于是标签匹配天然大小写不敏感。

## 子包 `providers`

后端方言层。池只认 `contract.Chatter`（`ChatStream` / `Chat` / `Ping`）；哪一种实现由 provider 名决定（`20-resolve.go`）：

- **OpenAI 兼容客户端**（`00-client.go`）—— 覆盖自托管推理服务器与各家兼容网关。SSE 解析、工具调用增量、思考通道（同一个东西在野外有两种拼法，两种都解）、每条目输出上限、`extra_body` 逐字透传（唯独 `stream` 键被丢弃：客户端的响应处理是按调用路径硬接线的，让配置翻转它会直接弄坏读取端）。
- **Anthropic 原生客户端**（`30-anthropic.go`）—— 独立实现而非适配，因为线上形状实质不同：system 是顶层字段、每轮是带类型的内容块列表、tool_use 携带已解析的 JSON、SSE 是一个多事件协议。
- **OCR sidecar 客户端**（`36-rapidocr.go`）—— 把 `Chat` 映射到一个 sidecar 的 OCR 端点。一条消息一张图，跨消息可批；失败是「收集全部」式的——单图错误填进那张图的 error 字段，不中断整批。不支持流式（OCR 是请求/响应）。
- **图像生成客户端**（`38-comfyui.go`）—— 把一个**异步任务** API（提交 / 轮询 / 取件，图生图再加一次上传）藏在一次同步 `Chat` 调用背后，于是池的选路 / 健康 / 转移机制原封不动。进度通过 `contract.WithImageProgress` 挂在 ctx 上回传，而不是改 `Chatter` 的返回类型——生成是有生命周期的任务，而 `Chatter` 是一次调用，为了一家改所有人的形状是错的。

  进度事件分三个阶段，其中第一个有特殊约定：`submitted` 在后端**接受任务并给它命名的那一刻**触发——此时一个像素都还不存在。一个必须在自己崩溃后仍能找回任务的调用方（生图工具的预写日志），只能在这里、也必须在这个钩子返回**之前**把任务 id 落盘，否则它防的那次崩溃恰好能发生在这个缝里。事件同时带上**接单的条目名**——调用方从没选过它，是池选的，所以这是恢复路径唯一能钉回同一台后端去问「我那个任务呢」的办法。`progress` 阶段的当前/总数是**按阶段**而非全局的（一次生成先报采样步数、再报分块解码），所以那一对数字不能被渲染成一根单调前进的进度条。

另外几块：

- **`30-wire.go`** —— `contract.Message` 与 OpenAI 线上形状之间的翻译，只在序列化前的一瞬间存在，绝不逃出这个包。线上形状**不**挂在 contract 的信封上，正是为了让契约层与各家怪癖解耦：加一个原生后端时，它的线上类型可以住在这个文件旁边，而不必碰 contract。消息内容是 `any`，因为同一个字段要么序列化成一个普通字符串（常见情形），要么序列化成一组内容块（多模态：文本 + 图像 + 音频）。这里有一条诚实的注记：音频块用的是那些 whisper 风格 ASR shim 接受的形状，而 OpenAI 本家期待的是另一种；**音频到底能不能被听懂，取决于配置的是哪个 ASR 后端**，不是一句「OpenAI 兼容」就能兜住的保证。
- **`10-profiles.go`** —— provider 预设表：默认 base URL、放 key 的环境变量名、以及某些 API 根本不暴露的默认上下文窗口。未知名字按「自定义」处理（没有默认值，必须自己配 base_url），所以用户可以随意命名自己的端点。
- **`40-probe.go`** —— 按 provider 问后端「你的上下文窗口和并发是多少」。超时很短且吞掉所有错误：启动不能因为某台服务器碰巧没起来而失败。
- **`45-tokenize.go`** —— 分词能力表。`CanTokenize` 是键查找、`CountTokens` 走同一张表分派，两者不可能漂移（「加进一个但忘了另一个」正是这张表替换掉的失败模式）。
- **`35-toolcall-extract.go`** —— 内联工具调用打捞。某些微调模型把 `<tool_call>…</tool_call>` 当**正文**吐出来，而不是提升到结构化字段；不打捞的话这段标记会原样回答给用户。打捞不了的残留标记则被识别为畸形输出（条目级故障）。流式与非流式两条路做同样的事，因为它们必须表现一致。
- **`37-imagecaps.go`** —— 图像能力声明，按**画风**而不是按端点组织。一台渲染机不是「某个引擎」，它是一台跑着通用渲染器的 GPU；跑哪个模型完全由提交的工作流决定。把工作流挂在条目上既是虚构，又把数据反范式化了——第二台服务同一画风的机器得抄一整份声明。改成按画风键控之后，一个条目只声明「我在哪、我能画哪几种」。内置声明随二进制嵌入，外置目录允许运维调工作流或加一种这个构建从没听说过的画风，且**每次重载都重读**（改工作流和改 `models.yaml` 是同一个运维动作）。
- **`50-reqlog.go`** —— 出站请求的 JSONL 日志，供提示词缓存分析。一请求两行（req / res，共享一个配对号），文件容量封顶、超了丢最老的一半，所以 `tail -f` 仍然可用且文件永远可解析。**系统提示词被替换成一个长度标记**：它是那段近乎恒定的可缓存前缀，逐轮原样记录会淹掉真正在变的尾部。每条记录都带上**是哪个条目**发的这次请求——这个值通过给 ctx 打标签传下来，与图像进度钩子用的是同一个惯用法，于是 `Chatter` 接口不必为了可观测性多长一个参数。凭证经共享的脱敏原语过滤。初始化失败会自我禁用，绝不阻塞请求路径。

## 设计理据

**接口窄，实现可整个换掉。** 代理只依赖 `contract.ModelPool`。「池回退成单模型」这种事不需要碰 agent 侧任何代码。

**配置坏掉不是死刑。** 空池 + 活着的文件监视，胜过一个死掉的哨兵对象：运维改好文件就恢复，不必重启一个正在服务的进程。

**一个失败到底是谁的错，决定了要做什么。** 池里几乎所有分支——冷却与否、转移与否、告警与否、退避与否——都从这一个分类问题分出来。所以分类被集中在一个文件里，并且每一类都有明确的「误判会怎样」的记录。

**告警必须与熔断解耦。** 熔断数调用次数，这对路由是对的，对告警是错的：一个很少被调用的 Kind 可以每一次都失败而从不触发阈值。

**软性的东西永远排在硬性的东西之下。** 缓存亲和是一个提示，不是约束：负载均衡压过粘滞，「快满了」压过「这儿缓存热」。

**尺寸决定必须稳定，服务决定可以随机应变。** 于是有两个 picker：一个看健康和负载，一个只看配置。让压缩预算跟着一次冷却抖动走，代价是不可逆的。
