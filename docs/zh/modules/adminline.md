# adminline

管理通道：系统级的「呼叫管理员」漏斗。任何子系统遇到必须让运维知道的事——某个接入源掉线、模型池里一条条目被判死、后端持续拒绝——都从同一个入口出去。

它同时保证两件事：**告警不丢**，**告警不刷屏**。这两件事由两套互不依赖的机制分别承担。

---

## 在架构中的位置

**Provides**

| 能力 | 谁在用 |
|---|---|
| `contract.AdminLine` | [model](model.md)（池健康、条目冷却/判死）、[stoma](stoma.md)（源健康）、以及任何需要叫人的子系统 |

**Needs**

- `contract.DB` —— 见 [pgpool](small-modules.md#pgpool)。告警审计流要落库。
- `contract.Gateway` —— 见 [stoma](stoma.md)。仅用于**按名字解析出一个接入源**，人类出口靠它把告警发出去。

本模块是可选的。这不是「可有可无」的意思，而是一条对消费方的要求：**所有调用方都把 `contract.AdminLine` 当可选协作者持有**，接口值为 nil 时 `Notify` 是空动作。于是 adminline 自己起不来，只让系统失去告警能力，不连累任何别的模块。

调用方不 import 本包。它们从 trunk 取到接口引用后点对点直调；`Notify` 是可变参格式化签名，写一个调用点和写一行日志一样便宜——这是刻意的，一条昂贵的告警 API 会让人在最该喊的地方选择不喊。

## 功能

**一个不阻塞的入口。** `Notify` 渲染文本、组装告警、投进有缓冲的队列，然后返回。队列满时**不丢弃**：改在调用方自己的 goroutine 上做一次同步落库，且用一个明显更短的超时——它占用的是别人的线程，一场风暴不能把源健康检查这类调用者一起拖住。

**「不丢」这条不变量只由落库承担。** 与是否转发成功无关，也与有没有配出口无关。这个划分让后面所有的失败处理都变得简单：转发那一侧可以放心地失败。

**一条 append-only 的审计流。** 每条告警落一行：时间戳、级别（info / warn / error）、来源标签、正文，以及一个转发状态。

| 转发状态 | 含义 |
|---|---|
| 从未附着 | 落库时根本没有配出口 |
| 已转发 | 送达了附着的目标 |
| 被折叠 | 触发限流，并入了一条汇总 |
| 转发失败 | 有目标，但发送报错 |

后两态与第一态分开，是因为排障时「没配出口」和「配了出口但发不出去」是完全不同的结论。

**固定窗口限流。** 限流桶按 **(来源, 级别)** 分——同一个来源的 error 与 warn 各有各的预算，一类刷屏不会淹掉另一类。窗口内前若干条逐条转发；超出预算的不再单发，而是累加到该桶的折叠计数，同时把自己那一行标记为「被折叠」。

**折叠汇总。** 窗口翻页时发出一条合成行：某来源另有 N 条某级别告警被折叠。它以一个专属的来源标签发出——它是一次投递，不是一条被计数的告警，所以它自己**不会喂进它所汇总的那个桶**的限流预算，不然汇总行本身也会被限流。

**两种出口。** 出口由启动配置给出：

- **人类出口** —— 把告警当一条普通外发消息推到指定接入源的指定会话里。给人读，不起 agent 回合。
- **未附着** —— 只落库，不转发。

出口配错（拼不出形状、或指名了一个没启用的接入源）**不阻断启动**：记一条警告、降级为未附着，告警照常落库。

**保留期清扫。** 审计流会无限增长，所以模块在 trunk 的 housekeeper 上注册一个周期性剪枝任务，按时间戳删除超过保留期的行。这是持久化维护，因此走 housekeeper 的统一调度，而不是模块自转一个定时器。

## 内部结构

### 漏斗本体（`10-line.go`）

`Line` 实现 `contract.AdminLine`，持有存储、投递器、限流参数和队列。`Notify` 与 `Run` 的分工是本模块的骨架：`Notify` 只做「渲染 + 入队 + 满则同步落库」，`Run` 在自己的 goroutine 里排空。

`Line` 对 typed-nil 安全——消费方拿到的可能就是一个空引用，而这条通道的调用点往往正处在别的模块的错误处理路径上，那里最不需要的就是再崩一次。

时间来自数据库校准的进程时钟（见 [heartwood](../core/heartwood.md)）：多台主机写同一个库时，告警时间戳必须落在同一把标尺上，否则审计流按时间排序就没有意义。

### 单 worker 与告警流水线（`15-worker.go`）

worker goroutine 是**限流状态的唯一所有者**，所以那张 (来源, 级别) → 窗口 的表完全不需要加锁。每条告警的流水线固定：

1. **落库**（best-effort）——失败只记日志。
2. **判限流** —— 窗口数学用的是 line 自己的时钟读数，不是告警上携带的时间戳（后者是「事件发生时刻」，可能已经在队列里躺了一会儿）。
3. **投递** —— 结果回写成「已转发」或「转发失败」。

第 1 步失败**不中止**第 2、3 步：「存储挂了」本身就是这条线必须喊出来的事。代价是这一条没有审计行，后续的状态回写自然跳过。

同一文件里还有一个周期性扫描，做两件事：把「窗口已过、但一直没有下一条告警来触发翻页」的折叠计数冲出去（否则一个安静下来的桶，它最后那几条被折叠的告警永远发不出去），以及回收闲置桶，让这张表不随来源标签无限膨胀。

### 投递缝（`20-deliverer.go`）

`Deliverer` 是一个只有一个方法的**包内**接口。真正的实现写在 `contract.Source.Send` 之上，于是 **adminline 从不 import 任何接入源包**。出口规格的解析也在这里：把一个配置字符串变成「一个能发消息的对象」这件事收在一个函数里，解析失败返回错误，由模块层决定降级。

### 存储子包（`store/`）

告警行的类型、转发状态枚举、`Store` 接口与它的实现，以及自己的表迁移与按时间戳的剪枝。

这些类型**刻意不进 `contract`**。判据就是[契约层的准入规则](../core/contract.md)：`Line` 与这份实现是它们仅有的使用者，且它们不出现在任何跨模块接口的签名里。本模块对外的契约面只有 `contract.AdminLine` 这一个 `Notify` 漏斗。

## 设计理据

**为什么落库先于投递。** 转发要走网络：可能慢、可能失败、可能根本没配出口。审计行是唯一一份「这件事确实发生过」的记录，所以它必须先落。反过来，落库失败也不该吞掉告警——那恰恰是最需要有人看到的时刻。

**为什么限流是折叠而不是丢弃。** 告警风暴的信息量不随条数线性增长：一个后端连炸五十次，人需要知道的是「它在炸，五十次」，而不是收五十条一模一样的消息。折叠把「频次」这个信息保下来，同时把转发成本压成常数。被折叠的每一条仍然完整落库——审计流是全量的，被削减的只有推送。

**为什么限流状态不加锁。** 它由 worker 独占。这不是省一把锁的微优化，而是一条结构选择：把「谁能改这份状态」压到一个 goroutine，就不存在「限流计数被并发写坏」这类只在风暴中复现的 bug——而风暴正是这段代码唯一会被真正执行的时候。

**为什么关停时还要排空。** worker 收到取消后不立即退出：先把缓冲区里剩下的告警逐条落库，再把还挂在各桶上的折叠汇总冲出去。进程正在关停往往正是告警最密集的时刻，这时丢弃，最该保留的那一批恰好会消失。

**为什么坏出口不能阻断启动。** 出口是一条运维配置，写错的概率不低。如果一个拼错的出口能让整个进程起不来，「告警通道」就从可靠性设施变成了新的单点故障。降级为未附着是唯一合理的失败姿态：能力减半，系统还活着，而且降级本身被记进了日志。
