# session

session 是「这条进来的消息属于哪个会话」的唯一权威，也是「一个会话同一时刻只跑一个回合」的仲裁者。对话的连续性是 session，历史是连续性的载体——所以历史也归它。

---

## 在架构中的位置

**Provides**

| 能力 | 是什么 |
|---|---|
| `contract.SessionManager` | 会话子系统的入口：`Submit` 收一条入站事件、`RecoverPendingOnBoot` 清理上次关停留下的在飞记录、`RunningAtScope` 报某个 scope 上正在跑几个回合 |
| `contract.MessageStore` | 对话历史的读写面——turn 与 session 之间**唯一**的耦合面 |
| `contract.ChatHistory` | 按聊天 scope 寻址的只读浏览视图（管理端翻某个收件箱的对话记录） |
| `contract.MessageIndexer` | 「已投递的 bot 消息 → sid」索引的写入面 |
| `contract.SessionResume` | 唤醒一个会话继续它的任务（外部事件完成后的回手） |

**Needs**：`contract.DB`（共享连接池）· `contract.Gateway`（按名字解析活的 source，做回合前后的 I/O：表情回执、瞬时通知、回复寻址）· `contract.PanelRegistry` · `contract.SlashRegistry`

**软边**（`TryRequire`，缺席即降级，不进依赖图）：`contract.Turn`（`/session` 的上下文量表）· `contract.TurnHandler`（真正跑回合的人）· `contract.Transcriber`（入站语音转写）· `contract.Accounts`（`/whoami` 显示绑定账号）· `contract.Agora`（虚拟组成员路由）· `trunk.Housekeeper`（周期性扫除）。

**上游**：[stoma](stoma.md) 的网关把平台事件送进 [inbound 流程](../flows.md)，流程调 `Submit`。
**下游**：[turn](turn.md) 通过 `MessageStore` 读写历史；[flow-router](../flows.md) 提供 `TurnHandler` 这条反向软边；[agora](agora.md)、[arrangement](arrangement.md) 通过 `SessionManager` 派工；[webui](webui.md) 通过 `SessionResume` 做浏览器接管的回手。

session 与 turn 之间是一条**双向但不对称**的缝：session 硬提供 `MessageStore`（turn 硬 Need 它，拓扑排序里 session 先启动），turn 那一侧的 `TurnHandler` 是软边、懒解析——所以图无环，而「没有 turn 模块时 session 依然是 session」也成立（此时一个桩会把「本该跑一个回合」记进日志）。

---

## 功能

- **归属解析**：把一条入站事件解析成一个 scope，必要时解析成一个具体的 sid（回复续接、群里 @ 开新、内部派发指定 scope、邮件按回复线索续接）。
- **仲裁**：每个 sid 同一时刻最多一个回合在飞；忙时到达的消息进队，回合结束后按批排空。
- **提交路径**：语音转写折进消息文本、附件落位到 scope 的空间、已读回执、重复消息去重、队列封顶与丢弃。
- **忙时队列的可见层**：排队/计数/已处理/队满四种提示，以及把一条忙时到达的纯文本拉进正在跑的回合的 **nudge 快车道**。
- **消息所有权**：整个对话历史（普通消息行、带工具调用的助手行、工具结果行、压缩摘要行）由本模块持有并对外提供。
- **冷归档与复活**：长期不活动的会话序列化进归档表、从热表移走；后来的一条回复能把「归档时还活着」的会话原地复活。
- **启停纪律**：boot 时静默回收上次关停留下的在飞记录；关停时限时 drain 在飞回合。
- **命令与面板**：`/new`、`/session`、`/whoami`、`/close-session`、`/trace`、`/looping`、`/uncensored`、`/thinking`、`/prompt`，以及 webui 的会话面板。

## 内部结构

### 一条入站事件的生命线

```
网关事件
  → 解析归属               得到 scope；必要时得到一个具体的 sid
  → 语音转写               把声音折成文本，落进消息文本里
  → 附件落位               暂存文件搬进这个 scope 的空间
  → 已读回执 👀
  → 准入闸                 被阻塞 → 进队并浮现，不消耗回合
  → 忙？
      忙  → 去重 → 进队（内部事件有优先权，真实消息超封顶则丢弃 + 告知）
      闲  → 认领 sid（置 busy + 发回合令牌）
              → 写入站 WAL
              → 组装 TurnWork → TurnHandler.RunTurn
              → 排 WAL + 可能的「已处理 N 条」
              → 排空队列（下一批 / 释放 sid）
```

这条线上每一步的顺序都被某条具体的失败推着定死过：转写必须在落位清掉本地路径之前、落位必须在成员扇出之前、WAL 必须在回合真正在飞的那一刻而不是提交时写。

### 三个坐标：scope、sid、消息索引

**scope** 是路由坐标，由 `contract.ScopeFor` 这一个语法唯一生成：私聊是 `<source>:dm:<chat>`（可带 `#<thread>` 子 scope），群是 `<source>:group:<chat>`，内部派发则把目标 scope 逐字写在事件里。虚拟组还有一层成员子 scope `<group>#<member>`。语法的读写两侧（`ScopeFor` / `TargetForScope` / `SplitMemberSubScope`）都放在同一处——第二个解析器正是两侧漂移的开始。

**sid** 是会话身份。一个 scope 下可以有很多 session，但只有一个是 **active**（游标选举：`cursor_set_at` 优先，`started_at` 只是同游标行之间的 tie-break）。委派子会话不参与选举。

**消息索引**把「(scope, 平台消息 id) → sid」记下来：一条回复打到 bob 自己发过的某条消息上时，就接回那条消息所属的会话。写入侧是 `MessageIndexer`，由流程在投递完成后调用（只有流程同时握着 sink 的已发消息 id 和线路 scope）；读取侧在解析器内部。索引也是「这是不是 bob 的消息」的**权威**——命中即代表回复指向 bob，不需要 source 额外打标（有的平台并不保证把被引用消息的作者带上）。

### 归属解析：唯一入口

`resolveBase` 是纯的、只读 store 的路由规则；它是**私有**的。唯一的公开入口是 `Manager.ResolveSession`，它在纯规则外面套上成员子 scope 路由与冷复活。把基础规则私有化，就让「某个调用方绕过覆盖层拿到一个不完整答案」在结构上不可能发生。

规则本身：

- **内部派发**：`ChatID` 就是目标 scope；派发帧可以要求开新会话（force-new 只是**取代** active，从不关闭旧的——会话按设计从不被关闭）。
- **私聊**：默认续接 scope 的 active 会话。开启按回复路由的入口（邮件）则沿回复祖先链查索引，命中即续接那条会话，全不命中就是一封新信 → 开新会话。
- **群**：一个群是一个 scope、里面很多 session。回复打中 bob 的某条消息 → 接回那条会话；否则（新 @，或回复的是一条没有记录的消息）→ **@=new**，开一条新的。想续接旧话题就去**回复**它。这条规则是为了不让一个群会话无限增长 → 反复压缩 → 语义漂移。
- **读错误不是未命中**：索引查询出错时退化成「续接 active 会话」，而不是开新会话——一次数据库抖动不该把一条线程劈成两半。

`ensureLive` 是解析的最后一步：被点名的 sid 若已不在热表里，尝试从归档复活；「归档时还活着」的原地复活并保留 sid，「已结束/已清除」的则不复活，改为在该 scope 开一条新的。并发的两条回复打向同一条归档会话时用 singleflight 收敛成一次复活，避免转录被插两遍。

只读的斜杠命令走 `readScope`：同样带成员子 scope，但**不做复活**——一次窥视不该因为查了一下就把冷会话拉回来。

### 仲裁器：一个 sid 一个回合

仲裁器是纯内存的一组按 sid 索引的表，全部在一把互斥锁下。它知道**何时**该跑一个回合，`TurnHandler` 知道**怎么**跑。

| 表 | 装什么 |
|---|---|
| `busy` | 这个 sid 上有一个回合在飞 |
| `pending` | 忙期间排进来的事件 |
| `nudged` | 本回合被快车道拉走的消息 id（结账时与本批一起排掉） |
| `dropped` | 这个 sid 的队列溢出过，下一个回合要说一声 |
| `sidMeta` | scope + 忙链起始时刻 + 回合令牌 + 流程声明的模式 |
| `closing` | `/close-session` 正在处理这个 sid：放弃它的排队工作 |
| `cancels` | 取消在飞回合的拉杆 |
| `armedPrefer` | 按 (scope, 发起人) 挂起、尚未被任何回合消费的模型标签 |

这些全都是**进程内**状态：没有一条需要跨重启存活。持久的那一半只有三样——会话生命周期行、入站 WAL、回复索引。

一个回合的生命线：

1. 认领 sid（置 busy、发一个单调递增的回合令牌、记下 scope 与起始时刻）。
2. 把本批要跑的每条消息写进入站 WAL——**在它真正在飞的那一刻**写，因此首个回合和后续排空回合被一致覆盖。
3. 组装 `TurnWork`：回复目标、scope 的 sink 偏好、会话出生时盖的回合模式、粘性模型标签、以及三个回调（`OnMode` 让流程自报它施加的会话模式、`OnOutput` 让流程自报它真的投递了东西、`NextNudge` 是快车道的取数口）。
4. 在一个子 context 下跑回合——这个 cancel 就是 `/close-session` 的拉杆。
5. 回合返回后排掉它服务过的 WAL 行；满足条件时补一条「已处理 N 条」的确认；然后排空队列。

排空批次的挑选有讲究：带图片或属于同一媒体组的，一次只跑一条（模型每轮干净地看一张图）；纯文本则**按发送者切批**——群是一个共享的 sid，队列里混着不同的人，而流程按批次的第一个人类事件选路由，一批混两个人就会把非锚点的那个错误处理掉。

**回合令牌**是所有权凭证。任何清理路径（正常排空、panic 恢复、`/close-session`）都先比对令牌，确认自己还持有这个 sid 才动手——否则就是在偷一个新回合的位置。

**panic 恢复**不只是清 busy：它把 panic 期间排进来的消息**在进程内重新派发**（在新令牌下），而不是把它们丢给「下次重启才捞」。有界——每条消息在进程内最多重跑一次。

**回复目标**按会话的归宿算，而不是按触发事件算。这一条是承重的：一次内部唤醒（worker 的返程、cron）带的是「internal」来源和会话自己的 scope，天真地按事件寻址会把回复送回会话自己——一个无限自喂的环。所以：真实聊天事件 → 按事件回帖；内部唤醒且有 caller → 经内部桥回到 caller 的 scope；内部唤醒且会话绑定了 source → 从它自己的 scope 反解出投递目标；都解不出 → 丢弃，绝不自寻址。

**回合前后的 I/O 按批次自己的来源说话**，而不是按派发它的那个回合的来源。一批排空/重派发的消息可能是排在一个由**另一个**来源触发的回合后面的（比如一次内部桥唤醒），而那条桥的能力集和发送对人类的消息是错的——回复锚点会被丢掉、发送本身是空动，于是「已处理 N 条」的确认静默蒸发。所以每一批都按它第一个非内部事件的来源重新解析。

**并发数按需从忙表数出来**，没有单独的计数器：`RunningAtScope` 扫忙表里 scope 匹配的项。忙表本来就被在飞回合数量限住，扫描很便宜;而没有第二份状态就意味着它不可能在 panic 恢复 / 后续排空这些分叉路径上漂移。

**管理归属是一个只升不降的位**：一个管理员对这条会话说过话，会话就被标记为管理归属（幂等，已置位就不再写，所以不会放大成每个管理员回合一次写）。它只在一种情形下被读——一次**纯内部的续跑**（批次里没有任何人类事件：一次派发返程、一次定时唤醒）。这种批次里没有在场的人可供流程判断权限，于是它继承会话持久化的这一位；只要批次里有人在，就以那个人的身份为准，这一位不参与。

### 提交路径

`Submit` 立刻返回（工作跑在自己的 goroutine 上），因此网关的消费循环永不被阻塞。随后依次：

- **解析归属** → 得到 scope。
- **语音转写**（软边）在这里做，**在落位与持久化之前**，把结果折进 `ev.Text`。分两个位置：`instruction`（发送者自己的无字幕语音，它**就是**请求）替代/前置于消息文本；`material`（带字幕的片段、被回复消息里的片段、视频声轨）是别人的话，只能跟在用户自己说的话**后面**，永远不许占据请求位。
- **附件落位**：把暂存的附件搬进该 scope 的空间，**每条事件只搬一次**（在任何成员扇出之前），下游读到的都是空间相对路径。
- **已读回执**：👀 一次，覆盖后面所有的忙/阻塞/去重分支；纯粹的 UX，不进关停等待队列。
- **准入闸**：`TurnHandler.Blocked` 为真时不消耗回合，消息进队并向正在跑的回合浮现。
- **忙时分支**：内部事件享有队列优先权（绕过封顶——worker 的产物是系统回复不是刷屏，丢了就是丢工作），真实聊天消息超过封顶则丢弃并告知。同人同内容的重复消息静默跳过。
- **空闲分支**：认领 sid，同步跑第一个回合。

`/close-session` 与提交之间有一个窄窗口（close 可能落在「置 busy」和「注册 cancel」之间），提交侧用有界重试 + 短退避处理，重试用尽就明确告诉用户重发——而不是静默丢弃。

相册（媒体组）与入职态发送者这两类事件会让重复的「开新会话」**收敛到同一条**：前者因为源会为每个附件发一条事件，天真处理会开出 N 条会话跑 N 个并发回合，正好击穿「一轮一张图」的排空；后者因为一个未获批的陌生人反复 @ 会按 30 天保留期堆出一堆空会话行。二者共用同一套 singleflight + 短 TTL 复用缓存。

### 忙时队列与 nudge 快车道

队列的**可见层**由会话的流程声明模式决定：自动化会话（agora worker）全程静默，人类在场的会话才发提示。未知/空模式也按静默处理——宁可少说，不可对着自动化流程喊话。

**去重是一道「同一个人手抖」的闸**，不是内容相等就丢。群里两个人同时打「继续」是两份不同的输入，丢掉一份就是丢掉第二个人的回合和他那一行。带附件的事件更严：只有**真正的重投**（同一个消息 id）才算重复——一个带同一句字幕的相册，它的兄弟事件在非图片路径上还可能共用一个静态回退文件名，光比内容会把一个确实不同的文件吞掉。没有字幕的附件永不去重,每一个都是它自己的一件活。

**相册降噪**是同一个问题的另一半：一个十张图的相册会发十条事件，天真处理就是九条「已排队」提示。所以只有相册的**第一条排队兄弟**出声，共享同一个媒体组 id 的后来者保持安静（👀 仍然每条都有）。排空侧对应的那一半是「单事件排空不发已处理确认」——一个 N 张图的相册一轮一张地排,逐条确认就是刷屏。

**入职态发送者全程不出声**：他们的会话跑的是「一句固定回复然后沉默」的流程，在那之上再叠一层排队提示是误导性的噪音——那句回复本身就是他们该得到的反馈。同理，他们连 👀 都不给：一个后面没有回合的「已读」信号说的不是实话。

**nudge 快车道**把一条忙时到达的纯文本消息拉进正在跑的回合。规则很窄：只有纯文本（图片/语音要预处理，留给排空路径）、非内部事件（系统回复不该冒充用户）、且必须是回合**开始之后**才到的（回合开始时就已在队列里的积压由排空按序处理，快车道不做插队）。每个回合最多拉一条。

关键在于消费侧：turn 会把拉来的消息**持久化成一条真实的用户行**，再折进本轮的回放——所以无论模型理不理它，这条消息都留在历史里。此前它是被塞进系统提示的一个瞬时层，模型不理会它就等于把这条消息销毁（队列里已被取走、没有 WAL 行、历史里没有痕迹）。

### 唤醒：SessionResume

外部事件完成后（浏览器接管的回手是当前唯一的用例）需要把一个会话叫醒继续干活。策略由 session 施加，而不是由调用方决定：**只有自动化会话会被叫醒**——它没有人类在场可以重新触发它；有人在的会话就留给用户的下一条消息，这里是空动。

叫醒的方式不是一个专门的 resume 钩子，而是解析出 sid 的 scope、发一条内部事件——它作为一次真实的入站被处理（scope → sid → 一个全新的回合），于是那条附言以普通回合输入的身份进来，不需要任何额外机制。

有两处是被真实故障逼出来的:唤醒前会确认这个 sid **仍然是该 scope 的 active 会话**——成员 scope 是共享的（一个 active），如果在等待窗口里有人 force-new 开了一条新的，那么现在叫醒这个 scope 会把回手落进错误的会话里,不如丢弃并留下日志;以及内部桥忙时的有界重试——自动化 worker 没有人可以替它重来一次,一次被丢掉的唤醒会让它永远卡住。

### 冷归档与复活

归档器完全活在 session 模块内部——生命周期行和转录都是本模块的子包、同一个数据库，所以归档是一次单模块操作，没有跨模块缝。

- **归档**：最后活动早于阈值的会话（不论死活）被序列化成一行归档记录，然后删热消息、再删会话行。**这个顺序就是幂等性保证**：归档行是 `ON CONFLICT DO NOTHING`，且只由复活/清除移除，所以任何一步崩溃后重跑都安全。归档的是**回放窗口**（从最后一个摘要标记起，否则最后 N 行），不是全部原始历史——一个回合本来也只回放这个窗口，所以还原保真度等于回放保真度。
- **跳过在飞**：归档扫描会问仲裁器这个 sid 此刻是否忙/正在关闭，是就跳过——否则会把一个正在用的会话连行带转录删掉。
- **复活**：只有「归档时还活着」的才复活。重建生命周期行、重灌转录、删归档行三步在**一个事务**里——非原子的顺序可能留下一个「活着但空」的会话，把还在的归档遮住，静默丢掉整段转录。
- **清除**：超过硬 TTL 的归档行连同它们的回复索引行一起硬删。索引的保留窗口刻意比归档更长（必须覆盖「归档年龄 + 硬 TTL」），否则索引先被剪掉，复活就成了死路——回复找不到索引，直接开一条空会话。

### 保留与扫除

五项周期任务挂在 trunk 的 housekeeping 调度器上（软边——最小配置里没有调度器也能跑，只是不扫）：

| 扫除 | 收的是什么 |
|---|---|
| 陈旧在飞记录 | 超过一天的入站 WAL 行——正常的行在一个回合内就被排掉，活过一天的是 boot 清理漏掉的崩溃残渣 |
| 回复索引剪枝 | 超出保留窗口的索引行（每投递一条 bot 消息就是一行，不扫就无界增长） |
| 冷会话归档 | 长期不活动的会话搬进归档表 |
| 已压缩行剪枝 | 最后一个摘要标记之前、且超过保留期的消息行（归档只收**闲置**会话，这一项覆盖忙的那些） |
| 归档硬清除 | 超过硬 TTL 的归档行及其索引行 |

其中两条的窗口是**互相咬合**的：回复索引必须活得比归档更久（覆盖「冷却年龄 + 硬 TTL」），否则索引先没了，一条打向冷会话的回复就找不到复活入口——它会静默地开一条空会话，而这正是复活机制存在的理由。这类跨扫除的时间约束不写下来就会在下一次调参时被打破。

### 启停

boot 恢复是**静默**的：清掉上次关停留下的在飞 WAL 行，不向任何人推「我重启了，请重发」。关停则等所有由提交/排空派生的 goroutine 结束，有截止时间；超时会把还忙着的会话数写进日志（配一句「多半是某个工具卡在不可取消的 I/O 上」的提示）。还在排队的消息会被明确警告为丢失——排队消息从不写 WAL，进程一走就没了，发送者重发即可。

### 命令与面板

九条斜杠命令注册进共享的 [slash](small-modules.md#slash) 注册表（表在注册表里，逻辑在这里）。值得单说的：

- `/session` 是一块**配电盘**：解析出的 scope、active sid、会**将要**处理它的流程与模式（只读探针，不跑回合、不落库）、回合模式的**出生盖章 vs scope 默认**（两者不同就说明 `/looping` 是在这条会话出生之后翻的，还没生效）、sink 偏好、以及从 turn 借来的上下文量表。
- `/looping` 翻的是 scope 的**默认**回合模式。这个默认在会话创建时被盖到会话上并终身不变——所以翻它只影响未来的会话，没有任何会话会在对话中途换驱动。
- `/uncensored`、`/thinking` 各切换一个软模型标签，按 (scope, 发起人) 双键挂起：一个 scope 是共享的，单槽会让一个人的切换悄悄顶掉另一个人的；而且只有发起人自己的回合能消费它。消费发生在回合启动时、与会话已有的标签**合并**（而不是替换），并且合并前会在锁下重读一次——这样两次相邻的切换不会互相丢失，针对一条已被取代的会话算出来的集合也不会被盖到这条上。
- `/close-session` 按 scope 扫忙表找到目标回合并取消它；它同时清掉该 scope 下**所有人**的挂起标签——close 是给整段对话画的界，把谁的偏好留过界都不对。回执里回显被停的 sid：一个 scope 可能同时有两个忙 sid（active 会话 + 一条回复旧消息的回合）。

面板给出忙/排队/丢弃/被跟踪四个计数，加上**持久队列深度**（与内存队列是两个不同的问题，谁都不蕴含谁），以及一张「此刻正在跑」的表（scope / 已跑时长 / 起始时刻）。最长忙时长量的是忙**链**的年龄而不是当前回合的——一个 10 张图的相册一轮一张地排空，读出几十分钟是正常的；它抓的是「这个 sid 一直没有空出来」。

### 子包 `messages/`

对话历史的存储。行的形态：普通 user/assistant 行、带工具调用的助手行（`tool_calls`）、工具结果行（`tool_call_id` + `tool_name`）、压缩摘要行（`row_kind=summary`）。三处 JSONB 而非侧表或列：作者归属（形状随行类型而变，且永远随行整读）、用户行的结构化附件清单（只存元数据与空间路径，不存字节）、工具调用参数。

两条被写进接口的语义承诺：

- `GetReplay` **锚定在最后一个摘要标记**（压缩的起点），而不是固定行数——摘要因此永远在窗口里，最近的尾巴永远完整。还没有摘要时退化成最后 N 行。
- `AppendCompactionBatch` 是**原子批**：一行摘要标记 + 按形状重新追加的最近尾巴，一起提交或一起回滚，回放永远看不到写了一半的压缩。

`AppendUserMsgs` 同样是原子的：一批里每个说话人一行，中途失败整批回滚，重试不会重复已提交的行。

原地压缩不重写任何东西——摘要标记和尾巴是**追加**的，标记之前的旧行留在表里。它们对回放已死（回放锚定最后一个标记），但对一条长期存活、反复压缩的会话是无界增长。`PruneCompacted` 是对应的扫除：删掉「在最后一个标记之前**且**超过保留期」的行。

### 子包 `store/`

会话生命周期、崩溃安全的入站队列、回复路由索引、scope 偏好。三张表都在共享连接池上。

- **生命周期**：会话行是纯生命周期的（创建/游标/结束/标题/模型标签/管理归属/模式/回合模式盖章）。「谁是 active」由游标选举回答。
- **入站 WAL**：只记**在飞**的消息。排队的、被阻塞的、被丢弃的、撞上关闭的都不写——写/消费必须对称：`removeServedPending` 只能按 (scope, 消息 id) 结账，一条没有 id 的行永远无法被消费，只会躺到扫除为止。内部事件也不写：它们本身就是尽力而为的进程内投递。
- **冷会话候选**：用一个按会话的横向 `ORDER BY id DESC LIMIT 1` 取最后活动时间（时间戳与自增 id 同向），成本由较小的会话表驱动，而不是由整张消息表驱动；每次扫描有条数上限，让首次运行的大积压分多次排干。

## 设计理据

### 归属只有一个入口

基础路由规则是私有的，公开面只有 `ResolveSession` 一个。这不是风格问题：一旦有第二个入口，某个调用方就会拿到一个「没经过成员路由 / 没做冷复活」的答案，而这种错误的表现形式是**附件落到了另一个 scope**、或者一次回复静默开了新会话——两者都很难从现象倒推回原因。把覆盖层焊死在唯一入口上，这类 bug 在结构上就不存在。

只读的窥视命令走同一套原语的**不复活**变体，共享同样的成员子 scope 计算——两条路径共享原语，因此不会漂移。

### 一个群是一个 scope，里面很多 session，只有一个 active

反面是「一个群一条永久会话」：它会一直长，一直压缩，最后语义漂移到无法收拾。**@=new + 回复续接**把话题边界交还给用户：想开新话题就 @ 一下，想接着聊就回复那条消息。代价是要有一个可靠的「这是不是 bob 的消息」判定——由消息索引承担，而不是由平台的回复标记承担（后者在某些平台上并不可靠，而误判的后果是把一条有上下文的对话劈成一条没有上下文的新会话）。

### 消息所有权归 session

历史曾经属于 turn，因为是 turn 在读它写它。但 turn 是短命的「读尾巴 + 追加」执行器，而**对话的连续性**是 session 的定义——历史是连续性的载体，所以历史归 session。落到工程上：turn 只通过 `MessageStore` 这一个接口触碰历史，永远不自建 store；一个新的 session 实现可以自由更换存储方式（schema / 索引 / 后端），但不能单方面改共享数据形状与回放/压缩语义——那两条是接口的一部分，不是从缝里漏出来的实现细节。

同一个实现同时以 `ChatHistory` 这个**另一个更窄的接口**对外提供只读浏览，而不是把方法加进 `MessageStore`——回合热路径的写接口不该因为一个管理端读需求而变宽。

### WAL 只记「在飞」的

崩溃恢复的边界画得很紧：只有**正在被一个回合服务**的消息才写持久行。排队的、被阻塞的、被丢弃的都不写，而是当场用一条聊天里的提示告诉用户。理由是恢复侧的对称性——boot 恢复什么都不推送（没有「我重启了请重发」），所以一条留到下次开机的行，唯一的产物是一行日志。真正需要持久化的只有「用户以为已经在处理、结果进程没了」这一类，其余一律当场说清楚。

### 队列的可见层由流程声明的模式决定

同一套排队机制，对人和对机器要有完全不同的表现。这不由 session 猜——由处理该会话的**流程自报**（`OnMode`，路由器在它唯一一次选流程时调一次），session 缓存并持久化它。自动化会话静默且不吃 nudge；人类在场的会话有提示、有快车道。

「已处理 N 条」的确认还多一道闸：只有流程**真的投递了**东西才发（`OnOutput`）。仅仅「选中了一个流程」不够——有些流程的去重空转会选中自己却什么都不产出，那句确认就成了谎话。

### 没有 turn 也是 session

`TurnHandler` 是软边、懒解析、有桩。这不是防御性编程的装饰，而是模块边界的表述：一个会话即使从没跑过任何回合，它仍然是一个会话——有归属、有历史、有生命周期。仲裁器对「怎么跑」一无所知，只知道「什么时候可以跑」。这条缝是两个核之间**唯一**的连接。
