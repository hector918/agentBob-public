# retrieval

冷记忆在主进程这一侧的模块：把每个回合的对话喂给一个独立的检索服务，并在需要时反过来向它提问。

真正的向量库、嵌入与查询实现都跑在 sidecar 里。本模块拥有的是**两条缝**——一条写、一条读——以及夹在中间那个持久化 outbox。outbox 才是这个模块的重点：它保证「不丢语料」与「不拖慢回合」这两件事可以同时成立。

**默认关闭。** 配置齐备之前 `Start` 什么都不注册。

---

## 在架构中的位置

**Provides**

| 能力 | 谁在用 |
|---|---|
| `contract.RetrievalClient` | [tools](tools.md) 里的回忆工具（读） |
| `contract.RetrievalFeed` | [流程层](../flows.md)（回合收尾时投喂，写） |

**Needs**

- `contract.DB` —— 见 [pgpool](small-modules.md#pgpool)。outbox 是一张真表。

两侧消费者都用**软边**持有能力。模块关闭时，声明过的 Provides 就是没有对应注册——于是回忆工具报告「不可用」，流程直接跳过入队，行为零变化。

检索服务本身见 [sidecars](../sidecars/)。主进程只通过 HTTP 与它对话，不共享任何进程内状态；本模块对外的读契约里，甚至不包含写方法（见下）。

## 功能

### 读

**一次回忆查询。** 查询里带查询类型（实体提及 / 时间窗 / 语义）、该类型自己的参数、一组通用过滤器，以及条数上限。

**返回未解析的原始 JSON。** 由调用它的工具决定呈现成什么样子；模块不替它塑形，也就不必随服务端返回结构的演进而改动。

**fail-open。** 返回错误只意味着服务够不着，调用方跳过这一步，**绝不因此让回合失败**。

**作用域钳制。** 查询的身份约束（公司、用户、频道）由调用方折进过滤器；检索服务那一侧对「没带公司过滤器的查询」是 fail-closed 的。这是一道双人闸：调用方负责钳，服务端负责拒。非组织场景（私人对话）用一个约定的公司哨兵值归入预置分区。

### 写

**投喂一个回合。** `EnqueueTurn` 是 fire-and-forget：把这一轮的行落进 outbox 表就返回，推送由后台完成。它不允许失败、不允许阻塞回合。

**身份由流程提供。** 公司与房间由流程盖章，模块**不自己重新推导**——只有流程知道自己那套 scope 语义。

**每条消息保留自己的说话人。** 一个群里一个回合可能有好几个人说话，所以每条用户事件带着**自己的** handle 入队，而不是笼统归给「用户」。群聊场景还会在正文前缀上说话人名字，让「谁说的」既可读、也能被字面匹配检索到。助手自己的回复挂在一个约定的机器人 handle 下——「说话的是 bob」不该被当成某个人。

**入队前的净化。** 每条内容过一遍凭证脱敏（秘密永远不进语料），并按字符数截断：粘贴的大文件、被折进回复的大段工具输出，不该淹没整个语料库。截断按 rune 边界做——半个多字节字符会让整批被服务端拒收。

**确定性去重。** 每条消息的 id 由 (会话, 事件) 推导而来，服务端按它幂等入库。因此重推一批是安全的——这正是「失败就留着下次再试」这条策略成立的前提。

**跳过没有价值的行。**

| 情形 | 为什么跳过 |
|---|---|
| 只有附件、没有文字的消息 | 一张无说明的图在语料里只是噪音，与答案配对没有意义 |
| 空内容 | 服务端的嵌入环节会拒收，而它拒的是**整批** |
| 没有触发锚点的回合 | 主动发起 / 恢复 / 内部推动产生的回复，没有用户提问与之配对；且其推导出的 id 会在同一会话内重复，被去重逻辑静默吞掉 |

### 排空

**节拍与批量。** 后台 feeder 按固定节拍取出最老的一批推给服务，成功即删除对应行，然后继续排到空为止。

**瞬时错误留着重试。** 网络故障、服务重启、5xx——行留在队列里，下个节拍再来。

**内容错误隔离。** 只有**服务自己判定的内容错误**被当作永久失败，把该批 dead-letter 掉。否则一批推不动的行会把先进先出的队头永久堵死。判定刻意收窄：各类配置形状的错误（鉴权、路径、体积）一律当瞬时，留在队列里退避，免得一个中间层的误配把不可回填的追加型语料悄悄丢光。

**上限保护。** 服务长期不可用时 outbox 会无限增长，而每行都带着完整正文。所以 housekeeper 上挂了一个封顶剪枝任务：超出行数上限时丢弃**最老的**。这是安全兜底而不是调优旋钮——宁可丢掉最旧的冷记忆，也不能把主库撑爆。

**把队列状态摆到看得见的地方。** 模块向 [webui](webui.md) 注册一块面板，显示队列深度、**队头等了多久**、以及排空当前是否在失败（失败时附上原因原文）。深度本身分不清「忙了一分钟」和「服务已经死了」：三十行不断翻新是健康，三十行的队头躺了几个星期就是事故。

## 内部结构

### 模块外壳（`00-module.go`）

配置判定、迁移、注册两个能力、拉起 feeder goroutine、挂上剪枝任务与面板。

feeder 的日志在首次失败后会自觉降噪——一个死掉的服务不该每个节拍刷一条 WARN。代价是「此刻到底通不通」这个状态在日志里会很快变旧，所以它被单独存了一份**给面板读**。日志与面板在这里有意分工：日志记的是**变化**（掉下去、恢复），面板答的是**现状**。

### HTTP 客户端（`10-client.go`）

对检索服务的读写两个端点。`Retrieve` 实现 `contract.RetrievalClient`；`Ingest` 是写侧，**刻意留在包内的具体类型上**而不是进 `contract`——包外没有任何模块应该能直接往语料库里写，把方法留在包内类型上是让这条规则由编译器执行，而不是靠约定。

这里也是「哪些 HTTP 状态算永久失败」的唯一判定点。读响应刻意**不做体积截断**：一次回忆的返回可以很大，截断会把一份格式坏掉的 JSON 递给工具。

### 配置（`15-config.go`）

自己的配置片段：开关、服务地址、可选的调用密钥、超时、节拍、批大小。批大小按服务端的上限硬夹。

`Configured()` 是「这个特性是不是活的」的**单一谓词**——模块启动、feeder、回忆工具、流程入队，全都挂在它所决定的那两次注册上。一个开关，一处判定，没有第二份真相。

### Outbox（`30-outbox.go`）

表结构与迁移，加队列的四个动作：

- **整轮一次多行插入** —— 一个回合要么整体入队要么整体不入（不会出现半个回合的语料），且只有一次往返。
- **取最老的一批** —— 只读不删；删除发生在推送成功之后。
- **按 id 删除**。
- **封顶剪枝**。

外加一次读出「深度 + 队头年龄」的统计查询给面板。**先进先出的顺序完全由自增主键决定**，不依赖任何时间戳——行上的时间戳只用于诊断。

### 投喂与排空（`40-feed.go`）

`contract.RetrievalFeed` 的实现，把一个回合摊成行的构造逻辑（身份、说话人前缀、脱敏、截断、id 推导、跳过规则都在这里），以及 `drain` 这一趟的完整策略。

入队用的是一个**不随回合取消而取消**的上下文：会话被关闭、或进程收到关停信号时，回合上下文会被取消，但这份 best-effort 的语料写入仍应落地。

### 面板（`90-panel.go`）

三个读数的渲染，包括「队头多老才算卡住」的阈值。队列读不出来时显示的是「?」而不是 0——一个读不到的队列绝不能渲染成一个空队列。面板标记为仅管理员可见：服务地址与失败原文属于部署细节。

## 设计理据

**为什么中间要垫一个 outbox。** 直接在回合收尾时同步推给检索服务，等于把「语料入库」的可用性焊死在「用户能不能及时收到回复」上：服务慢一秒，每个回合就多一秒。落一行本地表是毫秒级的事，推送的时序、重试、批量与失败处理全部下沉到后台。代价是一张表和一个 goroutine，换来回合路径上零风险。

**为什么读 fail-open、写 fire-and-forget。** 冷记忆是**增益**，不是主干。回忆不上来，回答会差一点；回忆把回合拖挂了，回答就没有了。两侧的失败姿态都由这一个判断推出来：读失败即跳过，写失败即记一条 warn 说「这里有个语料缺口」，然后继续。

**为什么身份由流程给而不是模块自己查。** 「这条消息属于哪家公司、哪个房间」是 scope 语义，而 scope 的唯一权威在会话解析那一侧。模块若自己再推导一遍，系统里就多了一份可能与权威不一致的答案。让流程盖章、模块只做搬运，是[单一权威](../architecture.md)这条原则在这里的具体形态。

**为什么毒批要 dead-letter。** 队列是先进先出的：一批永远推不动的行会把它后面所有行永久挡住，结果是「一条坏数据让整个语料库停止更新」。识别出真正的内容错误并丢掉那一批，是让队列**继续流动**的代价。这个取舍有代价——服务端对整批做拒绝，所以一条毒行会连累同批的邻居——所以丢弃会显式记一条警告，而最常见的致因（空内容）在客户端就已经被过滤掉了。

**为什么面板上要显示队头年龄。** 这是本模块唯一一个从事故里长出来的字段。一个持续不可用的服务，其日志痕迹只有重启时的那一条 WARN；行数看起来一直「有一些」，而一个只看深度的观察者读不出异常。深度加上队头年龄才构成一个可判断的信号：**队列在动还是在积**。
