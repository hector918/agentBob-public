# arrangement — 任务编排

一个固定的引擎，跑一份完全弹性的 JSON 编排：按角色排出一列优先级桶，工作项在桶之间前进、打回或停泊。

## 功能

**固定引擎 + 弹性编排。** 引擎只有三件事：投放（入口）、一个把闲着的成员叫醒来领活的定时器（派发）、以及「一个角色一个优先级桶」这条规则。可变的部分是编排的 spec——作者写的一份 JSON：有序的角色桶，每个桶带一段自由格式的内容（这一环节的要求）。引擎只读 role 和顺序，content 对它完全不透明，是给做事的人看的。

**六个动作。** `Define` 校验并落库一条冻结的编排；`Inject` 往里投工作项；`Pull` 原子认领某个 (编排, 角色) 桶顶的项；`Submit` 交回产出并决定去向；`Cancel` 取消；`Status` 给 webui 出快照。

**三种去向。** `forward` 推进到下一个桶（已是终端桶则完成）；`back` 打回上一个桶（没有上游则停泊为「无上游可退」）；`park` 带一个描述性状态离开活跃流转（例如 `blocked`）。

**跨公司定义是有意的。** 作者可以给任意一家公司定义编排——闸是那项工具授权本身，不是公司成员身份。

**冻结不可编辑。** 编排一旦开跑就冻结。要改，取消再定义一条新的。这不是省事，而是因为「改了一半的编排」对那些已经在途、按旧定义被领走的工作项没有任何合理语义。

## 内部结构

### spec：唯一的弹性面

`10-spec.go` 解析并校验编排 JSON。校验是**纯结构性**的：至少一个桶、每个桶有 role、role 之间不重复。角色**有没有人**在这里不检查——没人的角色，它的工作项会在派发时停泊为 unmet，这是运行时状态，不是定义错误。

spec 之上只暴露几个纯函数：入口角色、某角色的前 / 后一个角色、某角色的桶内容、有序角色列表。引擎需要知道的关于「这份编排是什么」的一切，就是这几个函数。

### 两张表与原子认领

`leaf/arrangement/store` 有且只有两张表：编排定义（一条编排一行，spec 开跑后冻结）和工作项（活队列，`role` 是它当前所在的桶）。

工作项的状态语义很关键：引擎**只**对 `queued`（可派发、可领取）和 `in_flight`（等待交回）动手，**其余任何状态字符串都是「停泊」**——展示，但不驱动。这就是为什么停泊状态可以自由填写：新增一种「卡住的理由」不需要动引擎一行代码。

相应地，交回时有一道**保留字闸**，拒绝把停泊状态填成引擎自己的那几个状态。它挡的是几种具体的坏结果：填成 `queued` 会形成停泊→领取的循环；填成 `in_flight` 会永久占住一个并发额度，既不会被派发也不会被租约回收；填成 `done` 会触发一次假的终端投递；填成 `cancelled` 会被清理静默扫走；填成 `unmet` 会被自愈逻辑重新排队。

认领是**单行条件 UPDATE**：先按优先级（同优先级取最旧）挑出候选 id，再用一条带 `status='queued'` 条件的 UPDATE 把它翻成 `in_flight`；抢输了就试下一个候选。交回同样是条件 UPDATE，守卫是「认领人是调用者 **且** 状态仍是 `in_flight`」——非持有者提交、重复提交、以及取消之后的迟到提交，全都影响 0 行、返回明确的失败。

**这里没有事务，只有条件写。** 两个成员同时被叫醒也不会认领到同一项。

### 派发：选择器与排水器

两个 goroutine，跑在一条可取消的后台 ctx 上（`Start` 传进来的那条是临时的，不能用），`Stop` 里 cancel 加 `wg.Wait()`。

**选择器**（默认 30 秒一轮）只做选择，从不发消息。一轮里依次做四件事：

1. **回收过期租约。** `in_flight` 超过租约时长的项是候选，**但要先看持有者是不是还在跑回合**。回合没有墙钟上限，一个慢但活着的成员绝不能被回收——回收会让它已经做过的外部副作用再跑一遍。进程重启会清空「谁在跑」的记录，所以重启后的孤儿项自然变得可回收。
2. **筛出可派发的编排**：状态是开跑中、且**公司处于活跃**。公司被停用或暂停时它的桶不派发，工作项原地留在队列里，等公司回来继续——而不是被判为「无人可派」而停泊。
3. **扫桶。** 一条 `GROUP BY` 查出所有非空的 queued 桶，一轮一次数据库往返，而不是一个桶一次。对每个桶判断「这个角色能不能真的把它排空」：既要有活跃成员，又要有协作权限（领取 + 交回）。任一缺失就把整桶停泊为 unmet 并记录原因。都满足时，对每个**空闲**的成员 scope 入队一个唤醒（成员正在跑回合就跳过——这就是空闲闸）。
4. **自愈。** unmet 的桶如果角色重新有人、权限也回来了，把它的工作项翻回 queued，下一轮自然被捡起。这覆盖的是「角色临时没人 / 成员收件箱临时下线」这类瞬时缺口。

**排水器**（默认 8 秒一次）每次只弹出一个唤醒并发出去。选择器只入队、排水器才发，是为了让一轮选择不会瞬间点燃一大把并发成员回合。发之前还要复查三件事：成员是不是又忙了、桶是不是已经被同事领空了、公司是不是刚被暂停——任一条不成立就丢弃这次唤醒（选择器下轮会重新入队）。取编排定义失败时也是丢弃，而不是带着空内容硬发。

排水器**从不改工作项的状态**。标记成 `in_flight` 严格发生在成员自己领取的时候，所以那张表永远不会出现「显示被谁拿走了，其实没人管」的假象。

唤醒队列有两层防重：

- **待发集合**按 (编排, 角色, scope) 去重——不是只按 scope。只按 scope 去重会让一个桶的待发唤醒盖住同一个成员在**另一个**桶的唤醒。
- **按 scope 的冷却期**。它存在是因为「发出消息」到「那个回合登记为忙」之间有一段异步窗口，在这段窗口里成员看起来还是空闲的；没有冷却就会被叫醒两次、跑成两个并发的领取回合。入队和出队两处都查这个冷却期，因为不同桶的唤醒可以合法地共存于队列中。

唤醒消息本身要求**新开一个会话**且**不需要回复**——它是一次即发即忘的叫醒，成员在那个回合里调用领取和交回工具；没有回复目标时这个回合也必须真的跑起来，而不是像一次路由失败那样被丢掉。

### 交回与终端投递

`Submit`（`40-impl.go`）根据去向拼接工作项的**累积载荷**：每一步的产出、每一次打回的理由，都以带标注的段落追加上去。所以下游（包括一个专门做校验的角色）看到的是原始任务加上完整的过程记录，而不只是上一步的输出。

终端桶完成时，产出被投递到**所属公司的 bridge**，而不是编排的作者——因为下命令的人自己也可能是一个 agent，bridge 才是那家公司稳定的「对人」出口。

投递失败时**不关闭编排**。关掉等于悄悄宣布完成而报告已经丢了；留一条没有活跃工作项的开跑中编排在面板上，是可见的、可重试的。

编排的关闭还有第二个条件：只有当它**没有任何存活工作项**时才关。投放可以把一条编排扇成多个并发工作项，单个终端完成并不代表整条编排结束。关闭动作本身带 `status='started'` 守卫，所以一次并发的取消不会被它覆盖掉。

### 两道权限门与并发上限

角色能不能处理一个桶，判据是它同时具备领取和交回两项能力。这个检查在三处出现，且都 fail-closed（组织层不可用即视为无法验证，拒绝放行）：

- **定义时**逐桶检查。一个角色处理不了自己的桶就当场拒绝创建，而不是开一条注定卡死的编排。
- **投放时**对目标环节再检查一次（第二道门）。
- **选择器每轮运行时**再检查一次。这是对创建时那道门的补丁：定义之后被撤销的授权会让工作项变成领不出来——这正是「编排跑飞」的根因。运行时检查把这种桶停泊为 unmet，权限恢复后再自愈。

`Define` 还有一个每公司的**运行中编排上限**。计数只算「持有可运行（queued 或 in_flight）工作项」的编排，不算所有开跑中的：一条只剩停泊项的编排不消耗任何成员产能，它也永远不会自动完成；把它算进上限，最终会把新建永久卡死。计数与插入之间没有锁，两个同时发生的定义可能各让上限溢出一个——对一个低频的管理动作来说这是可接受的。

创建时还有一个「排了就开跑」的动作：定义成功后立刻在入口桶投一个工作项——环节内容本身就是指令。这一步与定义是**原子**的：投放失败就把定义回滚掉。否则会留下一条零工作项的幽灵编排，永远不跑、永远不完成、也永远不会被清理，因为清理只碰终态。

### 清理与运维面

三个清理任务挂在中央 housekeeper 上（模块不自转定时器——持久化状态的扫除归调度器统一协调）：

- 终态**工作项**按保留期删除。
- 终态**编排**（取消或完成）按保留期删除，连带它们的工作项。
- 同一趟里先关闭**僵死编排**：开跑中、没有任何可运行工作项、且长期无活动——只剩停泊项。这类编排既不会自己完成，也不会有人想起来去取消它。关闭之后它就顺着终态编排的正常保留期被清走。

`/arrangement` 斜杠命令（管理员）可运行时调整选择器节拍、排水间隔和并发上限，也能取消编排、看状态。webui 面板出两张表：编排表（每行可展开看逐环节内容）和活跃/停泊工作项表，在手最久的排最前——那个数字就是最该被看到的头条。面板上每个操作都是「预填命令、回车确认」，不是直接执行。

## 设计理据

**引擎固定，编排弹性。** 换一套业务流程应该是写一份新的 JSON，而不是改引擎。所以引擎坚持只认识「有序的角色桶」，桶里的文字一个字都不解析——一旦开始解析，那些文字就变成了引擎的输入格式，弹性也就没了。

**状态是开放集合。** 只有两个状态驱动引擎，其余全是展示用的停泊状态。新增一种「卡住的理由」因此是零代码改动，代价只是一道保留字闸，防止自由文本撞进引擎自己的词汇表。

**认领用条件写，不用事务。** 两张表、单行守卫，就足以保证一项工作只被一个人拿到、只被结算一次。这与项目里「窄并发点上，带条件的单行 UPDATE 优于事务」的一贯取舍同源：它更容易读懂，也更难写错。

**至少一次，不是恰好一次。** 租约回收以「持有者是否在跑」为闸，已经把最常见的误回收挡掉了；但一个做完外部副作用、还没交回就崩掉的成员，它的工作项确实会被重跑。这是明确接受的语义——成员侧的工作应当幂等。

**选择与发送分开。** 选择器决定「谁该被叫」，排水器决定「什么时候叫」。合在一起写更短，但一轮选择就会同时点燃一批成员回合；拆开之后限速只有一个旋钮，而且这个旋钮不影响选择逻辑本身。

**停用要真的停住。** 公司停用/暂停的闸在派发、排水、领取三处都复查了一遍。只在派发处查会让它变成「劝告性」的——一次在暂停前入队的唤醒仍然能让成员领活、做事、交回。
