# stoma

多平台聊天网关——bob 与外界交换消息的气孔。它拥有每个消息源的生命周期，把 N 条平台入站流扇入成一条，并按名字把回复交还给对应平台。

## 在架构中的位置

| | |
|---|---|
| **Provides** | `contract.Gateway` |
| **Needs** | `contract.PanelRegistry` |

上游只有配置：`sources.Assemble` 在进程装配期构造出这一批 `contract.Source`，交给 `stoma.New`。下游是 [flows.md](../flows.md) 里的 inbound 流程——它 `Require` 到 `contract.Gateway`，`for range gw.Events()` 消费入站事件，再用 `gw.SourceByName` 取回源来渲染回复。

网关**刻意不认识** session、不认识筛查。谁能说话是 [gate.md](gate.md) 的事，一条消息归哪个会话是 [session.md](session.md) 的事，两者都在流程层、在网关之上。`Needs` 里那条 `contract.PanelRegistry` 只用于把自己的健康视图发布给 [webui.md](webui.md)——与 model、slash 同一个"往注册表里发布一块面板"的模式。

它还软连接（`TryRequire`）到 `contract.AdminLine`：源死亡、探针连续失败、恢复，这些**只有总线自己能观察到**的事件由它自己上报，不劳流程层转发。软边不进 `wantGraph`，另有 `wantOptional` 台账登记。

一条消息的完整路径：

```
入站                                    出站
─────                                   ─────
平台 SDK / IMAP / stdin                 平台 SDK / SMTP / stdout
   │  Source.Run                           ↑  streamsink.Wire
   ↓                                       │
MessageEvent ──┐                        Sink（每回合一个）
               ↓                           ↑  Source.NewSink
      stoma：扇入 + 探活                    │
               │  Gateway.Events()      Gateway.SourceByName(name)
               ↓                           │
        inbound 流程 → gate 筛查 → session 定位 → turn 跑模型与工具
```

网关在这张图上只占两格：把 N 条平台流并成一条，和按名字把源交回去。中间那一整条——谁能进、归哪个会话、回合怎么跑——都在它之上。

## 功能

### 契约面

`contract.Source` 是**双向**适配器的完整表面，一个平台要接进来必须全部实现：

| 方法 | 作用 |
|---|---|
| `Name()` | 源名。同时是会话作用域前缀、健康表主键、gate 策略文件名 |
| `Caps()` | 自我声明（见下）。构造后不变 |
| `Run(ctx, out)` | 阻塞收信，把事件推进扇入通道；ctx 取消时返回 |
| `NewSink(...)` | 为一个回合建渲染 sink |
| `Send` / `SendFile` / `SendButtons` | 一次性独立消息；error = 拒绝 |
| `HealthCheck(ctx)` | 廉价的上游存活探针，几秒内必须返回且必须尊重 ctx |

`Run` 必须是**可串行重入**的：总线会在启动窗口内用**同一个实例**重试，所以每个 per-run 字段（客户端、缓冲、closed 闩）都要在 `Run` 里重置，不能假定是 `New` 刚给的新鲜值。

### 入站：扇入

每个 source 有自己的 `Run(ctx, out chan<- MessageEvent)`，阻塞直到 ctx 取消，期间把平台事件翻译成 `contract.MessageEvent` 推进共享通道。总线为每个源起一条 goroutine，通道深度是个小常数——稳态每源一格就够，缓冲只用来吸收流程正在处理某一轮时的突发。`Stop` 取消 ctx、join 掉所有 goroutine、然后关闭事件通道，让 `for range` 的消费者自然终止。

总线只保证通道干净关闭，**不保证投递**：已缓冲但未开始处理的事件是故意丢弃的——发送者会重发。

### 出站：三条路

回复不走事件通道，直接点对点打到 source 上：

- `NewSink(ctx, target, sessionScope, sid, prefs)` —— 一次回合一个 sink，流式渲染的主路径。见下文 `streamsink`。
- `Send` / `SendFile` / `SendButtons` —— 一次性独立消息（忙碌提示、管理通知、文件投递）。按契约，返回的 error 表示**拒绝**（队列满 / 未连接 / ctx 结束），而不是投递失败。
- 可选能力接口：`contract.PhotoSender`（把文件当"图片"而非"附件"发）、`contract.MessageReactor`（👀 已读表情）、`contract.SelfMentioner`（本 bot 可被人类键入的 @handle）、`contract.MessageEmitter`（进程内注入）。调用方一律 type-assert，不实现就静默降级——`contract.DeliverPicture` / `DeliverPictureTo` 把降级规则各写一次，调用点不重复。

### 能力声明

`contract.Caps` 是 source 对上层的自我声明，其中 `Trusted` 是安全边界：零值 `false` 意味着**受筛查**，忘记声明的源被关在门外而不是悄悄敞开。只有真正非外部的源（本地终端、进程内桥）置 true——代价是它们同时绕过了 gate 的 `IsAdmin` 重盖章，因此必须自己审慎盖章。`RequiredModelTags` 则让某个源硬约束服务它的模型标签，流程在开回合时映射成模型请求的约束。

### 附件入库

四个外部平台各自的下载实现不同（CDN 直链、SDK 资源接口、MIME 解码），但入库的规矩是同一套：

- **暂存是作用域盲的。** 源把文件一律落进一个以源名命名的固定桶，由入站管线在 `ResolveSession` 跑完之后再把它们搬进已解析的会话沙箱。历史上源自己猜作用域，而它的启发式与真正的路由器会分歧，附件就落进错误的沙箱——现在源不再参与这个判断。
- **下载失败仍然登记附件**（`LocalPath` 为空）。提示层因此还能告诉模型"用户分享了一个东西，但字节没取到"，而不是当作什么都没发生。
- **禁用捕获（未接文件存储）走同一条降级路径**，而不是提前返回——提前返回会连带吞掉富文本消息里与图片并列的正文，整条消息在"无文本无附件"的闸上被丢掉。
- **文件名参与消歧。** 多模态 API 只收到字节和 MIME，没有文件名，所以一个相册里三张同名 `photo.jpg` 在模型眼里会撞成一团；按消息 id 生成唯一名字，让文本提示里的引用能对上具体那一张。

### 作用域字段

源不解析会话，但它填的字段决定了会话怎么被解析。`ScopeFor` 是把 `(source, 会话类型, chat id, thread id)` 映射成作用域字符串的**唯一**语法，写在 `contract` 里——低于它的每一个消费者（会话解析器、编排层的收件箱路由）都从这里算，两边因此不可能漂移（曾经的每源副本正是转发别名漏判的成因）。`TargetForScope` 是它的部分逆：从作用域恢复出可投递的聊天坐标，恢复不出来时明确返回失败而不是猜。

值得注意的是 `ThreadID` 的两副面孔：群/频道/话题的作用域**压平**它（同一个群就是同一个作用域），而 DM 的作用域可以被它切分成子作用域——邮件的转发别名正是用这一条，让同一个发件人写给两个别名时落进两个互不相干的会话。

### 注册与配置

`sources/10-assemble.go` 是**整个代码库里唯一点名平台的地方**：加一个平台 = 在 `00-config.go` 加一段配置子结构 + 在 `Assemble` 加一个 import 和一个构造块。stoma 本体永远学不会任何平台的名字。

配置读的是配置文件的 `sources:` 段——只有"接得通吗"这一半（开关、端点、持有凭证的**环境变量名**，凭证值本身从不进文件）；"谁能说话"那一半归 gate，另有自己的策略文件。Telegram / Feishu / Discord / Email 都是**列表**，一个进程可以同时跑多个 bot / 多个邮箱；每条目的 `name` 既是源名也是它那份 gate 策略文件的名字，留空则第一条取平台名、其余依次编号。

构造失败（缺 token、缺 secret）只**跳过那一个源**并大声记日志，绝不拖垮其他源。反之，两个源撞名会在构造期直接 panic——那是接线错误，静默遮蔽掉一个源比崩溃糟糕得多。

### 健康与生命周期

总线跑一条心跳，周期性并发调用每个源的 `HealthCheck`（每次探针有短超时；探针必须尊重 ctx，否则关机时会被留在孤儿 goroutine 上）。健康表把结果折叠成四态：

| 状态 | 含义 |
|---|---|
| `ready` | 正常 |
| `degraded` | 连续失败达到阈值（单次抖动不算） |
| `dead` | `Run` 带错误退出，本进程内不再重启 |
| `stopped` | `Run` 以 `io.EOF` 干净自退（例如无 tty 部署下本地 stdin 关闭）——不是错误，但接收循环没了 |

`dead` / `stopped` 都是**粘性**的：`Run` 退出之后，API 层探针再成功也只会撒谎（接收循环已经不在了），所以后续探针不能把它救活。

唯一的自动重启是**启动窗口重试**：进程刚起来的头几分钟内 `Run` 退出，几乎总是连通性瞬态（宿主重启后 DNS 还没起来、IM 后端短暂不可达）——这正是无人值守部署会撞上的失败，也正是"粘性死亡"会让整个入站平台在整个进程生命周期内下线的时刻。过了窗口，稳态下的 `Run` 退出就是运维该看见的真故障，退避重连由源自己在 `Run` 内部做，总线不再锤它。

告警一律异步发（新 goroutine + `recover`）：投递方 panic 会跨越 goroutine 边界，同步调用会因为一条告警而崩掉整个进程；慢的投递方也会卡住源/健康 goroutine。

同一张健康表还翻译成一块 webui 面板（一个计数 + 一张按状态着色的表）。面板标为**仅管理员可见**：`LastError` 里可能带着连接或配置细节，那是运维数据。面板是只读的——总线在这里汇报，不接受编辑。

## 内部结构

本体只有三个文件——`10-module.go`（扇入与生命周期）、`20-health.go`（健康表与探针循环）、`90-panel.go`（面板自述）。真正的体量在 `sources/` 下的九个包里：三个共享设施、四个外部平台适配器、两个进程内通道。

四个外部平台在能力上并不整齐，而这正是共享核存在的理由——差异被声明出来，由核心为它降级：

| | telegram | feishu | discord | email |
|---|---|---|---|---|
| 接入方式 | 长轮询 | WebSocket 长连接 | gateway 长连接 | IMAP 轮询 + SMTP |
| 渲染纪律 | 编辑流 | 块 | 编辑流 | 块 |
| trace 通道 | 有 | 有 | 有 | 无（一串半成品回复比一封成稿更糟） |
| 输入指示 | 有 | 无 | 有 | 无 |
| 回复锚定 | 有 | 有 | 有 | 有（RFC 线程头） |
| 表情已读 | 有 | 有（枚举映射） | 有 | 无 |
| 独立"图片"发送 | 有 | 无 | 无（附件本就内联） | 无 |
| 出站限流纪律 | 每 bot 串行槽 | 每 bot 串行槽 | 中继（库自带分桶） | 发送队列 + 重试 |
| 长度上限单位 | UTF-16 码元 | UTF-8 字节 | Unicode 码点 | 实质无上限 |

最后一行不是琐碎细节：切分必须按**平台自己计数的单位**来算，否则一条 emoji 密集的回复会在自以为安全的长度上被拒。核心因此不假设任何每字符成本模型，切分点通过 `Wire.WireLen` 在 rune 边界上二分得到。

### streamsink —— 共享渲染核

外部聊天通道的回复渲染**只有一份实现**。核心实现的是能力最全的那种情况：trace / content 双通道、限速的编辑节奏、超长自动切分、被限流后降级为块模式、"还在忙"的输入指示、以及在回合 ctx 已被取消时仍能送出最终帧。做不到其中某一项的通道**声明**这个缺口，由核心为它降级——"回退写在源里"就是指这个声明。

平台缝是 `streamsink.Wire`：`Send` / `Edit` / `WireLen` / `MaxChars` / `RateLimited` / `BenignEdit` / `EditGone` / `Typing` / `RedactErr`，加一个 `WireCaps` 声明。核心只 import `contract` 和标准库，**任何平台 SDK 出现在这个包里都是边界泄漏**。一个新通道接进 bob 只需要写自己那片叶子，网关与会话层不动。

两种渲染纪律由同一个核心长出来：

- **编辑流**（`CanEdit=true`，telegram / feishu 的编辑能力若开启）——缓冲，按固定节拍 send-then-edit，超过上限切分成消息链，持续 429 则降级为块。节拍是刻意放慢的：太快的编辑既撞平台限流，也快过眼睛能读的速度。
- **块**（`CanEdit=false`，email / feishu）——没有中途 flush，`Finish` 时一次渲染。切分照样生效（邮件返回一个巨大的 `MaxChars`，于是永不切分）。

几处载荷较重的细节：

- **`WireCaps.LineBreak`**：一个换行边界不是到处都一样写。markdown 渲染通道把裸 `\n` 读成软换行，会把整段 trace（或一份命令清单）塌成一个段落，那里边界必须是 GFM 硬换行。**只有编码**属于通道；**哪段文本是行结构的**属于生产者——只有 slash 分发器知道命令回复是 bob 自己的 UI，而模型写的表格里的换行绝不能被重写。这条决策被拆成两个所有者，也就是 `contract.LineBreakSink` 的由来。
- **`Finish` 的分叉**：`full` 是规范的内容回复，但它**不总是**此前 content delta 的拼接——回合核心会拿错误通告直接调 `Finish`，那些从没流过。核心因此渲染 `full` 相对已流出前缀的增量；一旦 `full` 与已流出的内容分叉，就整段重发。`contract.BareProductSink` 是另一侧的对称约定：ContentDelta 什么都不渲染的 sink（桥的返回 sink、邮件合批段、子回合捕获 sink）声明"我的 `Finish` 就是产物"，回合核心必须交给它裸回复，而不是带工具轮前言的累积串。
- **429 的归属**：核心把限流当**终态**——429 的节流归源级发送闸，闸已经在错误浮上来之前中继过了，还站着的 429 就是持续限流，再重试只是把回合拖更久。核心转而降级成块模式。
- **切分回滚**：中途 flush 撞到深度上限是可接受的（尾巴留在缓冲里，下一次 flush 会送）；但 `Finish` 那一次没有"下一次"，所以终态 flush 不设上限——否则会一边永久截断回复、一边报告成功。

`OnAnchor` 在**每一条**拿到平台消息 id 的新发送上触发（两个通道、切分链的每一块），让流程能在消息送出的瞬间就把它写进回复路由索引：用户回复中间某一块也能路由回原会话，而不是分叉出一个没有上下文的新会话。

### sendgate —— 出站发送纪律

"一次发送撞上平台限流时会发生什么"，只有一份实现，两种消费方式：

- **`Gate`**：每 bot 一个串行槽（telegram / feishu）。一个 bot 的所有 REST 发送——流式编辑、一次性通知、表情、文件上传——都从这一个槽过，拨号前先睡够共享的冷却下限，被限流则自己**中继**（有次数上限）而不是丢弃。平台按 bot token 限流，所以按 bot 串行是正确的粒度。没有它，两个并发群回合各自建自己的 sink（sink 的锁只在单个 sink 内串行），会并行打平台并各自独立退避，直接把限额打穿。
- **`Relay`**：同样的有界 429 重试，但**不带串行槽**，给那些客户端库自己已经按路由分桶限速的源（discord）。那里再套一层每 bot 的槽只会造成不相干频道之间的队头阻塞。

时效性是**调用方 ctx 的期限**，不是闸的旋钮：每一次等待（排队、冷却、退避）都感知 ctx，且在拨号前再查一次——一个排队排过了有用期的输入指示或表情会被静默丢弃，而不是迟到送达。调用方通过限定自己的 ctx 来声明紧急程度。

只有**被分类过的 429** 才会被中继：平台明确拒绝了这次发送，重试不可能造成重复。其他一切错误（含超时——那些**可能**已经送达了）原样返回给调用方。

### common —— 跨源小件

只有一件：`RedactErr` —— 在错误进日志之前把源自己的凭证（bot token / app secret）替换掉，再跑一遍通用脱敏器。不带秘密的错误原样返回（保留类型标识，热路径便宜）。这个包只依赖 `contract` 与共享基础设施，**永远不 import 平台 SDK**。

### telegram —— Bot API 源

体量最大的适配器。通过长轮询接更新，翻译成事件，回复走 `streamsink`。群里只在被 @ 或被回复时应答。

- **相册（media group）合并**：Telegram 把一个相册扇成 N 条独立更新，共享一个 `media_group_id`，而用户的说明文字**只骑在其中一条上**。缓冲器按组累积，在"说明文字到达"或"超时"两者先发生的一个上 flush，然后为**每个兄弟发一条事件**（不是一条合并事件）——每张图各自成回合，用户拿到的是一张图一条边界清晰的回复，而不是一整坨再被平台切碎、图文对不上。已 flush 的组还会保留一段 TTL，好让乱序迟到的兄弟捡到缓存的说明文字。
- **延迟下载**：群里未被寻址的相册，其照片**根本不会被下载**——下载被包成闭包推迟到 flush，而群闸在**组级别**判定（任一兄弟寻址了 bot 则整个相册通过），因为 @ 只在带说明的那条上。
- **@ 解析**：实体（entity）在存在时是权威的——所以 `mail bob@somebot.com` 不算 @。一条消息可以带多个本 bot 的 @，需要收集所有字节区间后**一次性倒序**切除，否则只有最后一个会被剥掉。还要处理"命令菜单发出的 `/cmd@botname`"（Bot API 约定：`/cmd@me` 等于 `/cmd`）与多 bot 群里 `/cmd@otherbot` 的整词剥离。
- **富文本**：回复文本本来就是 markdown，平台的富消息几乎就是 GFM 且**不需要转义**，所以模型的原文直接上线——这里没有转义器，也不能有（转义器会以反斜杠垃圾的形式出现在渲染里）。半开的标记（未闭合的 `**`、未闭合围栏）会降级为字面文本而非报错，这正是让编辑流可用的性质，因为流式窗口必然切在语法中间。服务端一旦拒绝富载荷，本 sink 就**粘性**降级成纯文本，避免一条回复中途在渲染与字面之间反复横跳。
- **两种"图片"**：平台的 `sendPhoto` 把图内联进对话，代价是服务端重编码——原始字节、alpha 通道、文件名都不保留；`sendDocument` 三者都留。所以选择权在调用方，且是关于**意图**的选择：刚生成给人看的图走前者，用户点名要的文件永远走后者（静默重编码是没人同意过的数据损失）。
- **token 卫生**：下载 URL 的路径段里带 token，而 `net/http` 会把 URL 包进返回的错误里。这里的包装器保留 `Unwrap`（`errors.Is/As` 仍能穿透）同时脱敏。

### email —— IMAP + SMTP 源

一个邮箱账号一个 `Source` 实例；多账号就是多实例，各有自己的轮询循环与发送队列。它是行为最不像聊天的通道，几乎每个特性都源自"邮件是异步的、有线程的、且会被人类共读"。

- **两阶段拉取与去重**：每个 uid 先只取 `Message-ID` 头（PEEK，不动 `\Seen`）跑内存去重，只有没见过的才付全文拉取 + 落盘的代价。
- **`\Seen` 是持久队列**：先发事件、后置 `\Seen`。关机时中途取消的消息保持未读，下次启动重取（at-least-once）；反过来做是 at-most-once，每次关机静默丢掉最后一条在途消息。运维可以关掉 `\Seen` 写入（好让人类共读者仍看到每封信），那时**所有**路径都不许碰这个标志。
- **错误分级**：只有**永久性内容缺陷**（MIME 结构坏、没有 From）才立即 `\Seen`——反复解析一封坏信没有意义。传输/服务端的**瞬态**错误保持未读等重连重取，但这个重试按 uid 计数封顶：反复失败到上限的毒消息也会被 `\Seen` 掉以打断重取环。
- **去重环的钳位**：每轮把未读集合钳到去重环容量以内。不钳的话，未读数超过环容量会挤掉仍然在场的 id，下一轮又把整个积压重新发一遍——一次多米诺。
- **引文剥离**：两级策略。首选是拿**上一封出站正文**做分块子串匹配，定位当前信里复现了上一封的那一段，再回退到引用头行切断——这能容忍换行位置变化、标点微调、前缀重引这些正则路子对付不了的情况；置信度不达标或没有上一封（进程刚起）时回退到多语言正则。本质是启发式：邮件客户端从不承诺任何格式，完美的剥离器不存在，目标是让文本在 N 轮之后仍然有界，不是字节精确。
- **转发别名**：当一个邮箱被声明为转发落点（自有域的多个别名都被转发进同一个收件箱）时，源从转发头里解析出**原始收件人**，挂在事件的 `ThreadID` 上——这样 DM 作用域按别名拆分、编排层也能按收件人匹配，而 `ChatID`（同时充当出站收件人地址）保持不变。回复时的 `Reply-To` 设成别名，让对方的回复顺着别名→转发器→bob 走，线程留在自有域上。
- **回复全体的环路防护**：回复的 Cc 里必须剔掉 bob 自己的所有身份（账号地址、自有域下的任何别名、当前别名），否则转发器会把这封回复送回 bob 自己的收件箱，bob 就开始自问自答。在这个名单上**不授予任何权限**，它只决定谁收到。
- **合批**：邮件不像聊天——每个回合都单独回一封是在刷屏。开启后，一个会话的多轮回复被**扣住合成一封**，在会话安静够久之后发出；按 sid 而非 scope 键（`/new` 开新会话时旧缓冲先冲掉，不跨会话边界合并）。缓冲落盘成文件，重启不丢已算出但未发出的回复。回合级系统通告（拒绝、引导、暂停提示）**故意**也走合批：一个被暂停的发件人连发五条，收到的是一封合并的拒绝而不是五封——合批本身就是反刷屏。只有非回合 sink（slash 回复、重启通知）立即发。
- **出站恢复日志**：从"进入发送队列"到"SMTP 接受"之间，渲染好的报文持久化成文件；崩溃/重启/永久失败会在下次启动（TTL 内）重放。重放是**字节等价**的——同样的头、同样的 `Message-ID`，收件人看到的是同一封信而不是重复件。这与合批是互补的两层：合批持有入队**前**的合并草稿，这份日志负责入队之后到被接受之前。之所以是文件而不是数据库行：树干刻意不给邮件源数据库句柄——一个权威历史已经存在于会话消息里的临时缓冲，文件是正确的量级。
- **头注入防御**：所有来自入站的头值在插值前都剥掉 CR / LF，否则一个构造过的 `Message-ID` 就能在回复里注入 `Bcc`。非 ASCII 走 RFC 2047 编码。

### feishu —— 企业 IM 源

通过 SDK 的 WebSocket 长连接收事件（不需要入站 HTTP 路由），回复走 IM REST API。渲染上是块纪律：该平台的消息编辑端点有速率与生命期上限，实时编辑流被推迟。

- **收信队列与去重**：WS 的 ack 泵与消息处理解耦——回调只做入队（快），固定大小的 worker 池按有界并发消费。理由是因果性的：延迟 ack 恰恰会触发平台的至少一次重投，所以在泵上同步下载附件会**放大**风暴。配套一个按 `message_id` 的去重表，在异步派发**之前**打标，两条几乎同时的重投才不会都通过。
- **卡片 vs 纯文本**：回复是 markdown，普通文本消息会把标记显示成字面量，所以**短**回复包成只含一个 markdown 元素的交互卡片。但卡片对超长内容会静默截断，所以**长**回复直接走纯文本——完整胜过好看（OCR 报告这类长文本本来也是纯文本）。短回复的卡片一旦被拒，同一段文本立刻以纯文本重试：降级成字面标记，但绝不丢。
- **父消息只取一次**：判断"是否回复了 bob"需要父消息的发送者，而那是一次 API 调用。父消息信息按 id 记忆化，于是 N 张图回复同一条提示只付一次拉取；这次拉取同时服务于群噪音闸和引用上下文。
- **群闸按 `!= p2p` 判定**，不是按 `== group`——话题群和任何未来/未知的会话类型都必须被闸住，否则 bot 会应答话题群里的所有闲聊。
- **表情映射**：跨源契约传的是可移植的 unicode 字形，这个平台的表情 API 认的是它自己的枚举，所以在源内转换。

### discord —— 服务器与私信源

通过 gateway WebSocket 长连接接入。有意**不申请特权的 message content intent**：内容只在私信、@ 提及、以及回复 bot 的情况下到达——而那恰好就是群闸本来的模型（没 @ 的服务器消息反正会被丢），于是省掉了开发者后台开关与规模验证要求。

- **频道分类失败时闸死（fail closed）**：没有服务器 id 的频道可能是 1:1 私信，也可能是多人群组私信。只有**确认过**的 1:1 才按 DM 放行；群组私信、以及类型查不到的（瞬态失败）都按群闸住——查不到绝不能让 bot 去应答一条没 @ 它的多人消息。类型是不可变的所以做了记忆化，但**只缓存确认过的结果**，失败不进缓存（免得毒化）。
- **回复内联**：这个平台把被引用的消息（含作者）内联在事件里，所以"回复了 bob"无需额外拉取即可判定，也不需要 message content intent（只有被引用的**内容**才需要）。但**转发**同样携带引用指针，必须排除——把转发当成回复，会让 agent 以为用户"回复了"其实只是转发过来的内容。
- 线程是独立频道，因此各自成作用域，不折叠进父频道。

### bridge —— 进程内"internal"源

没有上游线协议：进程内的调用方（`send_message` 工具、定时任务、主动投递）通过 `contract.MessageEmitter.Emit` 把 `MessageEvent` 直接推进网关，网关**当成真实聊天来的一样**处理。

之所以做成 Source 形状而不是一根裸通道：`Source.Run` + 事件通道这条扇入路径是唯一的规范入站路径（作用域解析、slash 分发、sid 解析、回合）。复用它，意味着一条内部发出的消息在网关以下的每一层都与人类打出来的**无法区分**。

它还是双向的：`NewSink` 是 agent→agent 派发的**返回腿**。被内部唤醒的 worker 会话，其回复必须回到调用方而不是被丢弃——sink 缓冲整个回合的内容，在 `Finish` 时朝调用方作用域再发出一条内部事件，于是调用方以一条普通入站消息的形式拿到 worker 的产物。目标作用域由会话核心算好经 `Target.ChatID` 传入，桥自己**零决策、零 agora import**。

环（A→B→A）**刻意不设机械上限**：计数或频率上限会杀死一个合法循环的 agent，两者结构上完全一样。退化的环终止于**模型的判断**——被唤醒的 worker 无话可说时会调 `stay_silent`，于是这个 sink 永远不被 `Finish`，什么都不返回，派发链就此停止。谁能被找上门，则由组织权限在更早的地方界定。

`Emit` 是非阻塞的：缓冲满返回一个可重试的忙碌信号，绝不让下游的慢拖死一个正在发消息的工具。

### local —— 本地终端源

一个小 REPL，用与 IM 平台完全相同的方式给总线喂事件，并打印回复。渲染纪律是终端追加打印，与共享核不同，**故意保持自成一体**——它不是收件箱会连上去的外部接口。

有意思的部分是并发：每个 `NewSink` 铸造自己的流通道并追加进一个 FIFO，渲染器按注册顺序一次消费一个 sink。之所以是 FIFO 而不是单槽——sink 与其消费者是异步的：一个卡在存储上的回合可能在用户已经敲下一行之后才打开它的 sink，两个回合的 sink 会同时存活，单槽会让迟到的那个遮蔽（并丢失）真正的那个。配套一个"欠账"计数与追赶循环，让迟到的回复以"迟到回复"的样子渲染出来，而不是被误记成新那一行的答案。

被丢弃的 sink 里可能装着**内部唤醒**回合的产物（worker 返回、定时任务），那些不能静默丢：会被抽干并带标题打印出来，否则终端用户得去会话历史里刨。

`Run` 在用户按下 Ctrl-D 时返回 `io.EOF`——总线据此把它记为 `stopped` 而不是 `dead`：不是错误，但接收循环确实没了，面板不该继续显示绿灯。

## 设计理据：分层注册

source **不是**树干的对等模块，它挂在 stoma 上。

理由很简单：一个 source 离开网关毫无意义。它的整个存在就是"把入站事件推进那条扇入流、把回复渲染回那个平台"——两端都是网关。把它注册成树干的对等节点，等于在架构图上凭空造出 N 个只与同一个模块通信的节点，`wantGraph` 会因为多接一个平台而变红，而那次变红什么也没审查到。

于是插件的注册面下沉一层：`sources.Assemble` 是平台的接线点，`stoma.New` 是它们的宿主，树干只看见一个 `contract.Gateway`。这带来两个直接后果：

1. **契约层不会因为加平台而变胖。** source 与网关之间是**直接耦合**，共享类型留在拥有它的一方，另一方直接 import。只有真正经树干中介的东西（`Gateway` 接口本身、流过它的 `MessageEvent` / `Target` / `Sink` 信封）才进 `contract`。
2. **平台名字只出现在一个文件里。** stoma 本体是平台盲的——它谈论的只有"源"、"扇入"、"探活"。加一个平台不动网关，也不动它上面的任何一层。

同一个模式在别处复现：`streamsink` 是渲染纪律的宿主，`sendgate` 是限流纪律的宿主，两者都不在树干上注册。谁有一群"离了我没意义"的插件，谁就自己当宿主。
