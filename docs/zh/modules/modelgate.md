# modelgate

对外的 API 网关：把 bob 的模型能力以 OpenAI 兼容的 HTTP 接口 + API key 的形式暴露给外部调用方。

## 在架构中的位置

**Provides** —— 无。它是一个纯出口，不向其他模块提供任何能力。

**Needs**
- `contract.ModelPool`（[model](model.md)）—— 唯一的硬依赖：没有池就没有东西可暴露。

**软边**（`TryRequire`）
- `contract.APIKeys`（[accounts](accounts.md)）—— bearer token 校验、每把 key 的可达范围、计费归属。缺席时**失败闭合**：每个请求 401，绝不放行。
- `contract.ImageCatalog`（[model](model.md)）—— 画风清单与提示词手册。缺席时图像端点报告「无可用画风」而不是 500。
- `contract.PanelRegistry`（[webui](webui.md)）—— 自述一块面板。缺席时无面板，服务照常。

模块 `Optional() == true`，绑定地址也是尽力而为：`listen` 失败只降级 API，不中止 agent；地址配成 `off` 或空则完全不起服务。绑定到非回环地址时会打一条警告——每个请求都要一把有效 key，但在裸 HTTP 上 key 是明文旅行的。

**它不是一个聊天入口。** 它从不碰 flow / turn / session。它只是把一个 `contract.ModelRequest` 转手给池，并在边缘做 OpenAI JSON 形状的翻译。请把它与 [model](model.md) 分开看：一个是「进来的请求怎么找到后端」，另一个是「外面的人怎么进得来」。

---

## 功能

- **OpenAI 兼容端点**：`GET /v1/models`、`GET /v1/models/<id>`、`POST /v1/chat/completions`（阻塞 JSON 或 SSE 流式，工具透传）、`POST /v1/images/generations`、`POST /v1/images/edits`，外加一个 bob 自有的 `GET /v1/key`。
- **按 key 的准入**：一把 key 要么是**车道形式**（允许进入若干个 Kind，每个请求说自己要哪一个），要么是**钉住形式**（一份条目名白名单，直接绕过路由）。两者都空 = 什么都到不了（失败闭合，不是「全部放行」）。
- **对外只说能力，不说库存**：车道形式的 key 看到的是**标签**（能力名），不是池的条目名。条目名是 bob 的内部库存。
- **计费**：每个请求在 ctx 上盖一个消费者印记（一个约定的 source 家族 + key id），池的按用户账本据此把这次调用的 token 记到 key 所属账户上。生产者与账本靠 contract 里的一个常量对齐，无需 leaf 之间互相 import。
- **能力手册共享**：`GET /v1/models/<style>` 返回画风的完整提示词手册——与对话内 `image_create` 工具读的是**同一份**。提示词指导是调得最勤的那部分，第二份副本会在做出来的下一周就开始漂移。

## 内部结构

### 服务器与鉴权（`10-server.go`）

一个极小的 `server` 结构，只装三样请求期依赖：池、惰性的 key 权威、惰性的图像目录。**这里没有并发闸**：容量是池的业务（每条目并发 + 每 Kind 等待队列 + 忙碌重试），门口的闸只能**猜**上限，而池知道真实占用。

鉴权是 `Authorization: Bearer` 加一次 `VerifyKey`。key 权威解析不到时也 401——不可用绝不等于放行。请求体有大小上限（一个粗粒度的、鉴权之后的 DoS 护栏）。错误一律渲染成 OpenAI 的错误信封。

### 目录：车道不外露（`20-models.go`）

`GET /v1/models` 对车道形式的 key 列**标签**，对钉住形式的 key 列它能钉的**条目名**。返回体是 OpenAI 的 list 形状（`data` / `id` / `object` / `owned_by`），加一个非标准字段 `state`——这是调用方唯一无法自行推断、而又必须知道的东西：这玩意现在能不能用。状态用池的原词，不做对外重命名（多一层翻译就是多一套要学的词汇）。

**车道名刻意不列出**。一条车道（`kind`）按载荷形状、key 准入、排队和记账做切分，这四件事完全活在 bob 内部；对外唯一体现「你在哪条车道」的地方是**你调哪个端点**,而端点本身已经说清楚了。请求仍然**接受**车道名以保持兼容,只是不再列。

一个筛子值得一提：图像条目可能带着一些纯运维用的标签（回退提示、能力标记），它们根本不是画风。只有**已声明**的画风才可画，所以一个未声明的图像标签若被当作能力列出来,图像端点转头就会以「未知」拒绝它——两个端点为了一个目录自己发明的名字互相指责。所以这类标签被过滤掉。

### 路由地址解析（`30-chat.go`）

`buildModelRequest` 把请求解析成一个 `contract.ModelRequest`，规则随 key 的形式而变：

- **车道形式**：`kind` 命名车道（必须是这把 key 准入的）；`requires` / `prefer` **原样**透传给池的选择器。`kind` 省略时，`model` 被读成一个能力名——解析出它属于哪条车道，正是这件事让 `kind` 可以完全不出现在外部词汇里。若一个能力横跨多条车道，端点**拒绝**而不是猜：猜错会静默地把请求送进另一种载荷形状、另一条队列、另一本账。
- **钉住形式**：`model` 就是条目名，直接 `PinnedEntry`。路由字段被忽略——钉住的意义就是绕过路由。

`requires` 作为**硬性**要求透传，与内部调用方的拼法完全一致。一套机制，不是两套：优雅降级由运维声明的标签回退链负责，链跑干了就大声失败。在这里把它软化，等于让外部流量绕开池自己的「排队胜过静默降档」保护——那条保护正是靠 `len(Requires) > 0` 判断的。

**车道准入的围栏只能立在这里**：池在钉住路径上刻意不检查 Kind，所以一把 key 的车道范围没有第二个地方可以强制。

### 流式的一个反直觉决定

文本增量实时流出。**工具调用增量不流。**

原因在池那边：一个纯工具轮次没有可见文本，所以池把它保持为可重试的，并且可能在流中途转移到另一个后端——这会重跑这个 watcher、重新发出一整套 index 从 0 开始的 tool_call 增量。一个按 index 拼接的客户端会把两段残缺的参数字符串接成非法 JSON。所以工具调用是在 `ChatStreamWatch` 返回之后、从**已定稿**的响应里**一次性完整**发出的——此时任何失败转移都已经尘埃落定。

SSE 的头是**懒写**的：只要还没有内容事件发出去，一个流前的池错误就仍然能以正确的 HTTP 状态码 + JSON 错误体呈现；一旦开了流，中途失败只能带内响（一个 error chunk 加 `[DONE]`）。

### 失败的翻译（`30-chat.go`）

`laneDiagnosis` 负责回答「为什么这次没有答案」，而且**只用 modelgate 真正观测得到的东西**：车道、以及车道内条目的健康。它刻意不宣称自己看不见的因果——**有**活着的候选就意味着池确实够到了后端而请求本身被拒（提示词过大是最常见的一种），此时说「没有后端能服务」就是一句自信的谎话。它数条目而不点名字：车道形式的调用方对应的是能力，条目名是内部库存。

它同时是一个**净化层**：池自己的错误文本里带条目名、家目录路径和管理员 CLI 命令，这些一样都不能往外走。

状态码上的一个区分：等待队列满是 **429**（后端活着，只是没地方站队了），而真正的不可用才是 503。`contract.ErrModelQueueFull` 之所以是一个跨层 sentinel，就是为了让这一层能把两者分开说。

### 图像端点（`35-images.go`）

一层薄薄的转手：鉴权、把 OpenAI 请求变成 `ModelRequest`、交给池、把字节递回去。有意思的部分（选后端、合成工作流、等任务跑完）早就在 `contract.ModelPool` 后面，且与对话内的 `image_create` 工具共用。

几个刻意的拒绝，而不是宽容：

- `n > 1` **拒绝**，而不是安静地只给一张——要了四张拿回一张且没有任何抱怨的调用方，没有任何办法察觉。
- 生成请求带 `change`（编辑强度）**拒绝**：从零生成没有东西可改，这个参数会被直接丢掉，而**被丢掉的参数在回复里读起来和被采纳的一模一样**。拒绝顺便点名那个真的接受它的端点。
- 只支持 `response_format=b64_json`（bob 不托管图片 URL）。

顺序也是设计过的：**车道准入检查排在画风查找之前**。画风查找失败会列出所有可画的画风，先跑它等于把整份目录递给一把可能根本不能画的 key,而随后对一个真名返回 403 又会确认它的存在。

「已声明但此刻没被服务」与「不认识这个名字」是**两个不同的答案**（前者 503、后者 404）：目录本身就以一个不可用状态列着它,在这里回「未知模型」会与目录自相矛盾,并且把调用方支去修一个从来就没错的名字。

`model` 在这里**命名画风**，与 `/v1/chat/completions` 里它是车道简写不同。这个分歧是刻意的：对生成而言，调用方说「哪个模型」时心里想的就是画风，而要求谁去发 `model: "image"` 只会更别扭。画风是能力名，所以这不违反「条目名不外露」。

### `GET /v1/key`（`50-key.go`）

一个 bob 自有的运行时自省端点：让 key 持有者从自己的脚本里读到**这把 key 能做什么**（它的策略）以及**它能够到的东西此刻是什么状态**（健康、上下文窗口、值得写进 `prefer` 的标签），从而据此裁剪请求。它刻意**不**暴露任何用量/账单，也不暴露任何内部身份（后端模型 id、provider、优先级、错误文本）。

一个细节：车道行**不**报一个车道级的上下文窗口。车道级的最小值 = 该车道里任何一个后端声明的最小窗口，一个工具型小模型就能把所有人拖下水，而且这个数字调用方无从行动。容量按**标签**分解上报——那才是调用方真正做 `requires` 的粒度，而且 `requires` 是硬性的，于是这个数字是一个保证。一条车道的后端若一个标签都不带，就没什么可分解的，直接报自己的窗口。

响应里还附上端点**采纳**与**静默忽略**的参数清单。这是端点的属性而非任何单个模型的属性，所以它挂在顶层。

### 面板（`90-panel.go`）

管理员可见的一小块自述：是否在服务、绑在哪、池里有多少个可交付的 llm 条目。它**不含任何 key 数据**——`contract.APIKeys` 是一个只做校验的接口，key 的管理与列举住在 accounts 那边。

## 设计理据

**外面看到的是能力，不是库存。** 条目名是运维的词汇，随时可能被重命名或换实现。标签是稳定的、有含义的、调用方真正能据以选择的东西。

**不可用一律失败闭合。** key 权威缺席 → 全部 401。key 无策略 → 够不到任何东西。这两条都不能反过来写成「没配置就是全放行」。

**别在门口再造一套限流。** 容量是池的业务，门口的闸只能猜；池知道真实占用，也早就有队列和退避。所以饱和以池自己的信号浮上来，在这一层被翻译成一个可重试的 429。

**目录说什么，端点就接受什么。** 两者必须是同一个集合，否则它们会为了某个名字互相指责，而调用方无从判断该信谁。

**一句诚实的诊断胜过一句自信的猜测。** 有活着的候选，就说「请求本身被拒了，最可能是提示词超窗」；一个都没有，才说「后端不在」。
