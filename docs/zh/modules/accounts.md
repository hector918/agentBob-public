# accounts — 跨入口身份

同一个人从不同平台进来，如何归一成同一个身份；这个身份被授予了什么、花掉了多少、以及机器怎么代表它来敲门。

---

## 功能

**身份归一。** 一个人可能有多个 telegram 账号、多个邮箱、多个飞书 app 里的 id。accounts 把它们收敛成一个逻辑**账号**，每个入口是账号名下的一个**句柄**。

**访问是被授予的，不是默认的。** 身份（有账号）与访问（有流程授权）是两层。一个刚建出来的裸账号什么都做不了，直到管理员批准。授权字段是一个逗号列表，解析规则只有一处，**没有隐含底线**——空授权授予零权限，连"基础对话"都不给。

**绑定。** 用户可以自助把自己另一个渠道绑到同一个账号上；管理员可以铸一个码交给某人，让他把自己绑到指定账号（并且有换绑权）。绑定码是通用领取令牌设施上的一次应用，而不是一套自己的令牌机制。

**记账。** 每一次模型调用的 token 数按**句柄**入账。句柄键让一个尚未绑定的人的开销也被记下来，账号维度的汇总是读取时才算的联表。

**API key。** 给账号铸一把机器可用的 bearer token，机器面入口凭它认证调用方、按所属账号计费、并按 key 上的策略限制它能到达什么。

**回复语言种子。** 记住某个发送者用什么语言说话，让一条没有语言信号的消息（比如一条纯斜杠命令）也能回对语言。这是**按发送者**的，不是按聊天的——群里每个人各自成立。

## 内部结构

### 四条契约面为什么是分开的

同一个 `Manager` 实现四个接口，但它们**故意**是四条不同的缝：

- `Accounts` 是**只读**的，因为它在路由热路径上。把写操作放进来会让每条消息都可能触发一次写。
- `AccountProvisioner` 是入职的**写**面，被入职路径懒加载。身份与访问分层，正是靠"建号"这个动作只在这条面上、且它建出来的东西没有任何权限来保证的。
- `APIKeys` 只有一个动作（校验 token）。缺席时消费方**全部 401**，绝不放行。
- `ConsumptionReporter` 窄到只有记账，所以模型池能依赖它而不必知道身份模型长什么样。

### 启动失败时的替身

模块标着 Optional：完全不注册它的部署照样跑（路由器自选，用量丢弃）。但"注册了却启动失败"和"根本没注册"必须是**两回事**。

如果迁移失败时模块干脆消失，路由器就会看见"没有身份权威"并**放开**——一个入职来源上的陌生人会直接拿到完整流程。所以启动失败时模块**照样提供** `contract.Accounts`，只不过提供的是一个 fail-closed 的替身：每个发送者都读作"未绑定"，于是路由器把非管理员送去入职或拒绝，而管理员（平台侧就已知的身份）仍能通过基础底线。语言相关的两个动作降级成空操作。

另外三条契约面**不**提供：用量丢弃、入职写入不可用——它们的消费者本来就是懒加载并能降级过去的。模块随后返回成功（而不是错误），让脊梁带着降级状态继续启动，只是健康状态标成失败，供运维视图看见；返回错误反而会触发"已提供却又报错"的中止保护。

这是"缺席"与"在场但坏了"必须给出不同答案的典型例子：前者是部署选择，后者是故障。

### 身份键：平台家族 + 稳定 uid

句柄的键不是"来源名 + 用户 id"，而是**平台家族 + 跨应用稳定 uid**。来源名可能是按机器人、按邮箱分开的（同一平台上跑着好几个），把它们折叠到家族，同一个人在你所有的机器人 / 邮箱 / 应用里就是**同一个句柄**。稳定 uid 也优先取平台给出的那个跨应用不变的标识，而不是某个应用内的局部 id。

这个折叠规则住在契约层（`MessageEvent.AccountHandle`），因为它是身份归一的定义本身，任何一方都不能有自己的版本。

句柄行同时保留**真实的**来源名与访问 uid，但只作展示与审计用——绝不从这两列反向重新授予访问。它们回答的是"当时是从哪个具体渠道绑的"，不是"他现在能从哪儿进来"。

### 绑定

`40-binding.go` 是三条绑定路径，全部在同一把互斥锁下序列化，所以两次绑定不会在同一个句柄上打架。

**自助建号**（`CreateAndBindSelf`）建一个**无流程**的账号并绑上当前句柄，**不**自动放行。理由：一旦某个来源开放了入职，一个还没被放行的陌生人就能自己建号进入完整访问、全程无人批准。所以自助路径只给身份。

**凭码绑定**（`BindFromCode`）反过来**会**自动放行——一个码本身就是管理员的批准。放行的作用域跟着兑换事件走：在群里兑换就放行到那个群（否则一个按群的白名单仍会把他挡在外面），私聊兑换就放行整个来源。如果放行没落地（没有 gate、或写入抖动），返回值会如实说"已绑定但访问待批"，而不是谎报成功。

一个已经绑在**别的**账号上的句柄默认被拒绝，只有带换绑权的调用（管理员铸的码，或真管理员本人）能重新指向。换绑时**故意不撤销**先前的放行条目：那条记录键在同一个物理渠道与同一个人身上，他现在属于新账号，仍然应该能进来。访问在换绑之间是叠加的（不存在跨账号泄漏），真正的访问移除属于"解绑"路径，不属于换绑。

**绑定码**本身是一个批命令令牌：铸码时把 `/accounts bindto <账号>`（管理员码再加上换绑标记）冻进令牌，并冻结"以管理员权限执行"这一条。因为 `bindto` 本身是管理员限定的，所以令牌冻结的权限才是让收码人能跑它的东西——码即授权，一次性、带有效期。

### 入职开通

`45-provision.go` 是入职的两端。

`EnsureBareAccount` 是**进**：给一个还没有身份的发送者建一个**没有任何流程授权**的账号并绑上句柄，同时记下他**第一次出现在哪个作用域**。它显式写入空授权，而不是让数据库的列默认值生效——否则一个裸账号会带着默认访问出生。

`Approve` 是**出**：管理员一个动作完成开通。它做三件事——把每个句柄在其真实来源上加进白名单、按入职作用域决定授予哪些流程、写入授权。

两处幂等性设计值得注意：白名单**每次都重新确认**（重复添加是 no-op），所以重跑批准可以修复一次抖动掉的放行写入；而授权字段**一旦非空就不再改写**，所以重跑批准不会把管理员后来手工配的更丰富的授权集重置回最小集。这两条顺序也是刻意的——白名单那段跑在"已授权就提前返回"之前，否则重跑就够不到它。

建号之后绑定失败时，会在一个**脱离取消**的上下文里删掉那个孤儿账号行。因为失败原因很可能**就是**上下文取消（关机撞上入职协程），复用它只会把行漏下来。

### 读路径的失败姿态

`AccountFor` 这个读取是**路由承重**的，不只是展示。所以它区分三种结果，而不是两种：

- **确实未绑定** → 路由器把非管理员送去入职。
- **已绑定，授权已读到** → 正常路由。
- **已绑定，授权没读到**（存储抖动）→ 报告"已绑定，但流程未知"。

第三种是关键。如果把存储抖动折叠成"未绑定"，一次数据库打嗝就会把一个有权限的成员送进入职流程，吞掉他的回合，还发一条"已注册，等待管理员批准"的假通知。所以未知就是未知：契约里专门有一个"授权是否真的读到了"的标志位，路由器据此对非管理员**fail-closed**——一次读没发生，就不能拿它当作放行的依据。它下一回合自愈。

这与"已知为空的授权"是两回事：空授权是一个等待批准的裸账号，是一个**确定**的答案。没有这个标志位，两者无法区分（都是空字符串）。

### 用量缓冲

`10-buffer.go` 是按句柄累加的内存缓冲。若每回合都对存储做一次读—改—写，一个活跃用户会把同一行反复热写；改成折进一张互斥锁保护的表，再由周期任务整体落盘，就变成"每个活跃句柄每个窗口一次写"，与回合数无关。

落盘挂在 trunk 的 housekeeping 调度器上——虽然它是**写入**而非清理，但让所有周期性碰数据库的任务集中调度、错开峰值，比各自转一个定时器好。模块停止时还有最后一次排空，免得优雅关机丢掉最后一个窗口。

尽力而为的边界写得很清楚：`Add` 永不阻塞、永不让一个回合失败；单个句柄落盘失败会记警告并把条目**重新入列**，下个窗口重试，所以进程活着就不丢用量；崩溃会丢掉未落盘的那个窗口。已知的代价是：这个表的规模上界只在落盘成功时成立——一次长时间的存储故障会让每轮都重新入列且没有上限，表随故障期间见到的不同句柄数增长。这一点是被记下来接受的，而不是被忽略的。

两把锁各司其职：一把保护表本身，另一把序列化落盘**过程**。快照并清空让表本身安全了，但每个句柄的"读—改—写"没有；而落盘可以同时来自周期任务和关机路径，没有第二把锁就会有两次落盘各读一次同一行、丢掉一个增量。`Add` 从不碰第二把锁，所以一个回合永远不会被落盘阻塞。

### API key

`60-apikey.go` 是机器面的身份。一把 key 的一生：

**铸造**产生一个随机 token，只把它的哈希落盘——明文只在铸造的那一刻回给管理员一次，之后系统自己也拿不回来。铸造是**全有或全无**的：除了写 key 行，它还要绑定一个**合成的计费句柄**（一个专用的来源家族 + key 的 id），这样模型池的按句柄账本就能把这把 key 的开销汇总到所属账号名下，一行新的计费机制都不用加。这个绑定失败时会回滚 key —— 一个"能用但不计费"的计费凭证绝不能存在，它的开销会永远搁浅在一个联不上的句柄下。合成来源名钉在契约层的单一常量上，因为计费正确性依赖生产方与账本方对这个字符串**逐字节**一致。

**校验**把明文哈希后查库。未知 token、已吊销的 key、账号被暂停——三种情况**返回同一个结果**，调用方无法探测是哪一种。账号状态是同一条查询里的联表，所以暂停一个账号会立刻停掉它名下所有 key，不需要额外往返。

命中时顺带更新"最近使用"时间戳，但**粗化**过：校验发生在每一个请求上，无条件写会让一个批量调用方把同一行打爆。这个字段只是个粗略的"最近还活着吗"，每把 key 每隔一段时间写一次足矣。写用的是一个脱离取消的上下文——刚认证完就取消的请求也该被记下来，而写失败绝不能让一把有效的 key 失效。

**策略**有两种互斥的形态：一种是**通道白名单**（key 可以进入哪几条模型通道，每个请求再点名要哪一条），另一种是**精确条目白名单**（把 key 钉死在具体后端上，用于评测或者反过来把它挡在某些后端之外）。两者都空意味着这把 key 什么都到不了——同样是 fail-closed，不是"什么都行"。

通道形态**刻意不带标签白名单**：请求里的标签是软偏好，只在通道内部重排候选顺序，既不能扩大也不能缩小可达范围，在它上面设围栏是自欺欺人。要设围栏就用条目形态。

铸造命令对参数极其挑剔，这是有来历的：任何一个"看起来是想写选项"的 token——尾随逗号（列表被空格截断了）、多余的等号、光秃秃的选项名——都直接报错，而不是被当成标签吞掉。以前它们会静默铸出一把策略完全不对的 key，而错误要到很久之后才以一个指向不了原因的拒绝浮现出来。同理，一个写了但为空的策略选项是错误，不是"请给我默认值"；一个拼错的通道名会当场报错，而不是交出一把永远匹配不到任何东西的死 key。

### 管理命令与面板

| 子命令 | 谁能用 | 做什么 |
|---|---|---|
| （裸） | 任何人 | 回答"我在这儿是谁" |
| `new` | 任何人 / 管理员 | 非管理员建号并绑定自己；管理员可建空号 |
| `show` | 任何人 | 看一个账号的详情；不给 id 就看自己 |
| `list` | 管理员 | 列出全部账号 |
| `mint` | 管理员（私聊） | 铸一个绑定码交给某人 |
| `approve` | 管理员 | 开通一个待批的裸账号 |
| `flow` | 管理员 | 直接改一个账号的流程授权 |
| `pause` / `resume` | 管理员 | 切换账号状态 |
| `bindto` | 管理员（令牌代跑） | 绑定动作本身；绑定码的批命令调的就是它 |
| `apikey` | 管理员（私聊） | 铸 / 列 / 吊销 API key |

`/accounts` 注册成非管理员命令，因为它的"建号"路径要对任何已被放行的发送者开放；其余子命令各自在内部检查管理员身份。裸 `/accounts` 先回答"我在这儿是谁"再给用法——其他每个子命令都要账号 id，而在此之前没有任何东西告诉过你自己的 id。

**状态与授权是两条正交的轴。** 授权回答"你能走哪条路"，状态回答"这个账号现在还服不服务"。暂停一个账号不需要动它的授权字段（因此恢复时不需要还原任何东西），它只是让访问回落到入职路径并附一条被暂停的说明；同一个状态位还在 API key 的校验查询里作为联表条件，所以暂停会立刻停掉这个账号名下所有机器凭证。

会吐出秘密的子命令一律**私聊限定**：铸绑定码、铸 API key，在群里回复就等于把码发给了所有人。

`/bindaccount` 是自助面：一个已绑定的用户给自己铸一个码，去把另一个渠道绑到同一个账号。自助码不能换绑，只能绑一个还未绑定的句柄。

面板（`90-panel.go`）是管理员限定的账号名册：一个总数统计加一张**服务端分页**的表。用量汇总是按账号的联表，太贵，不适合每次刷新都对所有账号跑一遍，所以它属于详情钻取而不是名册——名册保持轻。

## store 子包

`leaf/accounts/store` 是这个模块的持久化。身份模型、句柄、用量核算的类型与 `Store` 接口全部留在**这里**，不进契约层——`Manager` 和这个实现是它们仅有的使用者，缝是模块内部的；流程层够到 accounts 只经由 `contract.Accounts`。这正是"直接耦合的共享类型不进契约"这条规则的一个实例。

### 三张表

**账号表**是逻辑上的人：显示名、备注、流程授权、状态、入职作用域、时间戳。**句柄表**是绑上来的入口，唯一键是（平台家族, 稳定 uid），并对账号加了索引；账号删除时级联。**按句柄用量表**键在同一对上，装着一个 JSON blob 和该发送者的语言种子——注意它**不需要绑定**：一个还没有账号的人的用量和语言照样记得下。

**API key 表**只存哈希（唯一约束，也就是校验时的查询键），加上标签、策略列、状态与时间戳；随账号级联删除。

### 迁移

迁移是**保数据**的（accounts 装的是真实用户数据，不是可以随版本抹掉的缓存），每一步都写成可重复执行的形式。几处值得记的：

- 引入"访问是被授予的"这条规则时，需要一次**恰好跑一次**的数据回填，把基础授权显式盖到所有既有账号上，免得任何人在这次翻转里丢掉访问。它用的是**按 token 精确匹配**而不是子串匹配，所以既不会对已经有该授权的账号重复盖章，也不会误匹配到某个碰巧包含这个词的更长的名字上。因为它是按版本号闸住的，之后新建的裸账号不会被它重新授权。
- API key 的策略经历过一次形态变更：围栏从 key 上的一个标量搬到了请求参数上，key 改为持有一个通道**白名单**。旧列**没有被删除**——删列是不可逆的，而留着不花什么钱。于是旧形态的 key 会落到"什么都到不了"的 fail-closed 状态（需要重铸），而钉死具体条目的那种旧 key 继续工作。

### 用量 blob 的降采样

`30-blob.go` 是纯 Go 的、无 I/O 的那一半：每个句柄一行、一个 JSON blob，内容是**周期键 → 计数**的表，并按年龄降采样——近期按天、中期按月、久远按年。折叠是无损的（计数向上累加），所以**总和永远精确**，而 blob 的键数有一个与部署年限几乎无关的上界，一个世纪也就几百个键、几 KB。

一次回合就是一次读—改—写：回合数、成功数、按**种类**的 token 计数（语言模型 / OCR / 翻译各自的输入输出），以及按**原生单位**的服务用量（比如按秒计的语音）。token 与原生单位在结构上是分开的两块，所以对其中一个求和永远不会把另一个折进来。

有两处刻意的 fail-open：损坏的 blob 在**写**的时候重置成空表（这次写覆盖掉损坏数据，句柄自愈），在**读**的时候求和为零。若不这样，缓冲会把这个条目每个窗口重新入列一次、直到进程结束，把一个已经读不出来的历史变成一次永久的故障。

### 读写要点

存储层几处有意的选择：

- **显式写入而不是依赖列默认值。** 建普通账号时把授权显式写进去，建裸账号时把空授权显式写进去。两个真相源迟早会漂移，而这里漂移的后果是一个本该没有访问的账号带着默认访问出生。
- **聚合而不是 N+1。** 名册每行要显示"绑了几个渠道"，这靠一次聚合查询拿到全部计数，而不是按行扇出。
- **吊销是翻状态，不是删行。** key 行留着：它绑定的那个句柄下的历史用量必须仍然可读，而且哈希应当保持被占用。
- **语言种子只种一次**，靠冲突更新上的条件实现，所以种子是稳定的——对话中途的临时切换属于会话运行时，不属于这里。

## 设计理据

**身份与访问分层。** 建号这个动作只产生身份，任何自动的路径都不会顺带产生访问。这条约束让"某个来源开放入职"这件事变得安全：陌生人能进来说话、能被登记，但在管理员按下批准之前得不到任何东西。

**授权没有隐含底线。** 空授权授予零权限。曾经的做法是把"基础对话"当作免费的兜底，结果是访问不再是一件被明确授予的事，也就无法被明确收回。改成显式之后，一次性的数据回填把既有用户平移过去，此后每一份访问都在字段里看得见。

**未知不等于否定。** 读失败报告"未知"，由消费方决定姿态（路由器对非管理员 fail-closed，下一回合自愈）。把抖动折成"未绑定"会制造一条听起来很确定、其实是编的答案——而这条答案会直接改变用户看到的东西。

**计费键在句柄上，不在账号上。** 未绑定的人也在花钱，也应该被记下来；账号维度的数字是读取时的汇总。这条选择还让合并两个账号这类操作天然安全——句柄改指向，历史跟着走，不需要迁移用量数据。

**机器身份走同一套账本。** 一把 API key 不是一套平行的计费系统，而是账号名下的又一个句柄，只不过它的"平台"是合成的。于是新增一种机器入口不需要新增任何计费机制——绑一个句柄就够了。
