# infra：入口与进程设施

组装点（`cmd/`）、配置加载（`config/`）、文案表（`i18n/`）、日志（`logging/`）、迁移（`migrate/`），以及把架构规则焊成测试的守卫（`arch/`）。

## 在架构中的位置

这六个包**都不是 trunk 模块**——它们不出现在模块连接图里，没有 Provides、没有 Needs、不参与拓扑排序。它们分两类：

- **进程级设施**（`config` / `i18n` / `logging` / `migrate`）：与 [contract](contract.md)、[trunk](trunk.md)、[heartwood](heartwood.md) 一样，任何层都可以直接 import。它们全都无状态或只持有一份进程级单例，不持有业务知识。
- **组装与守卫**（`cmd` / `arch`）：`cmd/bob` 是唯一知道「有哪些模块」的地方；`arch` 只含测试，不含产品代码。

依赖方向是单向的：设施包不 import 任何 leaf 或 flow；`cmd/bob` import 所有模块，但没有任何东西 import `cmd/bob`。

## 功能

它们共同回答一个问题：**一个进程要跑起来，除了业务模块之外还差什么。** 答案被刻意拆散——没有中央 god-config，没有中央 schema，没有一处「注册所有文案」的初始化——每一样都是一个薄机制，由用到它的模块各自持有自己的那一份。

## 内部结构

### cmd —— 唯一的组装点

`cmd/bob/main.go` 做且只做五件事：读环境变量、装好日志与文案表、构造 trunk、按顺序 `Register` 每个模块、启动并阻塞到信号。

关键性质是**注册块就是权威清单**。包文档明确写着「gateway→source→session→turn 只是个草图，真正不会过期的模块清单是下面的 `t.Register` 块」。这不只是自律：`arch/40-registration_test.go` 用 `go/ast` 解析 `main.go`，抽出每个 `t.Register(...)` 参数的完整构造函数路径，与守卫里的固定清单逐项比对，集合或**顺序**任一漂移即失败。顺序也被锁住，是因为它是脊梁定序器的 FIFO tiebreak——注册顺序在拓扑序相同的节点之间是真的会影响启动次序的。

注册顺序里少数几处带着约束注释，都是同一个形状：某模块在 `Start` 里要读另一个模块已经填好的东西（技能目录要在授权模块之前就位，面板注册表要在自述面板的模块之前就位），而这种「Start 期的读」是软边，模块图看不见它，只能靠注册顺序 + 软边台账共同持有。

配置全部来自环境变量，`main.go` 的包文档把它们逐条列了出来。整数型环境变量解析失败会 WARN 后退回默认值——对一个「磁盘上限」这样的旋钮，静默退回等于失败向开放的方向。

启动之后进程阻塞在信号上；收到信号先**恢复默认信号处置**再跑 `Stop`，这样一次挂死的关停中途再按一次 Ctrl-C 能真的终止进程，而不是被仍在注册的信号通道吞掉。

### config —— 模块自有配置的加载器

没有中央 god-config。每个模块自己定义 `Config` 结构体，重模块自己拥有一个 yaml 文件；`config` 只提供一个泛型机制：把一个 yaml 文件叠加到一份 defaults 上。

契约是「**文件只写覆盖项**」：文件不存在不是错误，直接返回 defaults；文件存在但缺某字段，该字段保留默认值。于是只要代码里的默认值是合理的，磁盘上的配置就一直很小，无论它被拆成多少个文件。

一处必须知道的粒度差异：标量与结构体字段是逐字段覆盖，map 是逐键合并，但**文件里出现的切片会整体替换**默认切片，不是追加。因此带非空默认切片的模块必须在文件里列出完整集合，而不是只写增量。

`Load` 的实现里还藏着一条对调用方的约束：`cfg := defaults` 是浅拷贝，而 yaml 解码会**就地**写入一个已存在的非 nil map——所以 defaults 里不能带预填的 map 字段，否则文件的键会被合并进那份被多次调用共享的默认 map。

### i18n —— 用户可见文案

所有面向用户的回复文案（斜杠命令输出、队列溢出提示、重启期间错过消息的横幅等）走一张按 key 查的表。基础表是编译期 embed 进二进制的 JSON；运维可以在 `$BOB_HOME` 下用一份**逐 key**的覆盖文件只改自己想改的那几条，不必抄整张表，另外还有一份按会话钉死语言变体的覆盖。

公开 API 只有四个函数（`T` / `Detect` / `Override` / `Reload`），全部委托给一个装在 `atomic.Pointer` 里的活 catalog，所以重载期间读者永不阻塞。

三条设计取向值得单列：

- **回退链**：变体（`zh-funky`）→ 裸语言（`zh`）→ `default`，`en` 是 `default` 的别名；key 在整条链上都缺失时**返回 key 本身**——缺文案会显式地暴露在日志和聊天里，而不是变成一段静默的空白。
- **降级不牵连**：可选覆盖层解析失败只损失该覆盖层。`Load` 不早退，它记下错误、跳过坏掉那一层的贡献、继续装配其余部分，最后把已经装好的 catalog 连同合并后的错误一起返回。只有内嵌的基础表本身解析失败才是真正的构建缺陷。
- **格式化的兜底**：文案里有裸 `%`、多余的动词或参数数量不符时，`fmt` 会把错误标记嵌进输出。检测到这种标记就退回未格式化的原串——除非某个参数**自身**含有该标记（用户或提供商可控的数据），那时标记什么也证明不了，格式化结果照发。

`Detect` 是一个刻意最小的检测器：数汉字与拉丁字母，汉字不少于拉丁字母判 `zh`，完全没有文字信号返回空串。空串是有含义的——它让调用方（[inbound 流程](../flows.md)）继续沿着「管理员钉死 → 本条消息检测 → 发送者记忆 → default」这条级联往下走。i18n 自身**不持有**任何按会话或按发送者的状态；语言记忆住在 accounts 模块里，级联的编排住在流程层。

### logging —— 进程日志

`logging.Setup` 装配进程范围的 slog logger，目标可选 stdout、文件或两者。默认是**两者**：一份带轮转的磁盘文件加上标准错误——纯容器日志会随容器重建蒸发，而只写文件又会让常规的容器日志查看失效。

枚举值写错（`wran`、`fle`）时退回默认值，但是**吵闹地**退回：警告被推迟到新 logger 安装之后才发，这样它落在真正配置的那个 sink 上，而不是随着安装前的默认 logger 一起消失。

每条记录的时间戳被钉成 UTC，无论容器时区是什么。理由是运维现实：进程写不止一个日志文件，其余几个本来就是硬 UTC；一旦部署设了时区，跨文件对齐同一个回合——出问题时的第一个动作——就得在心里给其中恰好一个加时区偏移。RFC3339 让每行的时标以 `Z` 收尾，于是刻度是写在每一行上的，而不是要记住的。这与面板渲染本地时间（见 [heartwood.md](heartwood.md) 的 `clock.Stamp`）是刻意相反的一对。

轮转写入器的核心不变量是**永不丢行**，而且这条不变量是结构性的：`rotate` 根本没有错误返回值，因为它的每条失败路径都就地恢复。

- 重命名失败（目录权限、磁盘满）：**保住**当前仍然可写的 fd，武装一个退避窗口，期间不再重试轮转，直接继续追加。文件会在窗口内超出软上限——这违反尺寸约束，但从不丢行；相反，把错误冒泡上去会让写入方丢掉这一行，于是一次持续的重命名失败会把整个文件日志变成黑洞，这在没人看标准错误的部署上是最坏的结果。
- 重命名成功但重开失败：永久退回标准错误，并且**触发本次轮转的那一行也照样落在**退回后的 sink 上。
- 这两条恢复路径都不能用 slog 打日志：`rotate` 是在写入方持锁时被调用的，而当这个 writer 正是已安装的 slog sink 时，一次 `slog.Error` 会绕回自身的 `Write` 再去抢同一把不可重入的锁，直接自死锁。所以它们直接写标准错误。

同目录下的 `logging/ringfile` 是一个尺寸有界的 JSONL 追加日志，被两条审计流（授权判定日志、凭证代理调用日志）共用。它只拥有追加/裁剪/缓存 fd 这套机械，调用方各自 marshal 自己的记录格式。它的错误契约是**警告一次然后自我禁用**：打开失败或裁剪失败就永久短路后续写入，从不向调用方返错、从不阻塞热路径——审计日志失效不该拖垮被审计的那条路径。裁剪有一条硬顺序：缓存的 fd 必须在 rename 之前关闭，否则下一次写入会写进那个已被 unlink、却还开着的旧 inode。

### migrate —— 每模块自有的 schema 演进

没有中央 schema。每个模块拥有自己那串有序的迁移步骤，并在 `Start`（拿到 `contract.DB` 之后）调用 `migrate.Run`。一张共享的版本表按**模块**记录已应用版本，只跑未应用的步骤。跨模块的顺序不需要单独表达——它从 trunk 的启动顺序里自然掉出来：每个模块在自己启动时迁移自己的表，而它启动时它依赖的模块已经启动过了。

两条保证：

**单步原子。** 一步的 DDL 与它的版本推进跑在同一个事务里（Postgres 的 DDL 是事务性的），因此是全有或全无。崩在中途会把 DDL 一起回滚、版本原封不动，重跑时那一步从干净状态重新应用。所以**步骤本身不需要各自幂等**——这条对写步骤的人是实打实的减负。

**并发启动串行化。** 两个进程对同一个库同时启动时，串行化由版本行本身完成：版本推进是一次 CAS（`UPDATE ... WHERE version = <本进程读到的值>`）。竞争失败的一方 CAS 命中零行，于是**整个事务——包括这一步的 DDL——回滚**，然后重读版本、跳过赢家已经应用的部分。没有用 advisory lock：那会是后端特定的 SQL，而 CAS 在两种后端上给出同样的「绝不重复应用」保证。

步骤在碰数据库之前先做纯校验：版本必须从 1 起（`<= 0` 会排到最前面并被应用循环静默跳过，所以直接报错），且不得重号。

### arch —— 把规则焊成测试

`arch/` 不含任何产品代码。它是前面所有架构规则的**机器守卫**，而且刻意严格：这些测试变红不是故障，是评审闸——一条新的跨模块连接必须先在这里被看见并批准，才能上线。

六道守卫：

| 守卫 | 锁住什么 |
|---|---|
| `wantGraph` | 已批准的**硬**连接图（每个模块的 `Provides` / `Needs`）。任何模块增删一条边，或模块本身增删，即失败 |
| import 边界 | `leaf/` 或 `flow/` 下的包不得直接 import **另一个**模块（同模块的子包无妨）。这类连接绕过 trunk，`wantGraph` 根本看不见，所以直接禁止，没有批准台账 |
| `wantOptional` | `TryRequire` **软**边的台账。软边不是声明出来的 Needs，反射看不到——守卫扫描每个模块源码里的 `TryRequire` 调用点并比对 |
| `wantProvides` | 提供方一侧的台账，从真实的 `Provide` 调用点扫描。`wantGraph` 只看得见**静态**声明，而条件性地在 `Start` 里发布能力的模块对它是盲区 |
| `heartwoodAllowed` | 基础层准入白名单（见 [heartwood.md](heartwood.md)） |
| scrub 分身一致性 | 独立 Go module 里那份手抄的脱敏副本必须与正本逐字节相同 |

守卫的写法本身也有取向。注册守卫**解析真实源码**而不是比对一份手抄清单，且遇到无法解析的注册写法直接 Fatal——扫描必须响亮地失败，不能开放地失败，否则一种新的注册写法就悄悄逃出了同步闸。软边台账的由来更能说明问题：它以前是一份手写的注释清单，然后悄悄烂掉了（发现时已漏记 5 条边），于是被换成了机器检查。

## 设计理据

**为什么没有中央 config、中央 schema、中央文案注册。** 三处用的是同一个手法：机制放在共享的薄包里，**内容的所有权留在模块里**。模块自带默认值并加载自己的文件；模块自带迁移步骤并在自己的 `Start` 里跑；模块自带文案 key 并在渲染点查表。这直接落实了模块之间零 import 的规则——一份中央配置结构体、一份中央 schema 文件，都会立刻变成每个模块都得 import 的共享类型，把一条被禁止的耦合从后门放进来。

**为什么权威真相源是「被解析的源码」而不是文档。** 模块清单、连接图、软边、提供方边，全都从真实源码扫描出来再与固定清单比对。任何依赖人去更新的清单终将烂掉——软边台账已经用实际经历证明过这一点。而记在测试里，这份文档就永远是当下的样子，因为它对不上时构建就是红的。
