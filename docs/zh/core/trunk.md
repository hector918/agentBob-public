# trunk：薄脊梁

`trunk` 是整个进程唯一的装配点：它只认识两个抽象——一个 `Module`，和一个能力接口类型。它不知道什么是消息、会话、回合或公司。

---

## 在架构中的位置

trunk 坐在 [contract](contract.md) 和 [heartwood](heartwood.md) 之上、所有 `leaf/` 模块与 `flow/` 流程之下。它是**唯一**被允许知道"系统里有哪些模块"的地方，而模块之间彼此完全不认识。

上层的规则由此推导：

- 一个模块不能 import 另一个模块。要用别人的能力，只能拿 `contract` 里的接口去 trunk 换实现。
- 一个模块也不需要知道自己被谁用。它只声明"我提供 X、我需要 Y"，剩下的排序、检查、拆装由 trunk 做。
- trunk 自己不 import 任何模块。它 import 的只有标准库——`reflect`、`sync`、`context`、`log/slog`。

「模块」不是目录位置决定的，而是"实现了 `trunk.Module` 并被注册进来"决定的。`leaf/` 下的行为子系统是模块，`flow/` 下的流程是模块，`heartwood/` 里的进程时钟、附件清扫器、提示词工厂同样是模块——它们既是被直接 import 的基础原语，又需要一份生命周期。`sidecars/` 则完全不是模块：它们是另一个进程里的服务，主进程只通过 HTTP 找它们。

---

## 功能

trunk 解决的是同一个问题的三个面：**一堆互不相识的子系统，如何在一个进程里被正确地装起来、跑起来、拆下去。**

| 机制 | 解决 |
|---|---|
| 能力注册表 | 消费方如何在不 import 提供方的前提下拿到它 |
| 生命周期定序器 | 谁先启动、谁后启动，缺件和环怎么在启动期就炸出来 |
| housekeeping 调度器 | 十几个模块各自的周期性维护任务，如何不各转各的定时器 |

设计愿景里还留了第四个机制——异步信号总线——目前未实现。同步的**回合生命周期钩子链不是 trunk 的事**：那是 turn 与 flow 的编排问题，放进脊梁就等于让脊梁知道什么是回合。

---

## 内部结构

三个机制在一次进程生命周期里的位置是这样的：

```
trunk.New()          建注册表；建 housekeeper 并立刻把它注册进去
  ↓
Register(m) × N      收下模块，顺序此时只作为后面的 tiebreak
  ↓
Start(ctx)
  ├─ 拓扑排序        建图 → 查重复/缺失/自依赖/环 → 定序
  ├─ 逐个模块        查 Needs 是否真的在场 → Start → 查 Provides 是否真的注册了
  └─ housekeeper.start()   所有模块都登记完任务了，才开始排空队列
  ↓
（运行期）            模块之间点对点直调，trunk 不在场
  ↓
Stop(ctx)
  ├─ housekeeper.stop()    先停维护，免得扫除打到正在关闭的存储
  └─ 逆序 Stop             错误汇总不早退
```

### 能力注册表

注册表是一张 `map[reflect.Type]any`，key 是**接口类型本身**：

```
TypeOf[contract.ModelPool]()   → reflect.Type，模块用它声明 Provides/Needs
Provide[contract.ModelPool](reg, impl)
Require[contract.ModelPool](reg) / TryRequire[contract.ModelPool](reg)
```

四条硬规则，全部以 panic 在启动期兑现，而不是返回错误让调用方忽略：

- **T 必须是接口**。注册一个具体类型意味着消费方将会耦合到实现。
- **不接受 nil 实现**（含 typed-nil）。忘了构造的 wiring bug 必须炸在 `Provide` 现场，而不是几百行之后某个消费方的第一次方法调用上。
- **一个接口只能有一个实现**。重复注册直接 panic。
- **`Require` 找不到就 panic**。硬依赖缺失是装配错误，不是运行时状况；想表达"真的可有可无"就用 `TryRequire`，它返回 `(T, bool)`。

"一接口一实现"是刻意的：当同一个接口天然有多个实现（聊天源、工具），那不是一项 trunk 能力，而是**某个父模块拥有的插件集**——`Gateway` 拥有 N 个 `Source`，`ToolCatalog` 拥有 N 个 `Tool`。插件集的多态由父模块自己管，注册表里只有那个父模块提供的单一入口。这条规则让注册表永远不需要"按名字选实现"之类的解析逻辑。

### 生命周期定序器

一个模块向 trunk 暴露六个方法，其中前四个对 trunk 而言完全无内容：

```
Name()      标识
Provides()  纯声明：Start 期间会注册哪些能力接口
Needs()     纯声明：Start 之前必须已注册哪些能力接口
Optional()  Start 失败是否可容忍
Start(ctx, reg)   获取资源、起 goroutine、注册 Provides
Health()    观察点（New / Ready / Failed / Stopped）
Stop(ctx)   释放资源
```

`Register` 的调用顺序对依赖正确性无关紧要——trunk 在 `Start` 时按 `Provides` / `Needs` 建图并拓扑排序（Kahn 算法）。排序期就地报出四类装配错误：**重复提供方、缺失提供方、自依赖、依赖环**（环会连带报出所有卡住的模块名）。就绪队列是 FIFO，所以同一层里注册顺序被保留下来，启动顺序是确定的。

排好序之后，每个模块的启动都要过一串闸，失败策略是一张明确的矩阵：

| 情形 | 关键模块 | 可选模块 |
|---|---|---|
| 声明的 `Needs` 在启动前未注册（提供方是个被跳过的可选模块） | 回卷并中止启动 | 跳过它，记 warn |
| `Start` 返回错误 | 回卷并中止启动 | 跳过它，降级继续 |
| `Start` 返回错误，但它**已经**注册了某个 `Provides` | 回卷并中止 | **升级为中止启动** |
| 成功返回，但声明的 `Provides` 没有真的注册 | 回卷并中止 | 记 warn，消费方降级 |

第三行是这里最容易被忽视的一条。`Start` 的契约是"**最后**才注册 Provides——在所有会失败的步骤之后"。一个可选模块若在注册了能力之后才失败，注册表里就留下了一个半初始化的实现：下游的硬 `Require` 会接到它，housekeeping 任务会打到它上面，而它永远不会收到 `Stop`（只有成功启动的模块才进入回卷列表）。这条契约以前只是注释，现在由定序器强制。

第四行防的是另一种谎言：模块声明了 `Provides` 却没注册，拓扑排序却已经据此把消费方排在了它后面。在这里以"模块 X 声明了 Y 但没注册"报错，远好过让下游模块的 `Start` 深处抛一个 `Require` panic。

`Stop` 走反向：先停 housekeeping（避免维护任务打到正在关闭的模块的存储上），再按启动逆序 `Stop`，错误用 `errors.Join` 汇总而非早退。启动中止时的回卷同样逆序，尽力而为。

`Health()` 是 trunk 唯一的观察口，返回四态之一：`StateNew`（已构造未启动）、`StateReady`、`StateFailed`（启动失败，或模块自测不健康）、`StateStopped`。trunk 目前**只读不判**——它不会因为一个模块自报 Failed 而做任何事。这是刻意保留的接缝：断路器是设计里的后续机制，它的输入就是这个观察口。把状态机留在模块自己手里（模块知道自己什么时候不健康），把"发现了不健康之后怎么办"留给未来的策略层，是这个接口的全部意图。

### housekeeping 调度器

调度器面向的是一类特定任务：**周期性的、幂等的、持久化维护**。全项目现有约二十个这样的任务，形状高度一致：会话侧的过期 pending 清理、消息索引修剪、冷会话归档与归档清除、压缩残留清理；模型侧的用量 flush 与用量修剪；账户侧的用量 flush；管理通道、URL 记忆、编排表、检索 outbox 的各自修剪；权限模块的执行目录扫除；工具侧的沙箱扫除与生图在途恢复；以及附件存储的定期清扫。

如果每个模块自己转一个 `time.Ticker`，结果是十几个定时器在无法预料的时刻同时敲同一个库、同一块盘。调度器把它们收成**单 worker 排空的优先级队列**：

- `Task{Name, Period, Priority, Run}`。`Run` 必须幂等——契约明确：跳过一次或连着跑两次都必须无害。
- 每轮 `collect` 摘出所有到期任务，**同时立刻推进它们的 `nextDue`**，所以一个任务在自己还没跑完时不会被排第二份。
- 到期批次按 `Priority` 降序排序（同级按名字，保证确定性），单 worker 串行执行——两个重扫除永远不会在同一瞬间压住存储。
- 一个任务 panic 或返回错误不会带走调度器或它的兄弟：panic 被 `recover` 隔离，错误记日志。

三个不那么显然的细节：

**首跑不等一个完整 Period。** `nextDue` 只活在内存里，进程一重启就归零。如果首跑定在"一个 Period 之后"，那么任何 Period 长于部署重启节奏的任务将永远轮不到——每周重启一次，一个七天周期的清理任务的时钟就每周被清零一次。所以首跑取 `min(Period, 一个短的开机宽限)`：任务本来就幂等，多跑一次无害；短宽限则保证开机那一刻不做维护，启动期 I/O 保持干净。

**失败任务指数退避。** 连续失败的任务把间隔翻倍（Period、2×、4×……）直到一个上限，一次成功即复位。这样一个坏掉的扫除不会每个周期都烧一次运行 + 一行日志到天荒地老。退避永远不会排得比任务自己的 Period 更早，Period 本身已超过上限的任务不受影响。关机时 `stop()` 取消 ctx，一个规矩的在途 `Run` 会返回 `context.Canceled`——这被识别为有序停止，不计入失败、不触发退避。

**Housekeeper 不是一条 `Needs`。** 它由 trunk 自己在 `New()` 里注册进注册表，早于任何模块启动；模块用 `TryRequire[trunk.Housekeeper]` 懒取。这是刻意的：如果它是一条硬 `Needs`，每个有持久化的模块都会在依赖图上多出一条指向脊梁的边，把图涂脏，却不表达任何真实的启动顺序约束。代价是它对模块连接图不可见——这一点由软边台账补上（见下）。

## 设计理据

### 媒人不是中介

注册表只做发现：提供方注册一次，消费方在自己的 wiring 里查一次，之后**持有引用直调**。trunk 不在每次调用的热路径上。

这不只是性能考虑（虽然确实省掉了每次调用的 map 查找与动态分发）。真正的收益是**脊梁没有机会长出业务逻辑**：它从不看见一次调用，就无从对调用做任何事——没有拦截、没有路由、没有"顺便记个日志"。中介型的总线会在半年内变成一个什么都知道的上帝对象，媒人型的注册表不会。附带的好处是栈是诚实的：出问题时 panic 的栈直接指向真正的提供方，中间没有一层框架。

### 拓扑排序管硬边，注册顺序管软边

`Needs` 是硬边，进拓扑图，由定序器强制。`TryRequire` 是软边，**不进图**——它发生在 `Start` 内部，反射看不见。

于是存在一类真实的启动顺序约束，脊梁无法表达：某模块在自己的 `Start` 里软取另一个模块的能力并立刻使用。这类顺序完全由入口的注册顺序（拓扑排序的 FIFO tiebreak）持有。项目里现有三处这样的顺序，每一处都由 `arch/` 下的测试直接钉在源码上：技能目录必须早于权限模块（否则启动期的授权对账跑在空目录上，把每一项技能授权都判否）、数据库连接必须早于进程时钟（否则时钟软取不到库、回退到宿主机时钟，整轮运行的时间戳都失去校准）、学习引擎必须早于它的三个消费方（否则它们的注册悄悄落空，整轮运行的学习静默关闭）。

为什么不把它们改成硬 `Needs`？因为硬边有连带杀伤。权限模块对技能目录用硬 `Needs`，就意味着技能模块（可选）一旦启动失败，权限模块（也可选）会被整个跳过——而权限模块缺席等于工具授权全开。相比之下，软边下的失败是"对账跑晚了、技能授权判否"，这是 fail-closed 的降级。**一条依赖边的正确形态，取决于它断掉时哪一边的失败更安全。**

### 规则焊进测试

上面这些约束——模块连接图、软边台账、动态注册的提供方、三处载重的启动顺序——全部是 `arch/` 包里的机器守卫，而不是文档里的君子协定。图变了测试就红，红色本身就是评审闸：一条新的跨模块连接必须先在台账里被批准才能上线。细节见 [infra.md](infra.md)。

值得单说的是**动态提供**：能力可以在 `Start` 里条件注册而不出现在 `Provides()` 声明里（浏览器接管就是这样——只有配置了浏览器后端时才注册）。这类边对基于反射的连接图完全不可见，所以另有一份从真实 `trunk.Provide[...]` 调用点扫出来的提供方台账兜住它。同一份扫描还顺手关掉了另一个盲区：**提供了却没有任何人消费的能力**是一条死线，现在会被直接判红。

### 关键模块与可选模块的比例

三十个注册节点里，只有十三个是关键的：数据库连接、准入闸、斜杠命令表、会话、提示词工厂、回合内核、模型池、webui、网关、令牌设施，加上流程路由器、默认流程与入站流程。其余十七个——工具、技能、权限、组织、编排、学习、检索、URL 记忆、语音转写、对外 API 网关、凭证、管理通道、账户、时钟、附件清扫器等——都是可选的。

这个比例本身是一项设计立场：**一次缺件应当让系统少做一件事，而不是让系统起不来。** 每个可选能力的接口注释里都写明了"缺席时消费方怎么办"——工具目录缺席则那类工具不出现在提示词里；用量上报缺席则花销不记账；检索缺席则流程跳过写入，行为零变化；而 API key 校验缺席则**一律 401**，因为这条边的安全形态是 fail-closed。这些不是实现细节，它们是契约的一部分，写在 [contract.md](contract.md) 描述的接口上。
