# flows：策略层

`flow/` 是薄编排脚本的家。「某种对话怎么走」住在这里，可整条替换；「系统能做什么」住在下面的模块层，不动。**改行为 = 加一条流程或换一条流程，机制不动。**

## 在架构中的位置

五个流程模块 + 一个共享库。Provides / Needs 取自架构守卫里的已批准连接图：

| 模块 | Provides | Needs（硬） | 软边（`TryRequire`） |
|---|---|---|---|
| `flow-router` | `contract.FlowRegistry`<br>`contract.TurnHandler` | — | `contract.Accounts`、`contract.Gateway` |
| `flow-normal` | — | `FlowRegistry`、`Turn`、`PromptFactory`、`Gateway`、`PanelRegistry` | `MessageIndexer`、`RetrievalFeed`、`SkillCatalog`、`ToolCatalog`、`URLLibrary`、`Warrant` |
| `flow-agora` | — | `FlowRegistry`、`Turn`、`PromptFactory`、`Gateway` | `Agora`、`ChatHistory`、`MemberFailureSink`、`MessageIndexer`、`MessageStore`、`PanelRegistry`、`RetrievalFeed`、`SkillCatalog`、`SkillFailureSink`、`ToolCatalog`、`URLLibrary`、`Warrant` |
| `flow-intro` | — | `FlowRegistry`、`Gateway` | `AccountProvisioner`、`Accounts` |
| `inbound` | — | `Gateway`、`Screener`、`SlashRegistry` | `Accounts`、`SessionManager` |

`flow/compose` **不是模块**：它不注册任何 trunk 节点、不 Provides 也不 Needs，是两条主流程共用的编排库。架构守卫的 import 边界检查为它开了唯一一个口子——正因为它是共享基础设施而非模块，跨流程 import 它是被允许的。

上游：事件从 [stoma](modules/stoma.md)（`contract.Gateway`）流入，经 [gate](modules/gate.md)（`contract.Screener`）筛查，由 session 攒批并交回来。下游：流程驱动 turn（`contract.Turn`）、向 [warrant](modules/warrant.md) 要 [工具](modules/tools.md)与[技能](modules/skills.md)的授权、把回复交给 source 的 sink。各模块详情见 [modules/](modules/)，脊梁三机制见 [core/trunk.md](core/trunk.md)。

## 功能

一个回合从进程边缘走到模型再走回来，中间要做的判断可以分成两类：

**机制类**——怎么攒批、怎么持久化历史、怎么跑工具轮次、怎么压缩上下文、怎么把 token 流回聊天窗口。这些在所有对话类型上都一样，住在模块层。

**策略类**——这条消息该由谁来答；这个回合以什么身份运行；工具包由谁授权；系统提示词有哪些层、装什么；产出算不算数、要不要喂给学习回路。这些随对话类型而变，住在这里。

策略层的形状因此是「一层薄壳」：解析出 sink，组装提示词，填一份 `TurnSpec`，把它交给回合核，然后消费回合的结果。两条主流程的 `RunTurn` 是**同一个骨架**，差的是往骨架里填什么。

## 内部结构

### inbound —— 进程边缘的分流

`inbound` 是唯一一条不产生回合的「流程」：它是把 source 总线接到管线其余部分的那段接线。一个单消费循环从网关的扇入事件流里取事件，然后分流。

分流本身只有一个廉价判据：内部事件（agent 之间的派发、定时唤醒、桥接回程）还是外部聊天事件。内部事件是可信的、按目标作用域直达，不过筛查也不过斜杠分叉；外部事件走完整的入口序列。

外部路径上依次发生四件事：

**语言解析。** 每条聊天事件被盖一次回复语言的章，级联是：运维钉死的覆盖 → 本条消息自身的检测结果 → 该发送者被记住的语言 → 默认。级联住在这里而不是 `i18n` 里，因为它需要 accounts 的按发送者记忆，而 `i18n` 被刻意保持为一个无状态的检测/翻译库。语言按**发送者**而不是按会话键入——否则群里最后一个说话的人就替整个群定了语言。为了不让这条查询卡住单消费循环，读侧有一个进程内缓存（该存储列是只种一次的，所以缓存值不会陈旧），写侧则甩到循环之外去跑。

**准入筛查。** 除了被标记为可信的 source，每条事件都过集中筛查，且是**失败即关闭**：只有明确的 pass 才继续，Drop、兑换、以及任何未来的未知动作都停在这里；未知动作还会 WARN，这样新增的枚举值是吵闹的而不是被默认放行的（pass 恰好是 iota 0，掉下去就等于放行）。source 解析不出来也一样丢弃——不能因为查不到而当作可信跳过筛查。

**斜杠分叉。** `/...` 开头的事件是命令，走带外分发，而不是当作回合输入提交。这里是整条入口序列上判断最密的地方，因为「谁可以跑命令」取决于这个手柄背后的账号，而不只是筛查放没放行：平台运维一律直通；已绑定但被暂停的账号在私聊里得到诚实回弹、在群里则落入回合让引导流程处理；绑定但权益读取失败（存储抖动）的落入回合，让路由的失败即关闭去接；真正的新人落入回合，被路由漏斗送去引导。相册的多张兄弟消息会共享同一条标题文本，所以分叉前有一道去重，让一条命令只跑一次。

**提交。** 剩下的交给会话模块。`Stop` 只停消费循环：总线里收到但还没开始处理的事件被直接丢弃（发送方会重发），只有回合正在跑的那条消息有 WAL 行，启动时由恢复逻辑静默清掉。

### router —— 选流程

`router` 是会话核心看到的那个回合执行入口。它同时提供 `contract.TurnHandler`（给会话）和 `contract.FlowRegistry`（给流程们），并且在任何流程之前启动，这样流程注册时注册表已经在了。

选路只有两条规则：**按 Priority 从高到低，取第一个 `Accepts` 返回 true 的**。注册顺序无关紧要。这就是整个策略层的可替换性所在——加一条新流程 = 注册它、给它一个优先级、写它的 `Accepts`。

真正的设计在于路由把两件事拆成**正交的两轴**：

- **路径**：由**作用域**决定，与权益无关。哪条流程 `Accepts` 这份工作，就是这份工作的路径。
- **权限**：调用者对那条路径的按账号权益。

一个已绑定但对所选路径无权限的调用者**被拒绝**，而不是被改道到一条更弱的流程。这条来得不容易：早先的实现是权益优先的改道，结果一个无权益的人在组织的聊天里会被静默地交给通用助手、并且用的是那个工作者自己的作用域和会话——泄漏了本不该看到的上下文。拒绝比降级安全。

在这两轴之前还有一道**前置闸**（仅对非管理员）：未绑定或被暂停的发送者在路径运行之前就被送去引导流程。引导流程从不自选（它的 `Accepts` 恒为 false），只由路由显式返回，所以这道闸是路由的判断而不是流程之间的竞争。这里所有的缺省都指向关闭：引导流程不存在时，暂停走的是**拒绝**而不是穿透——穿透会掉到权限闸上，而权限闸根本不读账号状态，于是「暂停」这个动作会变成空动作。

第三条规则同样是失败即关闭的：权益读**失败**（存储抖动，读到的是「未知」而不是「空」）时，非管理员这一回合被拒绝，下一回合存储恢复后自愈。执行不能建立在一次没有真正发生的读之上。

路由还承担两件轻活。它把选中流程的会话模式回报给会话仲裁者，这样仲裁者不用再选一次就能缓存并持久化它；而当模式是自动时，它把「插话快速通道」置空——一个自动化回合永远不该被中途到达的用户消息牵着走。另外，只读探针（导出提示词、查询路由）走的是**不带权限闸**的选路：查看一个作用域的提示词不是一次运行时回合，管理员必须能查看任何作用域，包括自己并非成员的组织收件箱。

无流程接受时不会静默掉；路由发一条本地化提示，保住「一个回合必有一次收尾」这条不变量。

### normal —— 默认对话流程

`normal` 是 Priority 0 的兜底：`Accepts` 恒为 true，没有别的流程认领的工作都归它。

它的策略部分很短：

- **身份**：`admin` 或 `user`，由入口的管理员盖章决定。批次里**任何**一条人类事件是管理员，整个回合就升为 admin——一次排空会把几个发送者攒成一个回合，共处一室的管理员出借权限是有意设计（管理员手里握着关闭会话这根控制杆）。纯内部批次（派发回程、定时唤醒，无人在场）继承会话本身的管理员归属，所以管理员的会话在一次派发往返之后无头恢复时仍然是 admin。
- **授权方**：`warrant`。工具包 = warrant 对（身份, 目录）的授权结果。warrant 缺席时返回 nil，即**失败即关闭**——降级/测试配置得到的是没有工具，而不是整个目录。
- **会话模式**：none。忙碌队列提示与插话快速通道在这个模式下都是开的。

`RunTurn` 的骨架：解析 sink → 开一条 trace（写上流程名与本回合的会话 id，这样读 trace 的人不用另外查）→ 组装提示词 → 填 `TurnSpec` → 驱动回合核 → 消费结果。

结果消费这一段全是**按结局分门别类**的判断，值得单说，因为它是「策略在流程里」的最好例子：

- 只有真正把东西送上线的结局才算「已答复」，回报给仲裁者去触发排空的已处理回执。
- 只有干净的最终答复才把本回合最后一个 URL 标记为「满足了需求」；澄清或转交是过程性回复，问了个问题或者交了班，不该算作被满足。其余结局也要显式消费掉那条记录，否则按会话的追踪表会漏。
- 冷记忆的写入只在干净结局（最终答复或有意的过程性回复）时入队：降级放弃的回复是一句套话，取消和出错什么也没送出去，都不属于可召回的语料。

另外两处写入与「回复能接回哪个会话」有关。回合结束后把送出去的那条平台消息 id 记进索引；同时，只要 sink 支持，就在**发送的瞬间**把每个通道的锚点消息也记进去。后者不是优化：没有它，用户回复 trace 行、或者在流式输出到一半时回复，都会索引落空，从而分叉出一个新会话，而不是折进正在忙的那个会话当作插话。两处写入都把 ctx 解绑，因为回合的 ctx 会在关闭会话与进程停机时被取消，而这条路由索引必须照样落地。

`composePrompt` 是纯函数：同一份工作进去，同样的（身份、提示词构建器、技能集、工具集）出来。运行回合走它，导出提示词也走它——所以导出的就是真回合会用的那一份。里面的提示词层被**按自上而下的顺序全部钉住位置**，包括暂时留空的槽位，因为 `SetLayer` 第一次设定就固定了渲染位置，这段代码本身**就是**渲染顺序。

### agora —— 组织成员流程

`agora` 是 Priority 10 的特化流程，认领那些作用域路由到某个组织收件箱的工作。组织模块不存在时它什么也不认领，兜底流程接管一切——所以它可以是 Optional。

它与 `normal` 共用同一个骨架，换掉的是每一处策略：

| | normal | agora |
|---|---|---|
| Accepts | 恒 true（Priority 0） | 作用域解析到收件箱（Priority 10） |
| 身份 | 入口盖章的 admin / user | 组织主体（成员 / 收件箱哨兵） |
| 工具包授权 | warrant 的授权矩阵 | 组织**供给**成员投影，warrant **裁决** |
| 凭证 | warrant 矩阵 | 组织的公司授权来当闸，warrant 出构建机制 |
| identity 提示词层 | 默认助手人设 | 该成员的身份卡（**替换**掉默认人设） |
| platform 提示词层 | 留空 | 通讯录 + 公司运作说明 |
| 会话模式 | none | auto（自主工作者：队列提示静默、插话通道关闭） |
| 回合驱动 | 由会话出生时的盖章决定 | **无条件**长任务循环 |
| 冷记忆分区 | 按调用者（私聊按手柄，群按房间） | 按成员主体 |
| 失败学习 | 无 | 降级回合喂给按角色 + 按技能两个学习器 |

几处结构值得展开：

**授权的形状是「供给 / 裁决」分离。** 组织模块知道谁在哪家公司担任什么角色、公司授予了什么，但它不做判决；它把成员投影交出来，由 warrant 这个**唯一的裁判**去与目录取交集。这样「谁能用什么」只有一套判决逻辑，无论请求来自个人对话还是组织成员。文件与执行通道则始终是 warrant 绑定的，可达空间是「成员自己的工作区 + 每家所属公司一个」。

**桥接收件箱只路由，从不跑模型。** 一个公司的「找人类」线路是纯转发：内部（工作者发出的）消息转到绑定的外部聊天，外部（人类回复的）消息重新注入到下游成员收件箱。这个判断排在最前面，在解析 sink、组装提示词之前——省掉的不只是开销，更是保证这条线路不可能意外地跑起一个回合。附件跨桥时会被**复制**进下游作用域的空间（两侧都走各自被限制在自己空间根下的文件通道，从不做跨根的裸拷贝），复制成功后重新渲染的转发文本会**去掉**这些附件的清单行——下游回合会自己再列一遍，留着就会显示两次。复制失败则整体降级为纯文本转发，此时文本里的清单行反而成了「发生过什么」的记录。

**暂停有两层，都是显式回弹而不是改道。** 公司级暂停会停掉整条链路，桥接也在内。成员级暂停单独判断，而且这个作用域**仍然被 `Accepts` 认领**——否则一次可逆的暂停会把一个公司群静默地改道给通用助手，之后人类的回复还会重新接进一个普通会话里去。认领了再回弹，语义才是干净的。

**虚拟群需要问「找谁」。** 一个群可以同时接若干成员的收件箱，人类用 `^成员名` 这个前缀来点名。没点名又没有默认成员时，流程不跑回合，而是列出成员让人类选——并且列的是**逐个探测过、当前可用**的那些（一次扇出可能横跨多家公司，一家的暂停不能推广到另一家）；全都不可用时改发暂停回弹，而不是请人从空名单里挑。列表里每一项都会带上本机器人的 @ 手柄前缀，这样在有多个机器人的群里，那一行是可以直接复制的**完整**地址。

**被寻址掩盖的斜杠命令要被拦下。** 入口的斜杠分叉只认**行首**的 `/`，所以 `^成员 /命令` 会溜过分叉；到了流程里剥掉寻址标记之后，那个裸的 `/命令` 就会作为字面文本进入模型，而模型会**扮演**这个命令而不是执行它。所以流程精确拦截「剥掉标记后**露出**行首斜杠」的那些事件：裸命令根本到不了回合（入口已分发），工作者自己生成的 `/` 开头文本（没有标记）仍是普通输入。

**降级回合喂学习回路。** 只有降级结局（打捞或未达标）才快照一次这个回合并同时喂给两个学习器：成员级（每个降级的组织回合都是一次角色失败，按作用域上报）与技能级（按模型经由技能查看真正调用过的技能上报）。澄清与转交是过程性结局而非失败，按结局判据而不是按「有没有回复」判据，正是为了不让一个合理的提问被当成失败去训练。快照的动作窗口锚定在本回合最后一条用户行上；如果这一回合已经滚出回放上限、锚不到，就用**空窗口**并如实写「动作未知」——宁可这一轮什么也学不到，也不要把上一回合的工具调用折进这一回合的失败快照。

### intro —— 机械化引导

`intro` 是**唯一不调用模型**的流程：检测发送者的语言，回一条固定文案说明怎么拿到账号，没有 agent、没有历史写入。

它从不自选（`Accepts` 恒 false），只由路由显式返回。三处细节：

- **按（来源, 聊天, 发送者, 已发文案）去重**，一条通知只发一次。键里带聊天，是因为只按发送者去重时，一次群里的提示会永久地把这个人后来的私聊问询也静音掉；键里带已发的文案，则让群里在「待批准 → 被暂停」的状态变化上保持一条中性提示，而私聊会因为文案键变化而重新通知。
- **群里的回复是中性的。** 群里的回复所有人可见，所以它给一句「私聊我」的提示，而不是把账号状态（待批准 / 被暂停）公开给整个房间；私聊才给状态相关的具体文案。
- **只有发送成功之后才记去重。** 代价是两条消息竞态时有一个极小的重复窗口，但这远好过一次瞬时的发送失败把唯一那条引导消息永久吞掉。同理，sink 解析不出来时也不记——下一条消息会重试。

回复之前，未绑定的发送者会被铸出一枚**裸账号**（无权益、待批准），这样管理员手里有东西可以批。这一步在去重检查之后，所以它每次问候跑一次，而不是每条消息都跑。

### compose —— 共享编排库

`compose` 是两条主流程共用的机制。分工的原则是：**流程复制编排（几行壳），但不复制逻辑**。

具体地说，「哪些提示词层、按什么顺序、身份从哪来、工具包谁授权」是策略，留在各自流程里；而下面这些在两条流程之间**逐字节相同**的东西住在这里：

- **静态提示词层的加载与播种。** 四个静态层各有一份内置默认值和一个运行时可编辑的文件。默认值只是种子（文件不存在时写一次，从不覆盖已编辑的文件），文件才是活的来源——每回合读一次，所以运维的编辑不需要重编译、也不需要重启就生效。种子写入走「写临时文件再改名」，避免崩在半途留下一个**残缺**的层文件被后续原样加载。文件被清空时回退到内置默认值：把文件清空不应该悄无声息地从系统提示词里剥掉一个核心层。
- **用户文本的拼接与附件清单。** 附件按**空间相对路径**列出——那正是工具的文件通道读取时用的字符串，所以模型可以把它原样传给工具，不需要任何按工具实现的「名字→路径」解析器。清单里的每一行都过控制字符清洗（防止构造的文件名注入出额外的列表行），但**不截断**（截断会把扩展名切掉，模型回显的路径就再也解析不了）。下载失败的具名附件也会如实列一行「未能读取」，而不是被丢掉——否则一个带说明文字的失败附件会完全隐形，模型会当成纯文本来回答。已经转写过的音频会附一句「内容已转写在上文」：一段被渲染成裸路径的语音与一个没被碰过的文件长得一模一样，模型会花一整轮工具调用去取一份就在上面几行的文字。
- **技能索引层。** 只在技能查看工具确实在本回合的工具包里时才渲染——「用某个技能」和「能调用技能查看」是两条独立的授权，让模型去调一个它调不动的工具，出来的是一个假装成幻觉的配置缺口。
- **工具选择规则层。** 从**本回合可见**的那些工具各自的选择提示里现拼一张「什么场景用什么工具」的表。看不见的工具不贡献任何一行，所以这张表永远只由模型真能调用的工具组成。
- **绑定通道。** 一个对象两副面孔：文件/执行空间的开启器，以及按种类唯一的凭证开启器。一次构造出两副面孔，是为了让 `TurnSpec` 上那两个字段不可能漂开。空间参数是硬闸：非空的空间必须是默认空间或在允许集合里，否则拒绝，并在错误里列出可达空间让模型自我纠正。空**主体**同样被拒绝——一个未识别身份的回合今天之所以安全，只是因为它的工具包恰好是空的，但本地通道按空间目录限制、并不看身份，所以「没有主体就没有能力」必须在这里显式成立，而不是依赖「恰好没有工具存在」。
- **附件集。** 模型对图像是盲的，它对某个具体文件的唯一抓手就是提示词里那份清单上的名字。解析顺序是：命中本轮批次里的具名附件 → 命中**更早回合**留在空间收件箱里的同名文件 → 本轮批次里符合谓词的那些。第二步排在第三步之前是有意的：清单承诺了路径跨回合仍然可解析，所以「不，第一张」必须赢过「默默换成本轮唯一的那张图」。
- **导出提示词的骨架。** 每条流程的导出共用同一套渲染与用户文本准备，流程只提供它自己组装出来的东西。这是防漂移的：曾经出现过一条流程的导出忘了做真回合会做的文本准备，于是导出的与真跑的对不上。

`compose` 还持有几条**两条流程都要用**的提示词常量，最典型的是长任务工作模式的纪律层：它讲清这个模式的契约——收敛才交付、过程对用户不可见所以最终回复必须自包含、信息缺口如实写明。放在共享层而不是各流程一份，是因为兜底流程在被盖章为长任务时注入它，而组织流程**每个回合**都注入它。

## 设计理据

**为什么 compose 存在，以及它为什么不是模块。** 架构原则是「一条流程复制编排，不复制逻辑」。如果两条流程各持一份提示词组装，它们会漂——而漂移的表现是一条路径上少了一层防御、或者导出的提示词与真跑的不一致，都不是编译错误。把逻辑压成一份，两条流程就只剩下几十行真正表达策略差异的壳。它不做成模块，是因为它没有生命周期、没有资源、不 Provides 也不 Needs；做成模块只会为一个纯函数库凭空造出一条 trunk 边。

**为什么「路径」与「权限」必须正交。** 把它们合成一轴的写法（按权益选流程）读起来更简单，但它把一次授权失败变成了一次**改道**，而改道的落点带着别人的作用域与会话。拆成两轴之后，无权限的结果是一句「你在这里没有权限」，唯一的例外是把一个还没有任何权益的新人送去引导——那句「已登记、等待批准」对他而言是真的。判断真假是这里的判据：一个已经有权益、只是没有**这条**路径权益的人不会被送去引导，因为那会承诺一个没人会去处理的审批。

**为什么这一层的缺省一律指向关闭。** 工具包在 warrant 缺席时是 nil 而不是整个目录；技能索引在授权读不到时是空的；权益读失败时这一回合被拒绝；引导流程缺席时暂停走拒绝而不是穿透。共同的形状是：**执行不能建立在一次没有真正发生的读之上**。降级配置得到的是少一点能力，而不是多一点。

**为什么回合的结局要分门别类，而不只看「有没有回复」。** 结局分类喂着四条下游回路：排空的已处理回执、URL 库的满足度信号、冷记忆语料、失败学习。这四条对「一次澄清提问」的正确态度各不相同——它是一次真实的答复（回执该发），但不是一次被满足的需求（不该标记满足），是可召回的语料（该入库），却**不是**一次失败（不该拿去训练学习器）。只看「有没有回复」的话，这四条里至少有两条会判错。
